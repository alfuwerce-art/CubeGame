# Контракты данных и handoff

Файлы JSON Schema Draft 2020-12 и примеры описывают проект. Примеры имеют `example: true`, нулевые SHA-256 там, где файл не создавался, и частичный скелет для чтения структуры. Будущий исполнитель должен отклонять такие документы при запуске и проверять хэши реальных байтов. Числа clearance и камеры в примере иллюстрируют форму контракта. Они не задают допуски владельца.

| Контракт | Ключевые данные | Пример и схема |
|---|---|---|
| STYLE_LOCK | Версия художественного стиля, checkpoint, LoRA model/CLIP, sampling, палитры и классы материалов, свет, запреты, способы conditioning, путь и политика прав для каждой модели и референса | [пример](contracts/style-lock.example.json) · [схема](contracts/style-lock.schema.json) |
| GEOMETRY_REFERENCE | Манекен, раса/форма тела, метры, источник, 3D landmarks, сегменты, суставы, rest transforms, rig pin, слоты с размерными ограничениями и сокеты, camera matrices, маски и контрольные изображения по виду | [пример](contracts/geometry-reference.example.json) · [схема](contracts/geometry-reference.schema.json) |
| ASSET_PROFILE | Категория, тип, слот, описание, совместимость расы/тела/рига, приоритеты геометрии, material/palette, generate vs required views, seed, шаблон, требования к image/technical handoff | [пример](contracts/asset-profile.example.json) · [схема](contracts/asset-profile.schema.json) |
| RUN_MANIFEST | Разрешённые версии и pin, граф, входы/выходы с SHA-256, camera/seed, ПО, параметры запуска, попытка и раздельные результаты image/fit/review | [пример](contracts/run-manifest.example.json) · [схема](contracts/run-manifest.schema.json) |

В production контракт `schema_version` управляет структурой и совместимостью parser. Каждое изменение семантики, весов, текста, упорядочивания, камеры, геометрии, входного файла, slot masks или binding выпускает новую неизменяемую ревизию сущности. После ревью запрещается перезаписывать содержимое по старому id/version. Pins всегда `{id,version,sha256}`. SHA-256 вычисляется над точными байтами файла в хранилище (UTF-8 для JSON, стандартизировать LF и сериализацию при создании). `run_id` — SHA-256 канонического JSON перечисленных pins, входных файлов, software fingerprint, view и effective seed; порядок списков значим. Попытка с изменением входа получает новый run ID и записывает parent/разницу в отчёте. Одно и то же задание переисполняется в отдельной попытке. Для GPU-выхода битовое совпадение проверяется только в закреплённом окружении. Вне него сравнивать детерминированные входы, метрики и видимые свойства.

## Разрешение графа

1. Разобрать три входа и выбрать шаблон по категории. Разрешить закреплённые версии, не выбирать latest. Совместимость проверяется по race/form/rig hash и slot ID. Проверить существование, локальность, SHA-256 и права всех зависимостей. Пути относительны к закреплённым явно каталогам и не могут выходить из них.
2. Порядок параметров фиксирован: STYLE_LOCK + зарегистрированный профиль категории → ASSET_PROFILE добавляет описание и материал → GEOMETRY_REFERENCE поставляет camera, crop, socket и изображения. Холст, mask и поза берутся из geometry. Профиль не может переопределять обязательные лимиты стиля/слота. Никакого молчаливого fallback при конфликте.
3. Проверить связи, выходящие за рамки JSON Schema: уникальность ID, родителя и порядок костей, отсутствие циклов, правильность матриц row-major (столбцовый вектор), ортонормальность камеры и пересчёт px/m, bounds min≤max, clearance min≤max, near<far, conditioning begin≤end. Генерируемые виды должны входить в required views. Один pack хранит записи по (slot, view) без дублей. Проверить edit ⊆ allowed, required ⊆ allowed, отсутствие противоречий с keepout, совпадение image frame, mapping родительского кадра, типы масок и ID. Модель CN и веса IPAdapter должны подходить к checkpoint family.
4. Подставить входы в один API-граф на вид. Вычислить hash графа и сравнить типы входов в `/object_info`. Зафиксировать bindings, промежуточные хэши, модели, параметры, effective seed, launch flags, software versions/коммиты, fingerprint устройства и метрики. Технические виды после fit публикуются с хэшем mesh revision и независимым источником `BLENDER_METRIC`.

## Форматы выдачи

| Данные | Формат | Происхождение и использование |
|---|---|---|
| Raw и worn | PNG RGB sRGB, один вид/один элемент, точный холст | Raw вывод ComfyUI; worn композит по edit keepout. По raw сохраняются метрики до обрезки |
| Isolated preview | PNG RGBA, straight alpha, 255 = foreground | Проверенная сегментация либо matte шаблона с явным source/mask confidence. Для технического выхода рендер того же меша |
| Маски/индексы | Lossless PNG, 8-битная бинарная 0/255, 8/16-битные ID по таблице | Template либо Blender object/material pass. Значение 0 — фон, nearest для resampling. Edit, silhouette, keepout и raw segment выдаются отдельными файлами |
| Depth/normals | OpenEXR float, validity mask, единицы и пространство | Источник Blender camera. Глубина или нормали, оценённые моделью, имеют `COMFYUI_ESTIMATE` и пригодны только для кондиционирования/диагностики. Без достоверного метода normals необязательны |
| Camera/landmarks | JSON, поза, projection matrix/ortho, hash источника и z validity | Проверка регистрации. Комбинация разных camera revisions требует явного remap |
| Материал | UV PNG без запечённого освещения где возможно, palette/ID JSON | Семантика цвета, тип поверхности, ID и вариант палитры. Раскраска переиспользует geometry |
| 3D | .blend, независимый .glb, rig/binding IDs и отчёт | Blender; на stage gate проверяются единицы и преобразования осей, reattach к тому же rig, отдельные детали и тестовые позы. .fbx — только отдельный форматный пилот |

Полярность на файловой границе — белый означает принадлежность выбранной области, alpha 1 означает непрозрачность. В локальном коде `LoadImage` MASK из alpha даёт `1-alpha`, а `JoinImageWithAlpha` инвертирует входную mask. Адаптер нод обязан привести полярность явно; контрольные случаи с полупрозрачностью и белой шахматкой проверяют соответствие. Проекция из RAW PNG без известной камеры и metric depth не даёт скрытых поверхностей.

Handoff включает весь обязательный набор артефактов, ссылки на pack/style/profile и результат проверки. `IMAGE_CANDIDATE` допускает рассмотреть переход к fit. Согласованные виды, размеры и веса считаются доступными после 3D gate. Библиотека принимает только владелец.
