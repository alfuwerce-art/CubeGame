# CubeGame — архитектура Unity v0.2 (проект на утверждение)

**Рабочее название:** CubeGame; финальное название игры не выбрано.  
**Статус:** PROPOSED / NOT APPROVED **как целый документ**. A03 (модульный монолит) утверждён в [ADR-0001](../architecture/ADR-0001-modular-monolith.md); разделение Data / Game Logic / View / Input / UI / Save/Load / Utils **как принцип** принято в [ADR-0002](../architecture/ADR-0002-data-driven-layered.md). Другие A01–A09 не становятся утверждёнными автоматически; отдельная реализация — по [плану внедрения](../architecture/DATA_DRIVEN_ADOPTION_PLAN.md) и авторизациям этапов.  
**Основание:** `DECISIONS_001-036.md`; при противоречии приоритет у решений продюсера.  
**Цель:** локальное воспроизведение игровых систем Cube World Alpha 2013, затем отдельные этапы расширения без разрушения основной архитектуры.

## A. Решения, предлагаемые для утверждения (ADR-кандидаты)

| ID | Рекомендация | Почему | Что остаётся проверить |
|---|---|---|---|
| A01 | Unity 6.3 LTS, конкретный patch pin в `ProjectVersion.txt` | Поддерживаемая производственная ветка | Запуск на рабочем ПК, совместимость пакетов |
| A02 | Universal Render Pipeline (URP) | Масштабируемая графика, собственные материалы и эффекты | Профиль тяжёлой сцены, тени/трава, fps |
| A03 | C# модульный монолит с Assembly Definition для границ | Изоляция ошибок, редактируемые и тестируемые подсистемы | Проверка сборки пустого стенда |
| A04 | Одна авторитетная игровая симуляция локально; UI и 3D отображают её результат | Будущая возможность переноса авторитета на сервер | Проверить бой/перемещение в тестовой сцене |
| A05 | Seed + версия генератора + ID объектов + постоянные дельты/состояния | Регенерация не сбрасывает действия игрока | Переоткрытие старого мира после изменений |
| A06 | Иерархическая симуляция NPC: детально рядом, экономно вдали | Не вычислять физику и LLM всего мира | Нагрузочные испытания с большим количеством NPC |
| A07 | Версионированные сохранения, безопасная запись и восстановление | Стабильность в длинных прохождениях | Тест прерванного сохранения/миграции |
| A08 | Модели+анимации как единая проверяемая pipeline | Не выпускать несовместимые ассеты | Пилот на одной модели в S05A |
| A09 | Сеть и платформа плагинов **не реализуются сейчас** | Нет затрат на сервер/лишних зависимостей | Будущая адаптация может потребовать рефакторинг |

Никакие художественные решения или окончательный список биомов в S01 не фиксируются. Никаких обещаний 100%-й детерминированности физики Unity или отсутствия переделок при переходе к сетевой игре.

## B. Зависимости и ответственность

```text
      CubeGame.Presentation (UI, 3D, camera, animation, VFX)
                               |
                         commands / views
                               v
                   CubeGame.Application (flow)
                               |
             +-----------------+------------------+
             |                                    |
      CubeGame.Features                 CubeGame.WorldRuntime
      (combat, NPC, quests,             (streaming, terrain,
       inventory, progression)           physics adapter)
             |                                    |
             +------------> CubeGame.Core <--------+
                               ^
                               |
                 CubeGame.Infrastructure
                 (save files, LLM/STT, asset IO)

Future: network adapter around commands, events and state.
```

- **Core:** типы ID, игровые команды/события, правила валидности, данные состояния, часы, общие интерфейсы; минимум зависимостей, по возможности без `UnityEngine`.
- **Features:** персонаж и навыки, бой, инвентарь и предметы, NPC, задания и фракции. Не обращаться напрямую к UI/сценам/сериализации. Взаимодействовать через согласованные интерфейсы и доменные события; исключить циклические зависимости.
- **Application:** управляет жизненным циклом игрового мира, валидирует команды, координирует модули, определяет порядок событий и сохранений.
- **WorldRuntime:** адаптер Unity к физике/коллизиям, генерация/стриминг объектов в сцене, пространственные запросы. Существенные результаты возвращаются симуляции, а не меняют её состояние из рендера.
- **Presentation:** камеры, меню, HUD, риги, анимации, материалы, аудио, эффекты. Читает снимки состояния, отправляет команды.
- **Infrastructure:** файловая система/сейвы, локальная LLM и распознавание речи, загрузка конфигураций, внешние интеграции.

Рекомендуемая структура: `Assets/CubeGame/{Core,Application,Features,WorldRuntime,Presentation,Infrastructure,Content,Tests}` с отдельными assembly definition там, где они дают измеримую пользу. `Packages/manifest.json` и `ProjectSettings/ProjectVersion.txt` фиксируются в Git. Для тяжёлых моделей/текстур позднее оценить Git LFS.

## C. Симуляция мира и времени

- Локальный процесс является **единственным владельцем правды о мире**. Создание нового прохождения создаёт независимый слот мира/персонажа; регионы одной игры принадлежат одному прохождению.
- Единый управляемый симуляционный цикл (фиксированный игровой шаг для значимых событий). Визуальные кадры рендерятся независимо, интерполируются при необходимости. Конкретная частота — после профилирования.
- **Рядом с игроком:** AI, перемещения, боевые состояния, коллизии, анимационные представления.
- **Удалённые регионы:** NPC, торговые маршруты, расписания, фракции и последствия событий живут через расписания/упрощённые переходы состояний; без каждой физической итерации и без постоянных LLM-запросов.
- **В очень далёких областях:** не обновлять бесконечный набор клеток; учитывать только запланированные существенные события и устойчивые сущности. Случайные процессы — с независимыми потоками PRNG, стабильными для тестирования.
- **При выходе из локальной игры:** симуляция полностью прекращается; не начислять прогресс за реальное время отсутствия.
- **Будущий пользовательский сервер:** пока есть игроки — симулирует; после выхода последнего — пауза (D17).
- Нейросеть не принимает окончательное решение об изменении мира: формирует диалог или предложение действия, которое проверяется обычным игровым кодом.

## D. Генерация, стриминг, стабильные ID

- Регион определяется `WorldId / WorldSeed / RegionKey / GenerationVersion`.
- Чанки нужны для **загрузки и выгрузки геометрии**, а не для стирания изменений. Не генерировать все кубы как отдельные GameObject; комбинировать геометрию, инстансировать повторяющиеся объекты и использовать LOD там, где это выгодно по профилю.
- Для каждого процедурного важного объекта — стабильный ID, воспроизводимый из региона, типа и стабильного локального идентификатора; порядок перебора коллекций не должен незаметно менять ID.
- Перемещение мировых NPC между регионами требует глобального реестра логических сущностей, исключающего дублирование при загрузке соседних чанков.
- Визуальные объекты могут уничтожаться при выгрузке чанка, но **логическое состояние** NPC и изменённых локаций не должно уничтожаться.
- Изменение генератора требует сохранения версии/миграции мира, а не тихой перегенерации городов и локаций.
- Размеры чанка и региона, дистанции стриминга, origin shifting для дальних координат и бюджеты памяти утверждаются на основании технических тестов S01–S02; не назначать их наугад.

## E. Сохранения

**Пример логической структуры (не утверждённый формат):**

```text
Saves/<WorldId>/
  manifest (schemaVersion, generatorVersion, worldSeed, gameTime)
  player
  global_state (quests, factions, migrating NPCs)
  regions/<RegionKey> (persistent objects + deltas)
  checkpoint / recovery metadata
```

- Генеративный неизменённый фон восстанавливается по seed, а изменённые объекты, владение, разрушения, память NPC и последствия заданий сохраняются.
- Для крупных состояний допустимы snapshots; дельты используются там, где они экономнее. Не хранить бесконечный журнал без компакции.
- Каждая запись имеет `schemaVersion`; валидировать ссылки/ID и проверять целостность.
- Сохранение в безопасный временный набор, подтверждение контрольной записью, затем переключение на новый checkpoint. При падении — восстановить последний подтверждённый, не считать незавершённую запись успешной.
- Автотесты: повторная загрузка разрушенного лагеря, NPC в другом регионе, изменение фракции, выход в момент записи, несовместимая версия генератора.

**Выбор физического формата (JSON/бинарный/встраиваемая БД) отложен до измерения размера и скорости тестового мира.** Не принимать предварительный формат за архитектурное решение.

## F. Подготовка под будущую сеть (без сервера сейчас)

Команды `Move/Attack/Interact/ChangeItem` должны приводить к проверенному изменению единственного источника состояния; Presentation не устанавливает HP, лут или владение напрямую. Сообщения и снимки содержат стабильные ID и сериализуемые данные. Локальные действия не требуют сетевого подключения.

В будущем сетевой адаптер и авторитетный хост будут владеть симуляцией и реплицировать разрешённые состояния. Физика Unity сама по себе не обеспечивает сетевой детерминизм. Задержки/предсказание клиента, боевые столкновения и владение объектами потребуют отдельного проектирования в S11. **Не создавать сейчас локальный сервер, платный хостинг, Netcode-зависимости или SDK модов.**

## G. Pipeline ассетов и графики

- S01 утверждает только измеримые технические ограничения: координаты/единицы, экспорт/импорт, ориентации, коллизии, форматы, совместимость со скелетами, имена/версии данных.
- S05A: одна модель → проверить/перенести исходную анимацию (если доступна технически) → одна новая анимация → проверка импорта, переходов и FPS → утверждение продюсером.
- Если исходная Alpha не предоставляет пригодные риги/клипы, это фиксируется как ограничение, а не имитируется успешный перенос; тогда движения воспроизводятся самостоятельно по наблюдаемому поведению.
- S05B: модели производятся партиями, **каждая** проходит индивидуальный просмотр; арт-стандарт складывается по утверждённым в Unity образцам.
- Рендер/эффекты: качество Low/Medium/High, но конкретные пресеты, тени, трава, освещение и физика листвы выбираются по прототипам. Выбор URP не означает утверждение конкретной картинки.

## H. Проверки, производительность, управление изменениями

- EditMode: Core/Features, генерация, ID, события, сохранения и миграции.
- PlayMode: сцена, ввод, физика, движение, бой, NPC, связка сохранение/загрузка.
- Acceptance/golden cases: сравнение с наблюдаемым поведением Alpha по зафиксированным сценариям, с отметкой достоверности источника.
- Performance: время кадра CPU/GPU, память, spikes при стриминге, объём сейва/время загрузки, отложенные NPC. Целевой ПК и численные бюджеты нужно согласовать после первых измерений; нельзя заявлять 60 FPS без теста.
- Для задачи требуются ветка/коммит, сведения о тестах, воспроизводимая сборка или демонстрация, регрессии и блокеры. Статус агента `READY_FOR_REVIEW` — не `ACCEPTED`.
- Изменение модульных контрактов/сохранений — архитектурное решение; изменение геймплея/визуала — решение продюсера. Утверждённое не редактировать задним числом без журнала изменений.

## I. Gate архитектуры до кодирования

Должны быть отдельным решением подтверждены: A01–A09, границы модулей и принцип авторитетного состояния. Затем S00 — фактическое исследование Alpha и S01 — технический эксперимент с рендером, движением, чанком и сейвом; детальные размеры/форматы фиксируются только по измерениям.

**Не решено здесь:** конечное название игры, финальная художественная стилизация, количественный баланс, детальные контентные каталоги, политика DRM/офлайн-доступа, конкретный netcode, полноценная система модов.

## Актуальное исключение D40 (2026-11-02)

По прямому решению продюсера **S00-R01 (статический анализ Alpha) и S01-PILOT (минимальный Unity vertical slice) разрешены параллельно**, несмотря на незавершённое общее исследование/архитектурный черновик. Это **не** открывает массовую реализацию всех систем или полное утверждение архитектуры. Unity Hub/Editor не установлены; их установка требует отдельного согласия продюсера на ПК, Blender пока не требуется. Источник исполнения: [D40](../decisions/D40-static-first-unity-pilot.md), [ACTIVE_STAGE](../ACTIVE_STAGE.md), [S01-PILOT](../stages/S01_UNITY_PILOT.md).
