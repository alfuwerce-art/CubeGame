# Cube World Reimagined — архитектура Unity (предложение)

**Статус:** ПРОЕКТ ДЛЯ ОТДЕЛЬНОГО УТВЕРЖДЕНИЯ.  
**Основание:** `DECISIONS_001-036.md`.  
**Цель:** локальная воспроизводимая Alpha 2013, допускающая позднее расширение систем, мультиплеер и модификации без переписывания всего проекта.

## Базовый подход

**Модульный монолит**, разделённый по ответственности. Unity управляет изображением, физическим представлением, сценами, вводом и анимацией. Основные правила игры работают независимо от конкретного MonoBehaviour и по возможности тестируются без сцены.

Рекомендуемые слои:

1. **Domain/Core** — правила боя, прогрессии, предметов, NPC, событий, состояния мира, стабильные ID. Без UnityEngine там, где это практически возможно.
2. **Application/Simulation** — такты симуляции, выполнение команд, обновление регионов, проверка правил и отправка доменных событий.
3. **Unity Presentation** — рендер, камеры, input, анимации, эффекты, UI, сценические представления сущностей.
4. **Infrastructure/Adapters** — сохранения, загрузка ассетов, локальная LLM/STT, в будущем сетевой транспорт и моды.

Правило зависимостей: игровая логика не должна читать состояние через прямые ссылки на HUD, MeshRenderer, Canvas или Animator. Presentation читает состояния и отправляет команды. Изменения значимых игровых фактов централизованы в Domain/Application.

## Логические модули

| Модуль | Владеет | Публичный контракт |
|---|---|---|
| WorldGeneration | Seed, биомы, размещение объектов, идентификаторы процедурных объектов | `GenerateRegion(seed, regionKey, generationVersion)` |
| WorldState | Постоянные изменения, регионы, лагеря, разрушения, владение | `ApplyWorldCommand`, `GetRegionState` |
| SimulationClock | Время мира и уровни интенсивности симуляции | `Tick`, `Pause`, `Resume`, `AdvanceRegion` |
| Character | Параметры, классы, навыки, перемещение | `CharacterCommand`, `CharacterState` |
| Combat | Удары, урон, эффекты, навыки, столкновения | `AttackCommand`, `CombatEvent` |
| Inventory | Предметы, экипировка, добыча, крафт | `InventoryCommand`, `ItemInstance` |
| NPC / AI | Состояния, потребности, расписания, цели, отношения | `NPCAction`, `NPCState` |
| Quests | Цели, условия, цепочки, последствия | `QuestDefinition`, `QuestState`, `QuestEvent` |
| Factions | Репутация, территории, события конфликтов | `FactionState`, `TerritoryEvent` |
| Persistence | Сохранение мира и героя, версии и миграции | `SaveGame`, `LoadGame` |
| Presentation | Модели, риги, анимации, UI, звук, освещение | View/Controller/Presenter API |
| NPC Language Adapter | Локальный текст/речь и контекст диалога | `DialogueRequest`, `DialogueResponse` |
| Future Network Adapter | Авторитетная симуляция, клиентские команды и снимки | **Не реализуем сейчас**, но границы проектируем |

Приведённые названия контрактов — рабочие, не конечные API.

## Генерация и сохранения

- Исходный неизменённый мир задаётся seed + версией генератора + координатами региона.
- Постоянные ID процедурных объектов должны воспроизводиться при повторной загрузке.
- Сохранять **изменения относительно исходного состояния**, а также долговременные состояния NPC/фракций/квестов; для больших изменённых областей использовать снимки состояния.
- Порядок восстановления: загрузить данные сохранения → определить версию генератора → восстановить базовый регион → применить изменения → восстановить симуляционные состояния → создать представление в Unity.
- При изменении алгоритма генерации учитывать совместимость старых миров; нельзя тихо поменять их географию или ID объектов.
- Разделять сохранение конкретного прохождения и региона. Несколько новых игр — независимые прохождения; перенос персонажа между ними не предполагается.
- Проверять целостность и атомарность записи (временный файл, контроль и подтверждение завершения), резервные копии и миграции схем.

## NPC и масштабируемая симуляция

- Вблизи игрока: полноценное поведение и соответствующее физическое представление.
- В удалённых регионах: расчёт маршрутов, расписаний, отношений, событий и переходов состояний с меньшей частотой и без детальной физики.
- После выхода из локального прохождения: пауза мирового времени. Будущий сервер: пауза после выхода последнего игрока.
- NPC имеет постоянную личность/историю, фактологическую память и текущее состояние. Результат диалога LLM не считается фактом до проверки игровым кодом.
- Контроль очередей и лимитов запросов локальной модели; игровой цикл не блокируется ожиданием генерации текста.

## Подготовка к будущему мультиплееру

**Не писать сервер сейчас.** Однако игровая симуляция принимает команды, владеет состоянием, проверяет полномочия и генерирует события, вместо изменения мира прямо из UI. В будущем авторитетную симуляцию можно перенести в серверный процесс, а клиента сделать визуальным представлением.

Заранее проверять возможность сериализации команд/состояний, детерминированную часть генерации, устойчивые ID и отсутствие важных ссылок на локальную сцену. Нет обещания, что интеграция сети будет полностью без изменений.

## 3D-модели и анимации — единый pipeline

**Пилот перед серийным производством:**

1. Выбрать **один** персонаж/монстр и определить его текущие движения в Alpha.
2. Подготовить новую или переработанную модель в Blender с кубическим силуэтом.
3. Проверить старую анимацию на новом риге (или корректно перенести движения через ретаргетинг).
4. Создать **одну новую анимацию** для той же модели.
5. Импортировать в Unity и проверить масштаб, ориентацию, коллизии, материалы, переходы состояний и показатели FPS.
6. Получить отдельное утверждение продюсера на модель. Зафиксировать правила геометрии, рига и анимаций.

После пилота модели производятся партиями, но **каждая модель проходит индивидуальный просмотр продюсера**. Не стандартизировать окончательно художественный стиль до просмотра игровых прототипов.

## Качество, регрессии и контроль изменений

- Единые assembly definitions и namespace для модулей, минимизация циклических зависимостей.
- Тесты чистой логики (EditMode), интеграционные и игровые проверки (PlayMode), тесты сохранений и повторной загрузки, визуальные ручные проверки.
- Против изменения геймплея без согласования: golden cases по Alpha с зафиксированными входами и ожидаемым результатом.
- Профилирование CPU/GPU, памяти, времени загрузки, скорости генерации регионов на заранее согласованных тестовых устройствах.
- Каждая задача — отдельная ветка/коммиты, отчёт, сборка или демонстрация для применимых изменений, тесты, известные проблемы, ссылка на принятые решения.
- Архитектурные изменения требуют отдельного рассмотрения архитектором и утверждения согласно D24; функциональные изменения геймдизайна — продюсером.

## Что требуется утвердить до начала производства ядра

1. Конкретную поддерживаемую версию Unity и рендер-пайплайн (URP/HDRP) по техническому прототипу.
2. Размер региона/чанка, порядок стриминга и требуемую дальность мира.
3. Модель обновления симуляции, времени и событий; источник случайности.
4. Типы идентификаторов и версионирование процедурных сущностей.
5. Формат сохранений, стратегии снимков и миграции.
6. Минимальный набор API между Domain и Presentation.
7. Целевые устройства и измеряемые бюджеты производительности.

Этот документ **не утверждает** окончательный визуальный вид игры и не подразумевает аренды сервера.
