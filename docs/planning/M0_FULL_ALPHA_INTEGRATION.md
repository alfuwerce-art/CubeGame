# M0 — полная интеграция Cube World Alpha 2013 в единую Unity-игру

**Статус:** `ROADMAP_APPROVED / IMPLEMENTATION_NOT_STARTED` — план и ограниченный параллельный режим утверждены продюсером 2026-11-07 (D66). M0-00 допускает подготовительное исследование/аудит без вмешательства в рабочую игровую сборку. Реализация M0-01…M0-09 — только после приёмки применимых результатов S05B-2 и утверждения исполнимого ТЗ M0-00.
**База:** `stage/d65-full-catalog` (D65: `READY_FOR_REVIEW`, не `ACCEPTED`). Основной каталог `D:\Projects\CubeGame`; исходная Alpha `D:\Games\Cube world` только для чтения.
**Нумерация:** новые `M0-00`…`M0-09` — интеграционная последовательность, не переименование исторических S00–S05. Всего 10 этапов / 40 подэтапов.
**Цель:** один локальный исполняемый Unity-проект, воспроизводящий согласованный функционал Alpha (кроме отдельно отложенного мультиплеера), с рабочими межсистемными связями, сохранениями и полным игровым циклом. Не переносить движок Plasma/исполняемый файл; воспроизводить поведение собственным Unity/C# кодом. Исходные и производные ресурсы Alpha — локальные исследовательские материалы, не публичные релизные ассеты.

## 0. Правила выполнения

1. **Исследование → контракт → реализация → интеграционный тест → ревью → приёмка.** Для каждого подэтапа: входной SHA, ответственный, входные зависимости, выводы исследования, изменённые контракты, тесты (новые и регрессионные), видеодоказательство/сборка по необходимости, результат и известные ограничения. `PASS` агента не равен `ACCEPTED`.
2. **Использовать существующее:** S02 Core, S03 Combat, S04 Equipment, S05 модели/анимации сначала инвентаризируются. Дубли и переписывание без причины запрещены. Реестр S05 различает `ANIMATION_AVAILABLE`, `BEHAVIOR_VERIFIED`, `GAMEPLAY_ENABLED`, `NOT_APPLICABLE`, `UNKNOWN`. Библиотеку клипов не удалять из-за выключенного игрового действия.
3. **Одна рабочая игра:** основной Unity-проект, одна цепочка запуска и согласованные интерфейсы. Пилоты могут оставаться доказательствами, но не подменяют интегрированную игру. Gameplay-state принадлежит Core/Features/Application, а не `MonoBehaviour`/HUD/аниматору (ADR-0001).
4. **Данные/генерация:** сохранения имеют версию схемы и при изменении формат/генератор — тест совместимости или явный механизм миграции. `WorldId`, seed, генератор, стабильные ID сущностей, события NPC и изменения регионов не теряются при выгрузке. Все локальные изменения — реальные persistent deltas, неизменённые чанки — повторная генерация по seed.
5. **Ключевой инвариант:** подэтап завершён только если прежние проверенные пользовательские сценарии продолжают работать. При регрессии — исправить/откатить внутри ветки, не переносить поломку «на потом».
6. **Объём:** M0 реализует поведение Alpha с документированными осознанными отклонениями (например, декоративные растения/яйца без хождения и атак). Не внедрять преждевременно M1-графику и M2-LLM/новую RPG. Изменение поведения фиксируется в матрице отклонений; растительные монстры отдельно от декора.
7. **Порядок и зависимости:** крупные этапы и кодовые контракты последовательно; безопасные исследования, документация и независимый анализ могут идти параллельно по D66 и `docs/agents/MULTI_AGENT_WORKFLOW.md`. **Два агента не пишут одновременно в `D:\Projects\CubeGame`, не переключают в нём ветки и не запускают одновременно Unity.** Не создавать второй клон/worktree без нового решения.
8. **Граница источников:** `main`, принятые S04, чужие ветки не менять; без force-push/merge; не публиковать исходные/производные ассеты Alpha. Решения о запуске/приёмке только продюсер.

## 2. Параллельная работа Claude / DeepSeek: строго разрешённые пары

Параллельность допускается **только для независимых результатов без записи двух агентов в одну локальную рабочую копию**. Работа Claude с удалённой GitHub-веткой/ревью или read-only материалами, DeepSeek — с локальным Unity-проектом. Если Claude для анализа нужно **изменять локальный код, Unity-сцену, `.scratch` или выполнять тесты**, режим автоматически **SERIAL / HANDOFF**. Отсутствие у Claude удалённой записи GitHub — тоже SERIAL, а не основание нарушать защиту.

| Пока DeepSeek работает над… | Claude может параллельно… | Граница |
|---|---|---|
| M0-00B: исследует механику Alpha | M0-00A: проводить read-only аудит кода/контрактов по зафиксированному SHA | Два независимых отчёта, отдельные remote docs |
| M0-01: фундамент/сохранения | Подготовить доказательства и ТЗ генерации M0-02 (только исследование) | Не менять API M0-01 |
| M0-02: мир/стриминг | Исследовать создание персонажа/движение M0-03 | Без кода/Unity |
| M0-03: персонаж | Аудировать предметные таблицы и контракты M0-04 | Без редактирования S04 |
| M0-04: предметы | Проверять Alpha боевые формулы и писать golden-сценарии M0-05 | Не менять боевые модули |
| M0-05: бой | Готовить реестр NPC/типов и evidence/спавн-требования M0-06 | Не назначать анимации без доказательств |
| M0-06: NPC/AI | Собирать Alpha-сценарии поселений/данжей/торговли/квестов M0-07 | Не трогать live NPC/генератор |
| M0-07: контент | Готовить UX-сценарии M0-08 и тестовую матрицу M0-09 | Только docs |
| M0-08: UI | Собирать независимые чек-листы golden-сценариев M0-09 | Ревью работающей сборки — только на зафиксированном SHA, если не мешает Unity |
| M0-09C: профилирование | M0-09B: сравнение с Alpha и независимый review опубликованного SHA | Unity-тесты, профилирование и правки выполняет один агент |

**Нельзя считать параллельным кодированием:** совместные правки `Assets/`, `Packages/`, `ProjectSettings/`, `.scratch/`, сейвов или общих контрактов из одной рабочей копии, одновременная работа Unity Editor/BatchMode, параллельные git checkout/commit/merge/rebase/push в той же локальной папке. Если две задачи требуют изменения этих частей — одна останавливается на handoff. Впоследствии можно отдельно утвердить изолированные рабочие окружения, но сейчас второй клон/worktree не создавать.

### Handoff / публикация

- Claude: результаты независимых исследований/ревью — в **собственной удалённой ветке**, через поддерживаемый GitHub API или без записи локальной папки. Только docs/evidence, без изменения активного кода. Для анализа локальных ассетов допустим read-only доступ.
- DeepSeek: основной локальный Unity-код и тесты в `D:\Projects\CubeGame` и своей stage-ветке.
- Контракты, от которых зависит код DeepSeek, должны быть **заморожены и утверждены до кодирования**. Изменение предложенного API Claude в середине чужой реализации — отдельный handoff, а не «тихий» коммит.
- Документы двух веток согласуются по SHA после завершения обеих задач; решать конфликты явно, `main` не трогать.
- Критические ревью и исправления, требующие правки кода, — **последовательно**. Никаких одновременных локальных записей даже при разных файлах.

## 3. Система шлюзов против регрессий

| Шлюз | Что проверяется |
|---|---|
| G0 перед задачей | HEAD и рабочее дерево; стабильный baseline; заявленные входные контракты; охват тестов |
| G1 после каждой реализации | Новые unit/EditMode, PlayMode с реальным вводом/физикой/сценой; прежние тесты затронутых модулей |
| G2 на границе этапа | Запуск игры и актуальный сквозной сценарий, сохранение/загрузка, стабильные ID и зависимости событий |
| G3 после изменения генерации/сейвов | Seed reproduction, чанки/unload, delta persistence, миграции/старые сейвы, восстановление после сбоя |
| G4 перед закрытием | Claude review опубликованного SHA, документированный coverage и ограничения, отчёт DeepSeek, личное решение продюсера |

Сразу же после появления нового слоя он подключается в единую игровую сцену; не считать «работает в изолированном пилоте» достаточным для M0. Измеримые целевые FPS/память назначать после профилирования, не придумывать.
