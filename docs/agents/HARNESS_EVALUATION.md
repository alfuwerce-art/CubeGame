# Harness evaluation — проверка изменений обвязки

**Статус:** процесс испытания, **не** право агента менять правила самостоятельно.

## Когда применять

Только для повторяемой типовой задачи (например, изменение Unity-фичи, документационный аудит, git-preflight, сравнение тестов), если несколько попыток ошиблись одинаково. Не использовать тройной прогон для разовой художественной задачи или создания первой игровой модели; это вернёт нас к бесплодной фабрике.

## Контрольный эксперимент

**Baseline:** один заранее описанный сценарий, фиксированные исходные данные, одна версия модели, одинаковые ограничения и бюджеты. Сохранить задачи, SHA, логи, diff, итог тестов, время, затраты/итерации и неизвестные факты.

**Propose (две независимые гипотезы):**
- General: как улучшить способ выполнения (маршрут инструментов, проверка ошибок, бюджет контекста, передача между сессиями).
- Domain: какие предметные знания о CubeGame реально не хватило (GDD/ADR, test oracle, сохранения, Unity/сцены).

**Probe:** по одному изменению на отдельной изолированной копии или worktree, та же модель и сценарий. Вариант A не видит решения B и наоборот. Никогда не тестировать на canonical, не менять внешний DSH профиль и не генерировать самовольно игровые механики.

**Compose:** объединить **только** изменения с доказанным выигрышем без нарушения guardrails. Прогоны A/B могут обнаружить изменение поведения, но **не** доказывают корректность игры без независимого тестового оракула и ревью владельца.

## Метрики

- корректность: заранее определённые acceptance tests, diff/target files, реальные тесты, интеграция и пользовательская игровая проверка;
- безопасность: 0 запрещённых операций, 0 самовольных изменений scope, 0 утечек секретов;
- стабильность: повторяемость, падения, откаты, сохранения;
- эффективность: затраченные вызовы/токены (если провайдер показывает), время, число исправлений;
- качество отчёта: SHA, реальные данные, явные NOT_RUN/FAIL/BLOCKED без ложного PASS.

Решение: `ADOPT` / `REJECT` / `INCONCLUSIVE` с датой, задачей, моделью/DSH версией, исходным HEAD, ссылками на журнал и измерениями. Предположения и результаты из видео не вписывать как метрики CubeGame.

## Библиотека опыта

Только проверенный опыт размещать в `docs/agents/experience/` по доменам: Unity, docs, review. В одном блоке: проблема → гипотеза → baseline/probe → наблюдение → решение → откат и где применять. **Не** подключать опыт целиком в постоянный системный контекст; загружать только подходящую запись.

Обвязку разрешено обновить в отдельном PR после ревью. Изменения прав доступа / hook-bridge / автоисполнения требуют отдельной локальной проверки владельца.
