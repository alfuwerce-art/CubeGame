# CubeGame — план управления контекстом, чатами и рабочими сессиями ИИ

**Дата:** 2026-11-06. **Статус:** READY_FOR_REVIEW как регламент сессий; до прямого утверждения действует текущий MULTI_AGENT_WORKFLOW.  
**Опора:** [MULTI_AGENT_WORKFLOW](MULTI_AGENT_WORKFLOW.md), [AGENTS](../../AGENTS.md), [ACTIVE_STAGE](../ACTIVE_STAGE.md), [ROADMAP](../planning/ROADMAP_DRAFT.md).  
**Цель:** работа Claude / DeepSeek / Codex / ChatGPT в одном проекте без повторения уже принятых вопросов, раздувания промптов, расхождения веток и потери доказательств.

## 1. Не путать четыре единицы

| Единица | Пример | За что отвечает |
|---|---|---|
| **Milestone (M)** | M0, M1, M2 | Большая продуктовая цель и приёмочные результаты |
| **Stage (S)** | S05A-2 | Разрешённый объём работ с набором задач и одним закрытием этапа |
| **Task (TASK_ID)** | S05A2-ANIM-WALK-VERIFY | Один проверяемый результат в конкретной Git-ветке |
| **Session / chat** | Разговор Claude с задачей, рабочая сессия DeepSeek | Временный контекст исполнителя, **не** источник истины |

**Правило:** одна самостоятельная функция/механика — одна сессия. Новый этап, подэтап или другая функция/механика — новый чат. Не открывать отдельную сессию для каждого вспомогательного C#-метода или файла внутри той же механики.

## 2. Roadmap против Session Plan

**Roadmap:** «какие этапы и что должно быть готово». Уже существует, не дублировать.  
**Task plan:** «какую проверяемую задачу авторизовал продюсер для текущего этапа». Лежит в `docs/stages/` и отчёте.  
**Session plan:** «какой именно набор файлов и SHA получает новый агент, с чего начинает и что обязан вернуть». Этот документ определяет правила и шаблон, а не второй Roadmap.

Ни один новый чат, ветка, PR или DRAFT не открывает следующую стадию. Сначала `ACTIVE_STAGE` и прямое разрешение продюсера.

## 3. Типовая сессия разработки

**Вход:**
1. Поручение с **TASK_ID**, ролью исполнителя, разрешённым статусом и Git SHA/веткой.
2. Минимальное чтение: `AGENTS.md` → `PROJECT_MEMORY.md` → `docs/ACTIVE_STAGE.md`; при «продолжаем» — `CURRENT_CHECKPOINT.md`. Далее агент выбирает релевантные документы по карте в AGENTS самостоятельно; полный GDD, все Dxx и история не загружаются без необходимости.
3. **Только относящиеся к задаче** Dxx, ADR, ТЗ, предыдущий отчёт и конкретные файлы кода.
4. Локальные проверки: `git status --short --branch`, HEAD, проверка чужих изменений, версия Unity, активный Editor.
5. Прямо назвать **границы**: «делаем X; не трогаем Y; что считать PASS».

**Работа:**
1. Исполнитель делает ограниченное изменение и регулярные контрольные проверки, не лезет в чужую задачу.
2. Сохраняет доказательства тестов и заметки о непроверенных предположениях.
3. При появлении нового решения — фиксирует предложение `DRAFT`, но не меняет утверждённый GDD/архитектуру самостоятельно.
4. При BLOCKED сообщает причину и точную точку продолжения, не выдаёт неполное за успех.

**Выход:**
1. Все изменения связаны с веткой и SHA, исключены оригиналы Alpha/секреты.
2. Отчёт: выполнено / невыполнено / реальные проверки / что не доказано / как воспроизвести / файлы и SHA.
3. Статус `READY_FOR_REVIEW` или `BLOCKED/PARTIAL`, а **не** `ACCEPTED`.
4. `HANDOFF`: 10–20 строк с необходимыми ссылками, чтобы следующая сессия не читала предыдущие 200 сообщений.

## 4. Один проект, несколько агентов — **строго последовательно**

| Шаг | Кто | Что делает |
|---|---|---|
| **1. Design** | Продюсер + ChatGPT | Утверждают игровой результат, если он нужен |
| **2. Contract** | Claude / ChatGPT по поручению | Готовят чёткий технический контракт без самовольного изменения дизайна |
| **3. Implement** | DeepSeek **или** Codex **или** Claude, назначенный на задачу | Работает в `D:\Projects\CubeGame`, своей Git-ветке |
| **4. Evidence** | Тот же исполнитель | EditMode/PlayMode, негативные тесты, артефакт просмотра, отчёт |
| **5. Review** | Другой ИИ/ревьюер | Изучает diff и доказательства, проверяет риски независимо |
| **6. Approval** | Продюсер | Проверяет геймплей/визуал и принимает/возвращает на правку |
| **7. Context sync** | Назначенный агент | Обновляет после утверждения `PROJECT_MEMORY`, `ACTIVE_STAGE`, решение/отчёт, не делает самовольный merge |

**Одновременная работа в одной директории запрещена.** Без дополнительной постоянной копии Unity, без worktree для обычного ревью, без изменения оригинальной Alpha. Разрешён push собственной рабочей ветки при проверке содержимого; merge в main только после согласия.

## 4.1. Передача между Claude и Codex и периодичность проверки

Claude и Codex равноправно выполняют сложные разработки. Если лимит или недоступность остановили одного, второй принимает **ту же задачу**, сверяя ветку, SHA, текущий статус, открытые проблемы и HANDOFF. Перезапуск исследования с нуля не требуется, пока доказательства доступны. При отсутствии HANDOFF восстановить состояние из Git/отчётов и не перезаписывать чужое несохранённое.

DeepSeek получает задачи меньшей сложности: исправления, локальные изменения кода, интеграция готовых решений. Эксперимент над сложной системой возможен только при явном ограниченном ТЗ.

Полный цикл тестирования и ревью выполняется на закрытии этапа/пакета; промежуточные действия не требуют повторного полного прогона. Рискованные изменения допускают короткие целевые проверки. На закрытии этапа проверить, не остались ли устаревшие компоненты; удаление проводить только после анализа ссылок и с откатом.

## 4.2. Обязательные границы сессий и checkpoint

- Переход к **новому этапу, подэтапу, самостоятельной механике или функции** всегда означает новый чат. Внутри выбранной функции допустимы её вспомогательные C#-методы, корректировки и повторные исправления в той же сессии.
- При **каждой остановке, передаче, плановом перерыве или достижении лимита** текущий исполнитель обновляет [CURRENT_CHECKPOINT.md](CURRENT_CHECKPOINT.md). Для длинных задач — после законченного значимого блока, на случай внезапного обрыва.
- Текущий исполнитель также обновляет `PROJECT_MEMORY.md` (это делают **все агенты**). **Только GPT** удаляет из неё устаревшие сведения и ведёт [STAGE_HISTORY.md](../STAGE_HISTORY.md). После принятия этапа GPT переносит туда краткое резюме, сохраняет открытые зависимости и чистит оперативную память.
- На команду **«продолжаем»** читать память, ACTIVE_STAGE, AGENTS, checkpoint, сверять Git и продолжать с `NEXT_STEP`. Если checkpoint не удалось сохранить до внезапного лимита — восстановить состояние по Git/отчётам и отметить неизвестное. Не начинать новый неавторизованный этап.

## 5. Когда создавать новый чат

**Новый чат обязателен:**
- Начало нового утверждённого этапа (S05A-2 → следующий после ACCEPTED);
- Новая самостоятельная функция/механика или TASK;
- Новый подэтап, даже внутри крупного этапа;
- Передача задачи от DeepSeek к Claude или Codex (другой исполнитель и задача ревью);
- Исследование, ушедшее в собственное ответвление и требующее отдельного отчёта;
- Текущий диалог слишком длинный и агент начал забывать границы задачи (сначала HANDOFF).

**Тот же чат допустим:**
- Правка небольшого дефекта после теста одной и той же задачи;
- Повторная проверка/исправление после отчёта REVIEW_FIX, если контекст ещё достаточно ясен;
- Несколько функций и файлов одного маленького механизма;
- Последовательная детализация одного игрового решения в ChatGPT.

**Новый чат НЕ равен новому Git-коммиту и не равен новому этапу.** Не сохранять каждый вопрос/ответ отдельным markdown-файлом.

## 6. Минимальный пакет контекста нового агента

Передавать **ссылки и SHA**, а не огромный paste всей истории:

```text
PROJECT: alfuwerce-art/CubeGame
WORKING_DIR: D:\Projects\CubeGame
TASK_ID: S05A2-EXAMPLE-01
STAGE: S05A-2 IN_PROGRESS/REVIEW OPEN (проверить CURRENT)
AUTHORIZED_BY: Dxx + конкретное ТЗ
BRANCH: stage/... | codex/... | review/...
BASE_SHA: <actual SHA>
MUST_READ: PROJECT_MEMORY.md, docs/ACTIVE_STAGE.md, AGENTS.md
SPEC: docs/stages/... + Dxx + ADR...
PREVIOUS_REPORT: docs/reports/...
GOAL: <один проверяемый результат>
NOT_IN_SCOPE: <что запрещено менять>
EXPECTED_TESTS: <конкретные команды>
EXPECTED_ARTIFACT: <сцена / тест / файл / отчёт>
STATUS: AUTHORIZED / IN_PROGRESS
HANDOFF_FROM: <последний SHA/проблема>
```

**Указание в шаблоне «CURRENT»** требует перечитать GitHub, а не доверять сохранённой датированной строке в чужом промпте. Настоящая база/ветка/тесты берутся из задач, не из примера.

## 7. Шаблон результата / HANDOFF

```text
TASK_ID:
WORKING BRANCH / COMMIT SHA:
STATUS: READY_FOR_REVIEW | PARTIAL | BLOCKED
GOAL: what was attempted
DONE: facts and artifact paths
TESTS: actual commands/results, what NOT tested
CHANGED: files and purpose
NO CHANGE: explicit untouched critical subsystems
RISKS / BLOCKERS: concrete causes, not general guesses
PRODUCER REVIEW: what to launch/click/look at
NEXT TASK: only when authorized; not auto-started
OPEN DECISION: ask only if genuinely necessary
```

**Не писать «успех», если реально не запускалась Unity/не проверена модель или не получен PASS.** Не полагаться на резюме другого ИИ вместо отчёта/ветки.

## 8. Где хранится контекст, чтобы не засорять проект

- **PROJECT_MEMORY.md:** сжатые принятые решения, текущие этапы, важные SHA, ссылки на доказательства; **не** полные чаты, длинные логи и дубли спецификаций.
- **ACTIVE_STAGE.md:** только состояние и разрешённый объём ближайшей работы; длинная история — ссылки в отчёты и решения.
- **AGENTS.md:** единые общие/ролевые правила; **не** актуальные задачи по датам и не игровой дизайн целиком.
- **GDD и Dxx:** игровой канон; DRAFT не становится ACCEPTED от включения в текст.
- **Отчёты и тестовые данные:** отдельные артефакты `docs/reports/` и `docs/stages/`; машинные логи отдельно в игнорируемых местах.
- **Playbook:** повторяемая процедура для определённого типа работы; не создавать новый playbook на каждую функцию.

**Когда обновлять память:** все агенты записывают значимые изменения текущего этапа, передачи и блокеры. Только GPT чистит устаревшее и ведёт STAGE_HISTORY после приёмки. Допускаются краткие рабочие отчёты для READY_FOR_REVIEW, но отдельной отметкой. Не изменять утверждённые решения по косвенному предположению.

## 8.1. Владение рабочей директорией и безопасная передача

Для `D:\\Projects\\CubeGame` действует принцип **single writer**:

1. В каждый момент времени есть только один агент-владелец записи.
2. Перед передачей владелец фиксирует branch/HEAD, `git status --short --branch`, незакоммиченные файлы, выполненные тесты и HANDOFF.
3. Новый агент сначала сверяет эти данные с реальным Git. При расхождении работу не продолжает молча — фиксирует конфликт.
4. Ревьюер по умолчанию читает ветку и артефакты без записи. Для исправления нужен явный переход владения и статус `REVIEW_FIX`.
5. Не использовать постоянные копии проекта/worktree как способ «развести» агентов, пока продюсер отдельно не изменит это правило.
6. После передачи предыдущий агент не продолжает писать в ту же директорию до нового назначения.

Такой lock — организационный, без отдельного lock-файла в репозитории: источник состояния — Git + HANDOFF + назначение в TASK.

## 8.2. Удаление неактуальной информации из памяти

`PROJECT_MEMORY.md` — оперативная передача **текущего этапа** между чатами/агентами: исполнитель, ветка, SHA, прогресс, оставшаяся работа, блокеры, ссылки. Пока этап открыт, нужные сведения не удалять ради размера файла. После подтверждённого `ACCEPTED` **GPT** вносит краткий итог и ссылки в [`docs/STAGE_HISTORY.md`](../STAGE_HISTORY.md), переносит открытые зависимости в следующий контекст, затем чистит `PROJECT_MEMORY.md`; другие агенты только дополняют память актуальным прогрессом. Dxx, отчёты и Git историю сохранять.

## 9. Контроль потери контекста

Перед переключением агента проверить: 
- текущий STATUS и реалистичный базовый SHA;
- правдивость PASS/FAIL и файлов доказательств;
- нет ли решений, заменённых поздним Dxx (например, D65 изменён D66);
- нет ли второй копии Unity или незавершённой чужой работы;
- что следующая задача разрешена `ACTIVE_STAGE`;
- что пользователь не обязан повторять уже отвеченный вопрос;
- что в передаче есть ссылка на визуальный/игровой образец, если он нужен.

## 10. Пример разбиения одной большой механики на сессии (НЕ РАЗРЕШЕНИЕ СЕЙЧАС)

Представим будущую систему физического оружейного контакта D65:

- **Task COMBAT-01:** описать и утвердить контракт «промах/касание/плотный контакт» (дизайн чат);
- **Task COMBAT-02:** один тестовый меч против одного манекена, лог контакта (Unity агент);
- **Task COMBAT-03:** негативные тесты и исправления (может продолжаться в той же сессии);
- **Task COMBAT-04:** проверка блоков/щита с одним экземпляром сцены;
- **Task COMBAT-05:** ревью, видео, оценка продюсера, решение о дальнейшем масштабе.

Каждый этап можно разделить на меньшее число сессий, если один агент удерживает цель и выдаёт проверяемый результат. **Не требовать 5 чатов, если достаточно 2.**

## 11. Критерий приёмки этого процесса

На тестовой разрешённой задаче другой агент должен суметь из HANDOFF и Git SHA:
1. воспроизвести тесты;
2. понять ограничения и статус;
3. увидеть, что было изменено, а что не трогали;
4. продолжить работу без обращения к прошлому чату;
5. не открыть запрещённую стадию.

**До утверждения продюсером действует прежний MULTI_AGENT_WORKFLOW.** Этот документ предлагает более детальные правила и не меняет текущую авторизацию.
