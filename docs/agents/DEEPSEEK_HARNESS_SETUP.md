# DeepSeek Harness — актуальные правила для CubeGame

**Статус:** инструкция по безопасной работе с локальным ИИ-агентом. За действующим разрешённым объёмом обращаться к [ACTIVE_STAGE](../ACTIVE_STAGE.md) и [AGENTS](../../AGENTS.md).

## Рабочая среда

- Windows 11, основной репозиторий `D:\Projects\CubeGame`, удалённый Git `alfuwerce-art/CubeGame`.
- Пресет `cubegame-dev` используется только для задач этой игры.
- Доступ по умолчанию — ограниченная запись внутри workspace, запрос разрешения на рискованные операции. Не включать постоянный неограниченный режим.
- Git, PowerShell, Unity CLI и локальные файлы — только для текущего задания. Версию Unity сверять с проектом; автоматически не обновлять Unity, пакеты и системные инструменты.
- Не загружать секреты, приватные референсы или закрытые ресурсы в GitHub; не подключать платные сервисы без разрешения.
- Не трогать чужие проекты, пресеты и каталоги.

## Перед каждой задачей

1. Прочитать `PROJECT_MEMORY.md`, `docs/ACTIVE_STAGE.md`, `AGENTS.md`, GDD, Roadmap и утверждённые решения текущей задачи.
2. Проверить точную рабочую ветку, `git status`, remote SHA и незафиксированные изменения.
3. Сопоставить запрос владельца с разрешённым объёмом; не расширять задачу своими инициативами.
4. Запланировать проверки результата и запрещённые операции до исполнения. При конфликте требований остановить только конфликтующую операцию и сообщить о блокере.
5. Выполнить работу в своей ветке, получить воспроизводимые доказательства, проверить diff/секреты, передать SHA и статус `READY_FOR_OWNER_REVIEW`.

## Закрытая технология

[D95](../decisions/D95-single-repository-close-model-pipeline.md) отменяет прежний автоматизированный конвейер создания моделей. Никаких пресетов второй производственной лаборатории, ComfyUI/Tripo-графов, авто-рига, пакетов манекенов или автоматических стадий массовой генерации как части действующего проекта. Требования к качеству игровых моделей остаются, но конкретный способ производства заново не утверждён.

## Проверки

Отчёты содержат команды, реальные результаты, ограничения и ссылки на артефакты. Для Unity после отдельного разрешения — проверки импорта, компиляции, тестов, сборки и ручного игрового сценария. Не выдавать успешный exit code за доказательство тестов; проверять XML и фактический итог.

Этот документ не заявляет, что технические ограничения Harness уже принудительно внедрены. Здесь перечислены правила, а не код проверяющей обвязки.

## Harness²-адаптация для пресета `cubegame-dev` (предложение на ревью)

**Общая методика** — [HARNESS_ARCHITECTURE](HARNESS_ARCHITECTURE.md), [HARNESS_EVALUATION](HARNESS_EVALUATION.md), [TASK template](HARNESS_TASK_TEMPLATE.md). Это слой **разработки игры и проверок ИИ**, а не отменённый Factory.

### Как подключать локально без опасных автоматических действий

1. На рабочем ПК открыть локальный DSH и определить **реальную установленную версию** и активный пресет `cubegame-dev`; проверить доступные `dsh-skill`, `dsh-skill-filesystem`, `dsh-tool-skill` и `dsh-hooks-claude-code`. Не устанавливать и не включать пакет вслепую. Информацию брать из встроенного `dsh-doc` и источников **именно этой версии**.
2. Выставить workspace только `D:\\Projects\\CubeGame`, режим ограниченной записи и подтверждение опасных операций; сохранить резервную копию пользовательских DSH-профилей. Не переписывать `~/.dsh` автоматически.
3. Синхронизировать одобренную ветку CubeGame в локальный workspace через безопасный git-процесс, не уничтожая незакоммиченные изменения. Project skills: `.dsh/skills/cubegame-unity-change/SKILL.md` и `.dsh/skills/cubegame-doc-audit/SKILL.md`. Убедиться, что они **реально видны** в DSH skill catalog и грузятся по требованию. Если нет — диагностировать mount, не утверждать успех.
4. `node --version`, `node --test tools/harness/hook-pretool.test.mjs`, `node tools/harness/preflight.mjs`; убедиться, что тесты 7/7, а preflight при защищённой ветке выдаёт `BLOCKED`. Проверить результаты на реальном Windows, локальные тесты в другой ОС недостаточны.
5. Только **после явного ревью и локальной проверки** можно подключать `.dsh/hooks.example.json` через официальный hook-bridge DSH по `configPath` **в пресете `cubegame-dev`**. Bridge нередко использует общий процессный конфиг и не подхватывает `.dsh/hooks.json` автоматически. Не менять глобальную конфигурацию и не затрагивать другие пресеты.
6. Выполнить безопасную негативную проверку: `PreToolUse` отклоняет попытку `git push --force`, запись вне workspace и изменение защищённой ветки; обычный `git status` разрешён. Проверить реальные лог-события hook invoked/result. В отсутствие факта срабатывания считать `HOOKS_NOT_ACTIVE`.
7. Подтвердить, что обратная связь от хуков не ломает Unity-команды, tool names, sandbox и обычные сессии; при ошибках отключить hook, оставить preflight + permissions. **Никакого самопереписывания профиля.**

### Запуск новой задачи

`AGENTS → ACTIVE_STAGE → Concept → task-specific skill → task contract → preflight → execute → tests → review`. Пользователь разрешает конкретную задачу, а не постоянную автономную реализацию всего Roadmap. На выходе указать `DSH_VERSION`, `PRESET`, `SKILLS_DISCOVERED`, `PREFLIGHT`, `HOOKS_ACTIVE`, `HOOK_DENY_TEST`, `CHECKS`, `BRANCH`, `SHA`, `BLOCKERS`.

### Ограничения

`hook-pretool.mjs` — эвристика для известных команд и инструментов, не универсальная защита от сложного shell и не замена песочнице. Тесты скрипта **не** означают, что hook подключён. Контроль прав, безопасные рабочие ветки, diff, защита GitHub остаются обязательными. Не применять цикл саморедактирования Harness² без безопасного испытания на копии проекта и решения владельца.
