# CubeGame — единые правила ИИ-агентов (проект объединения)

**Дата:** 2026-11-06. **Статус:** READY_FOR_REVIEW как кандидат единого регламента; до прямого утверждения продюсера действует `AGENTS.md`.  
**Цель:** единые правила для **Claude Code, DeepSeek Harness, Codex и ChatGPT** без отдельных конфликтующих инструкций. До утверждения действует корневой [AGENTS.md](../../AGENTS.md), [ACTIVE_STAGE.md](../ACTIVE_STAGE.md) и утверждённые решения.

## 1. Источник истины и структура

**После утверждения:** корневой `AGENTS.md` становится **единственным каноническим сводом общих и ролевых правил**. Этот файл — проект редакции; его текст переносится/объединяется с действующим `AGENTS.md`, а не становится вторым обязательным регламентом.

- `CLAUDE.md`: **только короткий загрузчик** «прочти `AGENTS.md`, `PROJECT_MEMORY.md`, `docs/ACTIVE_STAGE.md`, назначенное ТЗ»; не хранить дубликатов правил.
- DeepSeek Harness `cubegame-dev` preset: краткая ссылка на `AGENTS.md`, ограничения локального доступа/инструментов; не копировать GDD и старые этапы в системный промпт.
- Codex: читает тот же `AGENTS.md`; поручение и ограничение берёт из конкретного ТЗ, не из старых чатов.
- ChatGPT: те же статусы дизайна и ограничения при выдаче заданий. Рабочие документы являются доказательствами, а не памятью конкретной модели.
- `docs/agents/CLAUDE_ONBOARDING.md` и `DEEPSEEK_HARNESS_SETUP.md` остаются **справочниками установки/ориентации**, без права переопределять AGENTS.
- `docs/agents/MULTI_AGENT_WORKFLOW.md` описывает детали передачи Git-задач и рабочей папки; не дублировать все требования в других файлах.

## 2. Первые действия ЛЮБОГО ИИ перед задачей

1. Прочитать `AGENTS.md` → `PROJECT_MEMORY.md` → `docs/ACTIVE_STAGE.md`; для продолжения — `docs/agents/CURRENT_CHECKPOINT.md`. Из таблицы документов в AGENTS самостоятельно выбирать относящиеся к поручению файлы, не загружая весь репозиторий.
2. Для поручения самостоятельно определить нужные **Dxx**, ADR и актуальное `docs/stages/<stage>.md`; открыть релевантный отчёт предыдущего агента/незакрытые блокеры, не читать всё подряд.
3. Проверить **выполненную и разрешённую границу**: ACCEPTED по геймдизайну **не** означает разрешение программировать. Стадия `S05A-2 IN_PROGRESS / REVIEW OPEN`; `S05B NOT_AUTHORIZED` до отдельного решения.
4. Перед записью локально: `git status --short --branch`, имя ветки, текущий HEAD, наличие чужих несохранённых изменений, доступная версия Unity `6000.3.27f2`.
5. Если нет права выполнить конкретную работу — исследовать/описать предложение, **не** изменять production-код или оригинал Alpha.

**Приоритет:** последнее прямое решение продюсера в подтверждённых Dxx → текущая авторизация ACTIVE_STAGE/ТЗ этапа → утверждённый ADR/реестр решений → проверенный код/тесты как факты → PROJECT_MEMORY → GDD/черновики. Если факты, документы и инструкции противоречат друг другу, **выявить конфликт, не выбирать тайком**. Техническое наблюдение не отменяет дизайнерский выбор, а дизайнерская цель не означает что механизм уже реализован.

## 3. Полномочия

| Роль | Ответственность | Не имеет права без продюсера |
|---|---|---|
| **Продюсер** | Канон геймплея, стиль, требования, бюджет/этапы, финальная приёмка | — |
| **ChatGPT** | Системный дизайн, документация, подготовка ТЗ, сверка решений, помощь ревью | Присвоить игре или этапу ACCEPTED самостоятельно, merge без разрешения |
| **Claude Code** | Сложная разработка, исследование, конвертеры, архитектура, техническое ревью; взаимозаменяем с Codex | Самостоятельно менять scope, принимать этап или вести одновременную запись |
| **DeepSeek Harness** | Посильные локальные изменения Unity/C#, исправления ошибок, интеграция готовых решений, техническая рутина; тяжёлая задача — только эксперимент | Самовольно браться за сложный перенос, массовую переделку моделей или менять архитектуру |
| **Codex** | Те же сложные задачи, что Claude; продолжение по HANDOFF при лимитах, независимое ревью | Самостоятельно менять scope, принимать этап или вести одновременную запись |

**Важно:** реальные полномочия и ведущий исполнитель **задаются ACTIVE_STAGE и ТЗ**, а не навсегда конкретной моделью. Ролевые описания старого онбординга не могут отменять поздние поручения.

### Новое назначение по решению продюсера (2026-11-06)

- **Claude Code и Codex — взаимозаменяемые старшие технические агенты.** Им назначаются сложные исследовательские и инженерные задачи: конвертеры Alpha→Unity, анимационные системы, архитектура, сложные инструменты и существенная переработка моделей. При исчерпании лимита одного второй продолжает ту же задачу по Git SHA и HANDOFF, без самовольного расширения scope.
- **DeepSeek Harness — исполнитель посильных ограниченных задач:** локальные правки Unity и кода, устранение дефектов, применение готовых инструментов, документация, вспомогательные операции. Сложные разработки, переносные конвертеры и масштабную переделку моделей ему не назначать по умолчанию; возможен только отдельный контролируемый эксперимент с критериями остановки.
- Назначение зависит от сложности задачи, а не от жёсткого запрета писать код. Claude/Codex могут и создавать, и проверять сложный код. DeepSeek может исправлять код, не меняя архитектуру без решения.
- **Проверки:** полноценное тестирование и независимый аудит преимущественно в конце этапа или завершённого проверяемого пакета. По ходу изменений — минимальные быстрые проверки при реальном риске сломать сборку, сохранения, данные или интеграцию. Не запускать полный Unity suite после каждого действия. Непроверенное не помечать PASS.
- **Удаление лишнего:** искать устаревшие или неиспользуемые компоненты, скрипты, пакеты, сцены и тестовые заглушки. Перед удалением проверять ссылки Unity/serialized data, зависимости, сохранения и историю принятых этапов. Удалять только в разрешённом scope с обратимым Git diff; при риске потери функциональности нужна отдельная санкция. Оригинальные Alpha-ассеты и чужие изменения не удалять автоматически.

## 4. Общие технические ограничения

- Рабочий репозиторий: `D:\Projects\CubeGame`; Alpha: `D:\Games\Cube world` **только чтение**.
- **Одна локальная рабочая папка, агенты последовательно**, без параллельной записи, дополнительных постоянных копий и worktree без отдельного решения.
- Git-ветка на задачу; разрешён **push своей stage/review/codex-ветки** после проверки файлов/секретов. Push ≠ merge ≠ ACCEPTED. **Без merge, force push, удаления веток или слома чужих изменений** без решения.
- Сначала штатные возможности Unity, не писать второй движок. `CubeGame.Core` сохраняет независимость от `UnityEngine`; корневая архитектура — модульный монолит ADR-0001.
- Реверс и ассеты Alpha: исследовать/конвертировать локально по D41/D46/D54; бинарники, оригинальные модели/архивы, секреты, персональные пути/данные не публиковать. Перед релизом использовать собственные/лицензированные материалы. Документы могут хранить **собственные описания**, но не копии закрытого исходника.
- **Дизайн D66** актуальнее D65 по прокачке: единственное магическое дерево, практика боя, свитки, летописи и руны. D65 контактные удары/перекаты и настройка смерти сохраняются.
- **D63/D64:** Frogman исключены из CubeGame, раса не делает NPC обязательным врагом и не запрещает смешанные фракции.

## 5. Два контура работы (не смешивать)

**Контур проектирования:** идея → анализ зависимости/риска → обозначение DRAFT → обсуждение → решение продюсера → Dxx ACCEPTED → GDD/MEMORY/ROADMAP при необходимости. Запись в GDD сама по себе не санкционирует реализацию.

**Контур реализации:** утверждённый этап → **одна ограниченная задача** → исполнитель/ветка → код/ассеты → автоматические/ручные проверки → отчёт и push → независимое ревью → продюсерские исправления или ACCEPTED → обновление памяти/статуса → следующая задача.

## 6. Универсальный контракт задания

Каждое поручение имеет **TASK_ID**, цель, связь с Dxx/GDD, предшествующий SHA, рабочую ветку, границы «МОЖНО/НЕЛЬЗЯ», нужные входные материалы, исполнителя, ожидаемый артефакт, тесты, критерии PASS/FAIL, способ показа продюсеру, отчёт и критерий завершения.

Не пытаться «сделать весь этап» одним бесконтрольным промптом. Задачу ограничивать **проверяемой возможностью/результатом**. Функция кода не обязательно равна сессии; несколько микрозадач допустимы только если общий контракт мал и ревьюируем.

## 7. Честный статус

- `IDEA/DRAFT` — мысль или проект спецификации;
- `ACCEPTED_DESIGN` — продюсер утвердил поведение, но код может отсутствовать;
- `AUTHORIZED` — разрешён конкретный технический объём;
- `IN_PROGRESS` — идёт работа;
- `BLOCKED/PARTIAL` — дефект/нехватка доказательств, не выдавать за PASS;
- `READY_FOR_REVIEW` — результат готов к независимой проверке, **не** принят;
- `ACCEPTED` — только подтверждение продюсера;
- `NOT_AUTHORIZED` — нельзя запускать следующий этап.

В отчёте разделять **«сделано», «протестировано», «визуально утверждено», «осталось»**. Зелёные unit-тесты не доказывают художественное соответствие или сходство с Alpha.

## 8. Проверки и отчёты

Исполнитель завершает задачу: воспроизводимые команды тестов, фактические PASS/FAIL, Git SHA/ветка, изменённые файлы, сравнение с эталоном, лог ограничений, инструкции ручного осмотра, риски, запрет на самоприёмку.

Ревьюер читает diff и независимые доказательства; если работа касается моделей/анимаций/визуала, продюсер **лично утверждает каждый переработанный модельный образец** по D35. Регрессии и визуальные несоответствия должны блокировать приёмку до исправления.

## 8.1. Гигиена межчатовой памяти

`PROJECT_MEMORY.md` — **оперативная память, которую обновляют все агенты в пределах текущего этапа; очистку выполняет только GPT**. Хранить всю необходимую для продолжения информацию текущего этапа: поручение, исполнитель, ветка/SHA, доказанный прогресс, открытые блокеры и следующий шаг. При смене задачи внутри этапа обновлять сведения. После `ACCEPTED` сначала записать краткий итог в [`docs/STAGE_HISTORY.md`](../STAGE_HISTORY.md), сохранить незакрытые зависимости для следующего этапа, затем удалить подробности закрытого этапа из оперативной памяти. История Dxx, ADR, отчётов и Git сохраняется. Ограничение по символам не должно приводить к потере важных данных активного этапа.

## 8.2. Владение очисткой и checkpoint

**Все агенты обновляют `PROJECT_MEMORY.md`** по мере исполнения текущего этапа. **GPT — единственный ответственный за чистку памяти** после завершённых работ и **за ведение `docs/STAGE_HISTORY.md`**. Исполнители не стирают результаты чужих работ и не переносят этапы в историю: дают точные отчёты и ссылки для GPT.

**Один этап/подэтап или самостоятельная механика/функция — одна сессия; при переходе к новой — новый чат.** Внутри той же механики исправления и вспомогательные методы продолжаются в текущем чате. После каждой остановки, передачи или перед лимитом агент сохраняет `docs/agents/CURRENT_CHECKPOINT.md` и актуализирует `PROJECT_MEMORY.md`. При длительной работе checkpoint фиксируется после значимого завершённого блока.

Команда **«продолжаем»**: перечитать память, ACTIVE_STAGE, AGENTS и checkpoint, проверить реальный Git HEAD/ветку и продолжить ближайший разрешённый шаг; если checkpoint устарел — восстановить состояние без догадок. Это не авторизация следующей стадии.

## 9. Работа с контекстом

Сессия имеет явную цель и входной комплект: TASK_ID, stage, commit, 3 обязательных файла, последние Dxx и предыдущий отчёт. На выходе — самодостаточный `HANDOFF`, не требующий полного чтения старого чата; см. [SESSION_CONTEXT_PLAN.md](SESSION_CONTEXT_PLAN.md) после подготовки.

**Не требовать новый чат на каждую C#-функцию.** Новую сессию давать самостоятельной задаче, новой фазе исследования или смене исполнителя, когда есть чёткий артефакт и точка передачи. Длинную сессию дробить до того, как появятся противоречия и потеря контекста.

## 10. Definition of Done и передача владения задачей

Кандидат регламента считается подготовленным к утверждению, только если выполняются все условия:

- **Один активный писатель:** в общей рабочей директории одновременно изменяет проект только один назначенный агент. Второй агент до явной передачи владения работает только как читатель/ревьюер.
- **Передача без скрытого состояния:** перед сменой исполнителя фиксируются ветка, HEAD, `git status --short --branch`, незакоммиченные изменения и причина каждого из них. Чужие изменения не прятать и не «дочищать» без назначения.
- **Ревью не равно исправлению:** ревьюер по умолчанию не вносит правки в ветку исполнителя. Если нужны исправления, продюсер/ведущий явно назначает `REVIEW_FIX` и нового владельца записи.
- **Scope lock:** найденное улучшение вне текущего TASK оформляется как DRAFT/OPEN DECISION и не реализуется тайком «заодно».
- **Проверяемый выход:** TASK нельзя закрыть без артефакта, реальных тестов/наблюдений, SHA, списка ограничений и инструкции воспроизведения.
- **Не дублировать канон:** после утверждения правила переносятся в корневой `AGENTS.md`; этот файл не остаётся вторым нормативным источником.

Эти пункты меняют только дисциплину работы агентов и **не** открывают новый Stage, не утверждают игровую механику и не разрешают merge.
