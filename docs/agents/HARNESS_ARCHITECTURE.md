# CubeGame — общая архитектура AI Harness
Один репозиторий, общие AGENTS/Memory/Active Stage и контракты; адаптеры Codex (.agents/skills) и DeepSeek (.dsh/skills). Канонические skills — .dsh/skills, зеркала генерируются/проверяются скриптом. Archive исключён.

## Цикл
Запрос обычными словами → короткий TASK (сам агент) → read-only Git/Editor/skills preflight → снимок защищённых файлов и baseline → реализация → независимые от реализации проверки (технические и визуальные по задаче) → gate check → отчёт/diff → решение владельца. Не запрашивать согласование каждого внутреннего шага. При неоднозначности сначала использовать принятый референс/паспорт; блокировать только существенный конфликт или риск. После двух безуспешных правок одного дефекта — смена метода или BLOCKED с фактами.

## Исполняемые проверки
Из корня чистой рабочей ветки: `node tools/harness/preflight.mjs`, затем `node tools/harness/task-gate.mjs start <contract.json> <receipt.json>`. После работы: `node tools/harness/task-gate.mjs check <contract.json> <receipt.json> <result.json>`. Контракт и receipt хранить вне tracked paths, например в локальном временном каталоге; не публиковать приватные пути/референсы. Шаблоны: [TASK](HARNESS_TASK_TEMPLATE.md). Gate фиксирует SHA, хеши контекста (изменение только для явно разрешённых editable_context_files в docs-задаче) и защищённых файлов; проверяет текущую ветку, ancestry, Git diff/untracked scope, наличие evidence и отдельные статусы. Для внешнего UE-каталога проверяются только явно перечисленные файлы/доказательства, не все операции редактора. Не использовать gate для обхода полномочий.

Gate — проверка согласованности и наличия артефактов, а не доказательство прочтения агентом, достоверности скриншотов, качества модели или работающего hook. CI проверяет скрипты на тестовых данных; локальную интеграцию проверить отдельно. Hook DSH проверяет часть операций, подключение UNKNOWN; Codex hook не включён автоматически. Реальные разрешения ОС/среды и независимое ревью обязательны. Не менять настройки без владельца.

## Доказательства и опыт
Принимать только наблюдаемые результаты, не выводить PASS из exit code или числа полигонов. Отдельные критерии, scope и визуальный verdict. Неудачные попытки кратко фиксировать: дефект, гипотеза, метод, результат. Сравнивать на одинаковой задаче по [HARNESS_EVALUATION](HARNESS_EVALUATION.md). Принятое решение владельца записывать в паспорт/память только в пределах его смысла.
