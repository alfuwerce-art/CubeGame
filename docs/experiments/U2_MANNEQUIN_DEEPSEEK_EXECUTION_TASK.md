## 0. Роль, цель, Definition of Done

Ты — **DeepSeek Harness, технический исполнитель**. Задача: при помощи доказанных инструментов локального Unity и Unreal Editor **исследовать уже существующую модель игрока из Unity-проекта CubeGame**, изучить её анимации **как примеры**, сопоставить с референсами владельца, а затем по утверждённым воротам изготовить **самостоятельно анимируемый модульный voxel-манекен CubeGame**. Проверить его как управляемого игрока и как врага с общей иерархией костей, сохраняя штатные системы анимации Unreal 5.9. **Не создавать производство 2800 моделей, отдельную фабрику, полный редактор рас или массовый набор анимаций**.

**Главный ожидаемый результат после всей последовательности:** в отдельной Unreal-сцене реально двигается `CG_Mannequin_V1`, имеет компактный воксельный силуэт по референсам, большие блоковые пропорции, отдельные визуальные модули кистей/предплечий/коленей/ступней, совместимый Skeleton и собственные AnimSequences, умеет стоять, двигаться, поворачиваться, прыгать, держать предмет и атаковать (атака/враг/урон — U3). Один экземпляр управляется игроком, второй тем же скелетом — AI. Форму, движения и технический результат владелец принимает лично.

**НЕ достаточно:** статичный PNG, создание одного FBX, импорт mesh без skeletal rig, использование анимации Manny/Unity без адаптации, зелёные unit-тесты без запуска, слова «готово» без видео/логов/путей, отсутствие публичного лицензионного контроля.

**Обязательные стоп-ворота:** M0 read-only аудит → обзор владельца → M1 геометрия/ракурсы → визуальная приёмка владельца → M2 риг/анимации/Player → технический обзор владельца → U3 противник/бой → U4 сборка. **Весь объём ТЗ дан сразу для прозрачности конечной цели, но ни один агент не вправе перескакивать ворота или назначать себе `ACCEPTED`.** Если U1 ещё не выполнен, реализацию U2 не начинать; M0 audit допускается заранее как отдельная read-only исследовательская задача.

**MANNEQUIN_V1 — художественно-техническая гипотеза для визуального ревью:**
- Adult-proportion stylized voxel humanoid; **почти квадратная крупная голова примерно 33–35% полного роста** — исходный ориентир, а не нерушимый численный канон; измерить и сравнить в ортографических ракурсах.
- Короткое компактное туловище/таз, приземистые короткие ноги, укороченные руки, небольшие блочные ступни. Нет круглого реализма, бицепсов, ярко выраженных мышц и пластилинового soft-body.
- Визуально раздельные плечи/предплечья/кисти; физически обоснованная кисть с настоящими отделёнными пальцами, достаточно подробная для захвата рукояти.
- **Ноги не должны превращаться в две сплошные человеческие голени**: видимые отдельные коленные блоки и стопы, допустимые воздушные промежутки; кости могут быть невидимыми, но движение обязано сохранять правильную опору и расстояния.
- Видимая геометрия модульная; Skeleton логически непрерывен. Независимые rigid-weight секции или корректно привязанные модули, без деформации кубических граней.
- Нейтральный матово-серый материал; без лица, волос, бороды, одежды, брони, расовых красок, UI, массовых аксессуаров.
- Точная высота и размеры UE Character Capsule **подбираются по факту**; не изобретать абсолютные масштабы. Сравнение фронт/профиль/спина/¾ при одинаковых масштабе, позе и камере; записать пропорции головы, плеч, рук, торса, колена, ступни и свободные зазоры.

**Обязательное качество модели:** единый стабильный origin/скейл/ориентация, чистые нормали и pivot, понятные имена секций/костей, независимая замена **как минимум одной** визуальной части без переделки всего анимационного графа.

## 3. M0 — read-only аудит источника, анимаций и проекта (ПЕРВЫЙ ВЫПОЛНЯЕМЫЙ ШАГ)

**Работать только на чтение. Никаких импортов, изменений Unity/UE, переноса FBX, генерации новой модели или коммитов чужого материала.**

**3.1 Проверка среды:** `git status` обоих каталогов по наличию репозиториев, remote, HEAD, какие ассеты локально не отслеживаются; UE версия/редактор открыт/название уровня, C++ compiler/UHT/UBT отдельным безопасным просмотром. Подтвердить реальный MCP `list_toolsets` + `GetCurrentLevel` либо аналогичным подтверждённым read-only вызовом. Доступ к toolset не означает существование инструмента для произвольного импорта/рига.

**3.2 Поиск персонажа в Unity:** проверить Unity `Assets/`, Prefab, модельные файлы, Renderer/SkinnedMeshRenderer/Animator и возможные Procedural MeshBuilder, .scratch и архивный runtime (если разрешён читать). Найти **конкретную фактически видимую модель игрока**, а не первый встречный Character. Карта происхождения (оригинальный Unity/импорт Alpha/генерируемый runtime), файлы/формат, иерархия GameObject, число meshes/submeshes, bones/anchors, позиции кистей/головы/ног, материалы. Если процедурный runtime — указать, как снимаются geometry arrays без правки сцены, как экспортировать **копию** во временный локальный NON_SHIPPABLE каталог. Экспорт на этой стадии **не запускать**.

**3.3 Поиск Unity-анимаций:** найти доступные `AnimationClip`, Controller, Animator, procedural animation scripts и фактически используемые состояния Idle/Walk/Run/Turn/Attack/HitReact/Death. Зафиксировать их `FOUND / NOT_FOUND / PROCEDURAL`, длительность/порядок и ключевые **поведенческие наблюдения**: перенос веса, частота и ширина шага, работа корпуса/рук, замах, момент касания, восстановление, контакт стоп. Не переносить старые клипы, curves, KeyFrames, timestamps и данные треков на новый риг. Визуальная реконструкция **нового**, отличающегося движения позже.

**3.6 Технический план:** 2–3 реально доступных пути переноса/создания модели с плюсами и недостатками (Unity FBX Exporter; extraction procedural geometry в локальную копию; собственный source mesh через Blender/редактор). Не утверждать, что Unity mesh «готов», пока его не нашли.

**Пакет M0 владельцу:** короткий текст и компактные evidence: реальный источник, классы/тип анимации, hash референсов, карта рисков, метод, правовой статус, карта папок и ответы на неопределённости. ## 4. M1 — создание и согласование манекена (только после принятого M0 и U1)

**Цель:** не красивый концепт, а **редактируемый настоящий 3D объект** с модульными деталями и нужным силуэтом. Предпочесть встроенные UE Modeling Tools/Editor-операции, если они обеспечивают контроль топологии/пивотов и автоматизацию; Blender как средство собственно геометрии допустим, если реально нужен. Не создавать новый кастомный voxel-генератор без необходимости.

Порядок:
1. Создать отдельную рабочую ветку/копию и **нейтральный собственный** исходник с понятными именами; исходный Unity/Alpha donor держать отдельно как временную LOCAL_ONLY reference; не коммитить чужие bytes.
2. Разложить компоненты и модульные островки: `head, neck, torso, pelvis, upperarm_L/R, forearm_L/R, hand_L/R, knee_L/R, foot_L/R`, а также пальцы в минимально пригодном для хватов количестве. Допускается другой именованный набор, если документирует тот же функционал.
3. Соблюдать блочную непластичную геометрию, равномерную читаемую пикселизацию/ступенчатую форму и корректные воздушные разрывы. Проверить все pivot и возможность расставить локальные origins на невидимых шарнирах.
4. Подготовить T-pose или A-pose как каноническую bind pose и серый нейтральный материал, без художественной отделки. Исходники сохранить редактируемыми, а не только экспортированный FBX.
5. Создать 4 одинаковых ортографических вида: **FRONT / BACK / LEFT/RIGHT / ¾**; крупно `HAND_OPEN`, `HAND_FIST`, `HAND_GRIP`, плечо, колено, ступня. Рядом с каждым показать relevant crop исходного авторского референса/ссылку на локальный источник (в пределах прав).
6. Составить измерения: доля головы в росте, плечи/торс, длины рук и ног, зазоры, ширина стопы; явные отличия от цели с перечислением `MATCH / PARTIAL / MISMATCH`. Не выдавать проценты «из головы».
7. Проверить импорт/открытие при необходимости, но **не начинать финальные риги и пакет анимаций до визуального ревью владельца**.

**Выход M1:** редактируемый mesh источник, UE importer recipe, 4 вида и детали, таблица сравнения, описание прав/происхождения. `READY_FOR_OWNER_VISUAL_REVIEW`. Если форма не принята — исправление только геометрии, без ненужной анимационной работы.

## 5. M2 — Skeleton, управление и ОРИГИНАЛЬНЫЕ анимации в UE (после принятия M1)

**Использовать Unreal 5.9 максимально — без самописного анимационного движка.** Проверить фактическую доступность каждого нужного инструмента и использовать по назначению:
- `Skeletal Mesh`, `Skeleton`, `Physics Asset` для геометрии/коллизий;
- `Animation Sequences` и `Control Rig`/Animation Editor для **создания собственных поз и клипов**;
- `Animation Blueprint`, `State Machine`, `AnimGraph`, `Blend Space` при надобности для переходов;
- `IK Rig` / skeletal controls / foot placement — только если реально исправляет стопы, не ломая блоковую геометрию;
- `Animation Montage` и `Anim Notifies` для ударов, реакций и игровых окон урона;
- `Sockets` для рукояти оружия/сменных деталей;
- `Enhanced Input`, `ACharacter`, `CharacterMovement` и C++ Gameplay Framework для игровых команд.

**Принцип:** визульно плавающие блоки сидят на **непрерывном логическом Skeleton**: `root → pelvis → spine → neck → head`; плечевой пояс/верхняя часть руки/предплечье/кисть/пальцы слева/справа; бедро/колено/ступня. Скрытые промежуточные кости допустимы. Веса твёрдые, грань куба не тянется/не сглаживается как кожа. Модульность через чистые геометрические островки или отдельные Skeletal Mesh Components/attach; одно конкретное заменяемое место показать в движении. Правильный `Capsule`, collision bodies, стабильная ориентация, no foot clipping.

**Источник Unity анимаций — только поведенческий референс.** Собственные клипы:
- `CG_Idle_New`: стабильная нейтральная стойка, редкие движения корпуса/рук;
- `CG_Walk_New`: свой цикл, фазы опорной ноги, мах рук, правильные отдельные колени и ступни;
- `CG_Turn_New`: читабельный разворот, без бессмысленного вращения рук;
- `CG_Run_New` (при наличии бега в текущей задаче) и `CG_Jump_New`: корректное ускорение/земля/приземление и логическое положение ступней;
- в U3: `CG_Attack_New`, `CG_HitReact_New`, `CG_Death_New`: новые позы/ритм/ход движения под контактный бой CubeGame.

**Нельзя:** экспортировать Unity `.anim` / FBX clips / Animator curves / keyframes, ретаргетить или воспроизводить их ключи на нашем новом Skeleton, применять готовый Manny-клип как **финальную** анимацию, копировать чужую узнаваемую хореографию покадрово. Можно сравнить основные свойства `шага`, `опоры`, `замаха` и построить **отличающееся оригинальное движение**, подходящее этому телосложению. Клипы должны быть редактируемыми в UE, с независимым provenance.

**Геймплей U2:** игрок открывает сцену, ходит в 4 направления, управляет камерой, меняет направление, прыгает, останавливается, не улетает/не рассыпается. Ступни стоят на земле, IK (если нужен) не делает их «желе», разрывы между частями остаются, оружие в кисти не плавает. В PIE и Standalone подтвердить реальное игровое управление. Отдельные C++ и AnimBP рутинные тесты — не замена запуску.

**Сдать:** UE package paths для Skeletal Mesh/Skeleton/AnimBP/Control Rig/Animations, исходник геометрии, named joints, skeleton diagram, weapon socket, видео/скрины `Idle/Walk/Turn/Jump/Grip`, таблицу отличий от Unity-модели и анимаций, логи компиляции и фактического PIE/Standalone. Статус `READY_FOR_OWNER_REVIEW`; даже при `TECHNICAL_PASS` модель ещё **не финальный художественный ассет**.

## 6. U3 — игрок и враг на ОДНОМ манекене

Только после рабочей U2-модели: использовать тот же `Skeleton` (или доказанную совместимость и единый набор клипов) для Player и Enemy. Разница — `Controller/AIController/Behavior`, параметры и состояния, **не копия другого рига**.

Минимальный сквозной сценарий:
1. Запуск тестовой карты, виден управляемый герой и один враг.
2. Игрок поворачивается/идёт, враг замечает героя и приближается без визуальных разрывов.
3. Герой держит простой оригинальный тестовый предмет/меч через сокет, выполняет авторский `CG_Attack_New`.
4. Проверка контакта оружия с противником, реальный `HP` уменьшается **один раз за разрешённое окно**, промах не наносит урон. Внешняя анимация связана с игрой через `AnimNotify/Montage`, механика урона — C++.
5. Противник показывает `CG_HitReact_New`, по достижении 0 HP — `CG_Death_New`/отключение атак. Враг не «оживает» от спама событий после смерти.
6. Выпадает тестовый предмет, работает подбор, UI показывает HP/подбор; SaveGame/LoadGame сохраняет позицию/состояние подобранного предмета согласно U3.
7. Всё в одном игровом проходе, без ручной подстановки состояний в консоли.

U3 — отдельный игровой этап, не доказывается одной красивой анимацией атаки. Вызовы MCP и Editor Python фиксировать по факту; не объявлять инструменты работающими только из `list_toolsets`.

## 7. Повторяемость, Python vs MCP и минимальный набор инструментов

- **Editor Python**: воспроизводимые редакторские операции, подготовка сцены, импорт проверенных файлов, создание ассетов/настроек **по реально поддерживаемому API**, сохранение; запуск дважды не создаёт дубликаты.
- **Unreal MCP**: подтверждённые команды `list_toolsets/describe`, получение проекта/уровня, установка assets/настроек/проверка только при реально доступном инструменте. Логи `tool_name/status/elapsed/action/observable_effect`.
- **C++ runtime**: CharacterMovement, атаки/урон, Enemy AI, состояние и SaveGame; не писать runtime бой на Editor Python.
- **Unreal native animation**: Control Rig/AnimBP/Montage и прочее по необходимости; не пытаться подменить анимационный редактор сотнями своих C++ строчек, если есть встроенный рабочий путь.
- **External modeling** (Blender/Unity FBX Exporter): только если штатного UE-инструментария недостаточно для редактируемой модульной геометрии. Логировать обоснование.
- **Точность сравнения способов:** U1 Python и U2 MCP выполняют разные функции и не дают чистого A/B рейтинга. Фиксировать длительность работы, количество tool calls, ошибки, повторные попытки, ручные вмешательства, количество реальных правок и результат. Если нужно строго сравнить Python vs MCP — одинаковая маленькая операция в двух чистых копиях сцены, без создания второго игрового ядра.
- **Не копить сырые логи сессий** и десятки гигабайт cache в Git. Хранить лишь отчёты/команды/сводку/минимально необходимые evidence, а временные UE DerivedDataCache и артефакты компиляции исключить.
