# ADR-0001 — Модульный монолит как архитектурная основа

**Проект:** CubeGame (рабочее название)  
**Статус:** ACCEPTED — решение продюсера в диалоге 2026-11-02.  
**Область утверждения:** только **принцип модульного монолита**. Другие решения A01–A09 из `ARCHITECTURE_PROPOSAL.md` ещё не утверждены.

## Решение

Игра строится как **один Unity-проект и один исполняемый игровой продукт**, состоящий из логически разграниченных модулей с определёнными ответственностями. Основные игровые правила и состояние не должны быть жёстко привязаны к сценам, MonoBehaviour, HUD и аниматорам. Модули общаются через договорённые контракты и события, а не через произвольный доступ ко внутренним данным друг друга.

При этом нельзя раздувать архитектуру «ради чистоты»: не требуются микросервисы, сетевые процессы, десятки интерфейсов на одну функцию или полноценная плагин-платформа сейчас.

## Причины

- Длительная эволюционная разработка: базовая Alpha → модели/графика → расширенные RPG-системы → мультиплеер.
- Локальный ИИ-разработчик должен иметь ограниченную область изменения и изолируемые проверки.
- Новые функции не должны требовать массовой переделки чужих модулей.
- Unity-представление и хранение состояния должны быть отделены от игровых правил.
- Пока нет серверов, расходы на хостинг запрещены.

## Последствия и границы

- Чёткие API, зависимости, владельцы данных, тесты на уровень модуля.
- Изменения общих контрактов — через архитектурное ревью.
- В будущем авторитетную симуляцию можно адаптировать под сервер, но это **не обещание** интеграции сети без рефакторинга.
- Точные assembly definitions, структура папок, версии Unity/URP, форматы сейвов, размер чанков и границы отдельных модулей утверждаются отдельно на S01 по прототипам.
- Статус настоящего ADR не переводит архитектурный черновик целиком в ACCEPTED.

## Источник

Ответ продюсера «окей, идем дальше» на предложение утвердить модульный монолит, проверив конкретные границы модулей на техническом прототипе.
