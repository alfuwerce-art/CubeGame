# CubeGame — план внедрения Data-Driven Layered Architecture

**Статус:** APPROVED AS PROCESS / IMPLEMENTATION NOT STARTED.
**Основание:** [ADR-0002](ADR-0002-data-driven-layered.md) + [ADR-0001](ADR-0001-modular-monolith.md).
**Не является разрешением** открыть новый игровой этап или начать массовый рефакторинг. Текущие границы — [ACTIVE_STAGE](../ACTIVE_STAGE.md).

## Актуальная позиция

Архитектура автора используется **как уточнение** уже выбранного модульного монолита, а не как его замена. Проверенный GitHub baseline (ветка `codex/s05a2-claude-continuation` на 2026-11-06):

- `Assets/CubeGame/Core/Combat`, `Equipment`, `Progression`, `Items` — чистое ядро; повторно не реализовывать.
- `Core/Persistence/SaveService.cs` использует `ISaveStore` / `ISaveSerializer`, а `Persistence/FileSaveStore.cs` отвечает за Unity-путь и атомарную запись — правильное направление зависимостей.
- `Presentation/Player/PlayerMotor.cs` пока читает `Input.GetKey`, считает движение и напрямую двигает `CharacterController`. Это **допустимый pilot-код**, но целевой Input → command → simulation → motion adapter ещё не доказан.
- `Presentation/Combat/CombatDemo.cs` и `Presentation/Rendering/PilotWorldView.cs` — пилотные сцены/адаптеры, не доказательство законченной общей архитектуры мира.
- Исследовательские `tools/alpha_models/...` / `AlphaAnimationController` в S05 — изолированная pipeline, не готовый production-контракт.

**Статус проверки:** документальный аудит по выбранным файлам и дереву репозитория; полный static analysis/Unity-прогон в этом изменении **не выполнялся**.

## Последовательность внедрения

### A0 — сейчас, документация: DONE после публикации ветки

- ADR-0002 задаёт контракт слоёв; `AGENTS.md` ссылается на него.
- Архитектурные уточнения отражены в `PROJECT_MEMORY.md`, `ACTIVE_STAGE.md` и дорожной карте.
- Действующие статусы и разрешения не изменены.

### A1 — при техническом ревью S05A-2 (без блокировки переноса анимаций)

- Нарисовать схему зависимостей *фактически существующих* проектов/asmdef и границ `Core`, `Presentation`, `Persistence`, изолированного S05-пилота.
- Зафиксировать 3 категории: `ALREADY_COMPLIANT` / `PILOT_EXCEPTION` / `NEEDS_CHANGE` с путём файла, технической причиной и риском.
- Для S05 проверить: исходные клипы и provenance — данные; `AlphaAnimationController` управляет **визуальной позой** и не объявляется владельцем HP/боевых правил; различать реальные тайминги Alpha, эмуляцию, самостоятельные Unity-переходы.
- Не блокировать завершение текущих разрешённых экспериментов по одному только различию имён папок. Независимые проблемы функциональности и происхождения данных остаются отдельными критериями ревью.

**Результат A1:** краткий `docs/reports/ARCHITECTURE_BASELINE_AUDIT.md`, перечень правок и оценка регрессионных рисков. Это ещё не implementation permission.

### A2 — перед интеграцией S05-пилота в основную игру, только после отдельной авторизации

- Описать интерфейс `AnimationClipData / PoseSource → Unity rig/Animator adapter` (названия кандидаты, не новый обязательный API).
- Отделить команды `Move/Attack` и игровое время от визуального проигрывания клипов и переходов.
- Валидировать provenance и соответствие ригу; отсутствие обязательных клипов → явный `FAIL`.
- Добавить EditMode-тесты преобразований и PlayMode-тесты реальной интеграции, не ломая работающий S05-пилот.
- Вернуть результат на личную визуальную приёмку продюсеру. **S05B пока NOT_AUTHORIZED**.

### A3 — следующий разрешённый этап функционального развития игры

- До добавления новой игровой системы проверить, можно ли использовать `Core`-контракт и существующие вычислители, вместо дублей.
- Для повторяемого контента ввести определения/конфиги с версией и валидатором; сначала один тип как эталон, затем расширение.
- При введении полноценного перемещения: разделить ввод, команду, симуляцию и Unity `CharacterController`; пилот `PlayerMotor` не переписывать ради документа.
- Для мира/NPC закрепить стабильные ID и независимые логические состояния до масштабного стриминга/сценовых объектов.
- После каждого изменения — существующая регрессия `S02–S04`, тесты сохранения, доказательство работы в Unity и явная фиксация статуса.

## Изменение критериев приёмки будущих этапов

В отчётах **новых/изменённых систем** добавить пять полей:

1. `LAYER_OWNER` — кто владеет состоянием и алгоритмом.
2. `DEPENDENCIES` — список новых зависимостей и отсутствие запрещённых/циклических.
3. `DATA_CONTRACT` — источник определений, статус достоверности Alpha, валидация; либо `NOT_APPLICABLE`.
4. `PERSISTENCE_IMPACT` — влияние на сохранения, миграции и стабильные ID.
5. `REGRESSION_EVIDENCE` — команды/результаты затронутых EditMode, PlayMode и других тестов.

`UNKNOWN`/`NOT_TESTED` — не `PASS`. Новое архитектурное требование не даёт агенту права менять игровое содержание, завершать S05A-2 или открывать S05B.

## Решение о дополнительных этапах

**Новый отдельный игровой этап сейчас не нужен.** A1 — небольшая архитектурная проверка в рамках уже существующего S05A-2-ревью. A2/A3 становятся задачами только после соответствующих разрешений. Если A1 обнаружит критическое нарушение владения состоянием/сохранениями, вынести отдельный короткий `architecture-review-fix` с тестами и согласовать объём; не переписывать ядро втихую.
