# CubeGame — порядок разработки персонажей
Дата: 2026-11-25. Согласовано владельцем в чате после разбора работы над манекенами. Это порядок работ, не техническая приёмка моделей и не разрешение на массовое производство.

## Текущий цикл в Unreal Engine 5.9
1. Найти существующий редактируемый мужской/женский манекен, его исходник, версию, зависимости и референс владельца. Не пересоздавать модель без задания. Защитить уже принятые части.
2. Внести локальные исправления геометрии по указанию владельца. Проверить ракурсы, нормали, пересечения, материалы, пропорции и неизменность остальных частей.
3. Проверить скелет, веса, pivots, деформации, хват и движения в реальном открытом UE. Использовать встроенные средства UE по назначению (Skeleton, Control Rig, Animation Sequences, AnimBP, IK, Montage, sockets) и соответствующие профильные skills. Не копировать старые игровые клипы; поведение может служить референсом. Не считать технический PASS визуальной приёмкой.
4. После базовых форм и анимаций проработать отдельно лицо, волосы и расовые элементы; затем одежду/броню; затем оружие и удерживаемые предметы, включая дельтаплан. Проверить полный образ и движение в экипировке. Допустимо возвращаться к форме и анимации при обнаружении проблем.
5. Владелец утверждает полный экипированный эталон. Только тогда фиксировать окончательные размеры и интерфейсы крепления для этого эталона. Не выдавать текущие измерения кандидатов за обязательные размеры. До проработки всех персонажей не начинать разработку генератора персонажей. Перед удалением этого временного ограничения при переходе к генератору получить отдельное согласие владельца; затем удалить правило без сохранения его как действующего требования.

## Для каждой итерации
Обычное описание владельца → короткий TASK с защищёнными областями → анализ исходника и референса → локальная правка → реальные технические/визуальные проверки по [ASSET_ACCEPTANCE](ASSET_ACCEPTANCE.md) → одинаковые ракурсы до/после и запись движения, если затронута анимация → решение владельца → сохранение точной версии и результата в паспорте/памяти. При отклонении исправлять конкретный дефект, а не модель целиком. Сохранение кандидата не означает ACCEPTED. При недоступности локального UE или исходника честно указать BLOCKED/NOT_RUN.

Производительность проверять на реальных сценах с NPC и LOD до массового производства. Не вводить произвольный бюджет треугольников на этапе поиска формы.

Этот порядок локального редактирования и доказательной проверки применять к другим ассетам (существа, оружие, броня, растительность) с подходящими критериями; риг и анимация обязательны только там, где применимы. Не расширять конкретное поручение до создания всех перечисленных ассетов.

См. [стандарт формы](CHARACTER_STYLE_STANDARD.md), [реестр](assets/ASSET_REGISTER.md), [навыки](../agents/SKILLS_INDEX.md).
