## Цель

Взять уже подготовленные Alpha-модели/действия/числовые правила и **проверить их внутри реального проекта Unity 6.3**, не ограничиваясь Python или standalone Mono. Ошибки исправлять в C#/Unity-адаптерах, сценах и фактическом игровом конвейере; после каждого исправления повторять Alpha-сравнение и Unity-тест.

## Порядок: несколько игровых систем, не один визуальный объект

### A. Предметы, крепления и анимации — приоритет 1

- Подключить `cubegame.item_layer/1` и `item_attach.py` как Unity C# данные/адаптеры к существующим S05 `AlphaRig`/`AlphaClip`/контроллерам; не запускать Python во время игры.
- Проверить `item_icon_id → модель → слот → anchor → IN_HAND/ON_BACK` для одноручного, двуручного, парного, лука/арбалета/посоха/щита/кулака и расходника. Привязки left/right/offhand, клипы 57→67→58, действия 80/81, состояние 71 камня голема — по подтверждённым данным и доступности.
- В сцене показать предмет на персонаже в статике и движении, удержание двумя руками и отдельные позы; снять 4 ракурса и моменты действия; проверить XYZ/повороты/кватернионы/scale/тайминги с Alpha-эталоном.
- Разделить: предмет показан в руке vs доказан расход/лечение vs доказана поза тела. При неизвестном эффекте не симулировать его как оригинальный.

### B. Реальный бой и численные расчёты — приоритет 2

- Связать S03 `HitResolver`/`DamageResolver`/`DamageMitigation`, S04 экипировку, action-state, hit window, HP, stamina/mana, cooldown, death, XP; использовать уже доказанные формулы, не дублировать Core.
- В Unity PlayMode воспроизвести детерминированный бой на манекене/NPC: запуск атаки → анимация/оружие → проверка попадания → численное изменение HP/состояния → hit/death → награда, где доказана.
- EditMode: граничные значения урона/блока/кулдауна и отсутствие расхода при отказе. PlayMode: фактическая связь анимации и урона. Сравнить с oracle Alpha и зафиксировать численное отклонение.
- Не додумывать OQ-01/OQ-24/стамину. При несовпадающих enum: сначала тесты и безопасный mapping RawAlphaID↔DomainID; **не менять принятые S04 enum или сейв v1 молча**.

### C. Остальные доступные системы — приоритет 3

- Movement: seed-векторы/кривые/стамина, реальные Unity движение/камеру/состояния; OQ-23 и прыжок оставить UNKNOWN до доказательства.
- World: детерминированность region/seed и восстановление небольшого участка/дельт **в Unity**, но не называть пилотный heightfield рельефом Alpha.
- NPC: анимация/действие/AI-тик/спавн для проверяемого вида, взаимодействие с боем; offscreen simulation — отдельно как CubeGame extension.
- Items/save/economy/quests: доступные EditMode/PlayMode тесты контрактов с реальным Core. Отсутствующие buy/loot/recipe/data не заменять произвольными данными.
- Для всех систем без достаточного Alpha-эталона: отчёт `PARTIAL/UNKNOWN/BLOCKED`, конкретный следующий эксперимент.

## Автоматизация и контроль

- Пайплайн **SCAN (только недостающие механизмы) → PLAN → VALIDATE → PILOT В UNITY → BATCH → REVIEW**. Сначала 1–2 эталонных представителя каждого уникального механизма; после PASS массово применять контракт ко всей совместимой группе. Никакого ручного перебора 2856 моделей.
- Минимум: Unity EditMode + PlayMode, лог результатов, режим запуска сцены для продюсера, кадры/видео сравнения, таблица `ALPHA_REFERENCE | UNITY_RESULT | DELTA | STATUS` с источниками каждого референса.
- Тесты Python/Mono из двух пакетов сохранить как независимую регрессию. При ошибке исправлять **Unity-реализацию**, а если выяснится, что эталон извлечён неверно — обновить доказательства с provenance, не подгонять тесты к ошибке.
- Каждая самостоятельная интеграционная партия: собственный commit+push в рабочей ветке; не merge в main. Публиковать прогресс/точные blocker через GitHub issue; не давать агенту статус `ACCEPTED`.

## Выход и критерии

1. Реальная Unity-сцена/сцены и C# source в текущем проекте, с подключёнными из существующего S05 представлениями. Не только JSON или скрипты командной строки.
2. Проверяемые Unity EditMode/PlayMode тесты с фактическим stdout и path логов; какие случаи прошли, какие skipped/blocked.
3. Предметы + анимации и боевой цикл, где доказано, визуально и численно сравниваются с Alpha-эталоном.
4. В отчёте четко различать `ALPHA_PARITY_PASS`, `UNITY_TECH_PASS`, `PARTIAL`, `BLOCKED`, `PLACEHOLDER_NOT_ALPHA`.
5. Готовый Unity-viewer для личного просмотра продюсером; отчёт с местом запуска, результатами, SHA/веткой.
