# S00 — протокол воспроизводимого замера движения и позиции (OQ-22 / OQ-23)

**Проект:** CubeGame. **Этап:** S00-R02 (D41), review-fix R02 (FIX-06) + финальная валидация (FIX-07).
**Статус:** `PROTOCOL_READY / RUNTIME_BLOCKED_ENVIRONMENT`. Разрешённые **4 запуска использованы** 2026-11-03; загрузка персонажа/мира не доведена из-за блокировки foreground/ввода средой DSH. Новые запуски без нового разрешения продюсера запрещены.
**Цель:** получить проверяемый ответ на два вопроса, не читая память живого процесса:

- **OQ-22** — что означает тройка `int64` в блобе персонажа (`+0x04…0x23`): текущая позиция, точка спавна или иное; в каких единицах и каков порядок компонентов.
- **OQ-23** — масштаб единиц движения: сколько блоков в секунду даёт базовая скорость, и какая гипотеза верна (A: 1 ед. = 1 блок; B: 1 ед. = 0.5 блока).

До закрытия OQ-23 скорости в прототипе остаются `PLACEHOLDER_NOT_ALPHA` (D42 `ACCEPTED`, но конкретные скорости не подтверждены).

## 1. Что уже известно и почему прошлый замер недействителен

Проверены две копии сейва, снятые в прошлой сессии:

| Файл | Время | Что показывает |
|---|---|---|
| `.scratch/shots/char_base.db` | 01:02:15 | до «движения» |
| `.scratch/shots/char_after.db` | 01:03:38 | после выхода в меню |

Фактический diff (инструмент `alpha_save_diff.py`, см. §3):

- изменилось **911 байт** в **580 диапазонах** — в основном слоты экипировки/инвентаря;
- тройка позиции `+0x04…0x23` изменилась **только в одном байте**: компонент 2 raw `10097787 → 10097786` (одна единица младшего разряда);
- скриншоты `shot06.png` (01:02:30) и `shot07_after_move.png` (01:03:15) показывают **тот же ракурс и те же ориентиры**; изменилось только игровое время (09:49 → 09:57).

**Вывод:** прошлый опыт **не доказал перемещение персонажа**. Визуальное «движение» не подтверждено, поэтому изменение позиции на 1 LSB нельзя трактовать ни как «позиция не сохраняется», ни как «поле не является позицией». Чтение памяти процесса тоже не дало результата (живой объект не найден за 2 подхода) и в новом протоколе **не используется**.

Дополнительно по коду: `GameWorld_serialize_state` (`0044d790`) пишет в блоб три `int64` из `Creature+0x10/+0x18/+0x20`; `Creature::deserializeState` (`0044be40`) читает их обратно. `vec3i64_toFloat` (`0042c4a0`) умножает на `1/65536`, то есть даёт **грубые единицы** (256 на блок), а не блоки. В `B_world.md` зафиксировано, что `0x1000000` (= `2^24`) соответствует одному блоку для позиций сущностей. Отсюда **рабочая гипотеза**: raw / `2^24` = блоки. Для проверенных сейвов это даёт компоненты 0/1 = `32 800.5` блока, компонент 2 = `0.601875`. `map_G0WORLD.db` содержит `reg` 509…515 и `tile` 32798…32802; компоненты 0/1 совпадают с горизонтальными ключами, компонент 2 — нет. Кандидат горизонтальной плоскости — **components 0×1** (инструмент `--plane xy`), но порядок x/z и семантика поля не доказаны: OQ-22 остаётся `PARTIAL`.

## 3. Инструменты (подготовлены, проверены на копиях)

| Инструмент | Назначение | Проверка |
|---|---|---|
| `docs/research/alpha2013/tools/alpha_char_save_probe.py` | read-only разбор копии `characters.db`: поля v11, сырая тройка позиции и интерпретации | запущен на `char_base.db`/`char_after.db` |
| `docs/research/alpha2013/tools/alpha_save_diff.py` | сравнение двух копий: изменённые диапазоны, **все три raw-дельты**, расстояния XY/XZ/YZ; `--plane xy / xz / yz` — явный выбор плоскости; `--duration`; `--expect-pos-change --min-blocks N`; `--self-test` | `--self-test` PASS; на паре сейвов 911 байт, 580 диапазонов, Δcomponent2 = −1 raw |
| `docs/research/alpha2013/tools/alpha_char_save_edit.py` | запись **только в новую копию** `characters.db`: `--pos-raw`, `--pos-blocks`, `--component-delta N D`; отказывается писать в оригинальную установку и поверх входного файла | проверен на временной копии: Δcomponent 0/1/2 = 10 блоков → 1 изменённый байт |
| `alpha_ctl/*.ps1` (локально, не в git) | скриншоты, ввод, проверка окна; используются как вспомогательные, не как доказательство | в финальной валидации ввод/foreground заблокированы средой (error 5) |

Команды (пример):

```powershell
python docs\research\alpha2013\tools\alpha_char_save_probe.py .scratch\shots\char_after.db
python docs\research\alpha2013\tools\alpha_save_diff.py .scratch\shots\char_base.db .scratch\shots\char_after.db
python docs\research\alpha2013\tools\alpha_save_diff.py --self-test
python docs\research\alpha2013\tools\alpha_save_diff.py <before.db> <after.db> --plane xy --duration 10 --expect-pos-change --min-blocks 50
python docs\research\alpha2013\tools\alpha_char_save_edit.py <copy-in.db> <copy-out.db> --component-delta 0 64
```

`--plane xy` означает **выбранную вызывающим** пару компонентов 0 и 1; это не доказательство, что горизонталь именно XY. До подтверждения осей скорость не считается установленной.

## 4. Протокол A — надёжное управление окном и подтверждение движения

Цель: исключить ложное «движение», как в прошлой сессии.

1. Скопировать установку (`robocopy`), сверить SHA-256 `Cube.exe` и `data*.db` с `SOURCE_REGISTER.md`; записать хеши копии.
2. Запустить игру **из копии**: `cmd /c start "" Cube.exe` (прямой `Start-Process` в этой среде зависал — известная особенность окружения, не игры).
3. Дождаться главного окна. Получить `MainWindowHandle` процесса `Cube`; если окно свёрнуто (`GetWindowRect` = `-32000,-32000`), вызвать `ShowWindow(SW_RESTORE)` и `SetForegroundWindow`.
4. **Проверить фокус**: `GetForegroundWindow() == handle`. Если нет — не отправлять ввод, повторить или остановить тест.
5. Войти в мир `G0WORLD` (seed 666666), выбрать ровный участок с двумя заметными ориентирами; не трогать мышь после входа (камера стартует с yaw 180°).
6. Снять `before.png` (весь экран или клиентская область), записать время.
7. Нажать `W` через `SendInput`/`keybd_event` со скан-кодом; удерживать **ровно 10.000 с** по `Stopwatch`; отпустить. Не использовать Shift/пробел/мышь.
8. Снять `after.png` через 0.5 с после отпускания. Сравнить **центральную область мира** (без HUD, часов и полос): если кадры совпадают, движение не подтверждено — тест недействителен, записать `INPUT_FAILED`, не переходить к §5.
9. Выйти в главное меню штатно (не Alt+F4), дождаться изменения `mtime` файла `Save\characters.db`; закрыть игру; скопировать `characters.db` в локальный evidence-каталог.
10. Повторить пп. 5–9 три раза в разных направлениях/на разных ровных участках.

**Критерий:** три действительных прогона, в каждом мир визуально изменился (pixel diff центра > порога), окно было в фокусе, ввод не потерян.

## 5. Протокол B — измерение позиции и скорости

1. Для каждого прогона выполнить `alpha_char_save_probe.py` и `alpha_save_diff.py` на паре «до/после».
2. Зафиксировать сырую тройку `before/after`, дельту raw и интерпретации (`/2^24`, `/65536`, `/2^32`).
3. Если тройка не изменилась — это **не** доказательство нулевой скорости: возможны (а) поле — точка спавна, (б) сохранение не успело, (в) движение не подтверждено. Перейти к протоколу C, не записывать скорость.
4. Если тройка изменилась: проверить, что компоненты выбранной плоскости в блоках лежат в `[0, 65536)` и что `component0/64` или `component1/64` попадает в диапазон `reg`-ключей `map_<world>.db`. Это проверка гипотезы `2^24`, а не доказательство.
5. Вычислить путь в **явно выбранной** плоскости (`--plane xy|xz|yz`); по умолчанию инструмент не выбирает плоскость и не выдаёт скорость. Если выбрана `xy`, это компоненты 0/1; если `xz` — 0/2; если `yz` — 1/2. `v = d / duration`.
6. Повторить 3 раза; записать `v_i`, среднее и стандартное отклонение.
7. **Погрешность:** таймер ±0.05 с (±0.5 %), квант позиции `1/2^24` блока (пренебрежимо), возможная кривизна пути/уклон/коллизии — основная систематическая ошибка. Если разброс `v_i` > 20 %, искать причину (стена, уклон, потеря фокуса), а не усреднять.
8. Сравнить с гипотезами: A — базовая скорость 20 блоков/с (путь ≈200 блоков за 10 с); B — 10 блоков/с (≈100 блоков). Учитывать, что 20 — множитель из кода, а не доказанные блоки/с.
9. Записать результат в `VALIDATION_CASES.md` (`VA-MOV-01`) и `R02_REPORT.md` с датой, seed, персонажем, уровнем, экипировкой и путём к локальным evidence-файлам (не в git).

**Критерий PASS для OQ-23:** три согласованных прогона, подтверждённое движение, известная единица позиции; иначе `NOT_VERIFIED`.

## 6. Протокол C — что это за поле: текущая позиция или спавн

Выполняется на **копии** сейва, без чтения памяти.

1. Взять `characters.db` из копии установки; сделать рабочую копию в `.scratch`.
2. Через `alpha_char_save_edit.py --pos-blocks` изменить только x, например `x+64` (один регион), оставив y/z; записать новый файл.
3. Положить изменённую копию в тестовую установку как `Save\characters.db` (предварительно сохранив исходную копию).
4. Запустить игру из копии, выбрать персонажа. Зафиксировать: где появился персонаж (скриншот, подпись региона, положение на карте).
   - Если персонаж появился в новой точке — поле используется при загрузке как позиция (как минимум spawn/load position).
   - Если в старой — поле не является позицией загрузки; искать другое поле/источник (карта, world DB).
5. Не выходя из мира, пройти 10 с (протокол A), выйти в меню, снова сравнить позицию.
   - Если поле обновилось на пройденный путь — это **текущая** позиция.
   - Если осталось на значении из п. 2 — это **точка спавна/респавна**, а текущая позиция хранится иначе.
6. Повторить с изменением z и, при необходимости, y, чтобы проверить порядок осей.
7. Записать вывод в OQ-22; при отрицательном результате — `PARTIAL/UNKNOWN`, не угадывать.

**Важно:** редактируется только копия; оригинальный `Save\characters.db` и установка не изменяются. Перед запуском сохранить исходную копию сейва, чтобы откатить эксперимент.

## 7. Протокол D — проверка системы координат без движения

Если протокол C невозможен, остаётся статическая проверка:

1. Взять `map_<world>.db` и ключи `reg<x>_<z>`/`tile<x>_<z>`; сопоставить с `x/64` из сейва.
2. Проверить, что `x/64` попадает в диапазон `reg`-ключей, а `x` — в диапазон `tile`-ключей (tile = блок).
3. Проверить альтернативы: `/65536` даёт 8.4 млн **грубых единиц**, а не блоков — для блоков нужно ещё `÷256`, что эквивалентно `/2^24`; `/2^32` даёт 128.1 блока — не совпадает с регионом 512. Гипотеза `/2^24` согласуется с обоими независимыми наборами ключей.
4. Зафиксировать: это **поддерживает** гипотезу, но не доказывает семантику поля (текущая/спавн). OQ-22 остаётся `PARTIAL` до протокола C.

## 8. Критерии доказательности

| Утверждение | Минимальное доказательство |
|---|---|
| «персонаж двигался» | подтверждённый фокус окна + pixel diff мира + три прогона |
| «позиция в сейве — текущая» | протокол C: загрузка из изменённой копии + обновление после движения |
| «скорость = X блоков/с» | три согласованных прогона, подтверждённое движение, известная единица |
| «единица = 2^24/блок» | совпадение с `map`-ключами и `0x1000000`; для полного PASS — протокол C |
| «поле +0x70 — цель» | **не доказано**; см. OQ-24 (`+0x70` — счётчик, не указатель) |
