# S05A-1 — пилот сборки одного персонажа и исследования анимаций (ЧЕРНОВИК ТЗ)

**Статус:** `DRAFT / NOT_AUTHORIZED` — подготовлен на основе [D48](../decisions/D48-s05a0-accepted-s05a1-draft.md); **НЕ НАЧИНАТЬ ВЫПОЛНЕНИЕ** без следующего решения продюсера.  
**Входной baseline:** `S05A-0 ACCEPTED`, [отчёт](../research/alpha2013/MODEL_CONVERSION_PILOT.md), конвертер [tools/alpha_models](../../tools/alpha_models/README.md).  
**Среда:** Unity 6000.3.27f2, изолированный проект; источник Alpha `D:\Games\Cube world` — **только чтение**.  
**Тема:** D31/D32/D35 и D46 — сначала конвертация и проверка анимаций, потом решение о собственных/переработанных ассетах.

## Цель и границы

Проверить, как собрать **один цельный технический гуманоидный персонаж** в Unity из нескольких исходных воксельных частей и как реализуются его ключевые движения. Это не запуск производства полного контента и не создание финального персонажа для релиза.

## A. Исследование схемы сборки

1. Не повторять S05A-0. Использовать декодер и конвертер, уже прошедшие пофасетные тесты. Сначала статически исследовать известные части (`human-head-m01`, `human-hair-m01`, варианты `body*` и другие **только при необходимости** для одного образца).
2. Определить из данных/кода оригинала, какие части входят в одного персонажа и как выбираются версии частей. Указать конкретные основания каждого соответствия; неизвестное маркировать `UNKNOWN` или `PARTIAL`.
3. Изучить в исходном коде/статических артефактах механизмы размеров, scale, offsets, узлов вращения, осей и привязки рук, броневых элементов и оружия; не объявлять приблизительную раскладку эталоном Alpha.
4. Для чистых R/G/B маркерных вокселей отделить **визуальную геометрию** от возможных anchor/marker-данных, сохранить координаты и цвет в метаданных; подтвердить семантику каждой категории по коду, если возможно; не удалять реальные красные/зелёные/синие декоративные воксели по слепому правилу.
5. Проверить tint-поведение на примере волос: различать базовый цвет и цветовую маску; применять только обоснованную логику, не домысливать семантику.

## B. Unity-пилот одного персонажа

1. Собрать **один** humanoid из допустимых технических копий частей в изолированном Unity-проекте.
2. Использовать иерархию `root → body → head/hair → arms/hands/legs` либо другую структуру, если подтверждена исходными данными. Конкретную схему пояснить в отчёте.
3. Проверить pivot/rotation/scale/offsets и ориентацию X (учесть найденное отражение OBJ `x'=-x`; предпочтительно прямой Unity Mesh там, где это устраняет потери). Доказать корректность **не только bounds**, но и локального положения частей, отсутствия инверсии и связи с узлами.
4. Отдельно проверить одно временное крепление оружия в кисти/сокете, не реализуя правила боя и экипировки повторно.
5. Снять сравнительные изображения спереди/сбоку/3⁄4 и простую демонстрацию иерархии. Все изображения/оригинальные ассеты остаются локально.
6. Если оригинальные offsets/аниматоры не восстановлены, разрешена **чётко маркированная техническая proxy-сборка** для проверки Unity, но статус соответствия Alpha должен оставаться `PARTIAL`.

## C. Исследование и анимационный пилот

1. Статически определить, где находятся фактические анимационные данные/процедуры в Alpha; отдельно проверить гипотезу процедурных трансформаций частей и механизм keyframes. Не утверждать, что «анимаций нет» только по отсутствию `.anim`.
2. Построить таблицу `state → parts/joints/transforms/timing → evidence/confidence` для **одного** простого цикла (предпочтительно idle или walk, выбрать по реальным данным).
3. Попытаться воспроизвести **один** проверяемый исходный цикл на собранной модели в Unity **только если восстановлено достаточно данных**; иначе зафиксировать точный блокер, не выдавать approximation за оригинал.
4. После проверки совместимости сделать **один собственный** тестовый idle/walk-клип на той же технической модели для подтверждения рабочего конвейера по D32. Это не финальная художественная анимация; не делать десятки клипов.
5. Тестировать деформацию/вращение частей, сломанные точки крепления, движение оружия, scale, отзеркаливание и повторяемость клипа в Editor/PlayMode (при необходимости).

## D. Проверки и отчёт

- Сохранить существующие Python 42/42 и Unity pilot 19/19 тестов, добавить тесты маркеров/геометрии/сборки/ориентации и smoke PlayMode анимации по реальному охвату.
- При ошибках в конвертации/сборке фиксировать `FAIL` с диагностикой, не подгонять исходные данные.
- Не писать в репозиторий оригинальные `.cub`, базы, OBJ/MTL, импортированные меши, видеозаписи/изображения с защищёнными ассетами; не запускать Alpha/Server.exe без отдельного разрешения; не устанавливать ПО без согласования.
- Не менять production Unity, S04 и боевые формулы, не запускать массовую конвертацию 2857 моделей и S05B.
- При будущем исполнении отчёт `docs/research/alpha2013/CHARACTER_ASSEMBLY_ANIMATION_PILOT.md` должен включать перечень частей, проверенные transforms и pivots, статусы исходных механизмов и нового клипа, ошибки, ограничения, воспроизводимые команды и результаты Unity.
- По D35 всякая **переработанная** художественная модель требует личного утверждения продюсера; пилотный технический сбор не означает художественную приёмку.
- При авторизации исполнения: новая ветка `stage/s05a1-character-animation` от последнего принятого HEAD S05A-0; не делать merge в main. После исполнения только `READY_FOR_REVIEW` — не `ACCEPTED`.

## Критерии будущей приёмки

1. Один технический персонаж собирается из проверенных частей и отображается в Unity либо задокументирован точный блокер.
2. Маркеры/тинт/offsets/масштаб и handedness разделены на `VERIFIED`/`PARTIAL`/`UNKNOWN`.
3. Один исходный цикл **либо** воспроизведён по подтверждённым данным, **либо** дан доказанный блокер; один собственный тестовый цикл реально запускается на той же модели, если технически возможно.
4. Результаты тестов и ограничений понятны, чужие ресурсы не публикуются.
