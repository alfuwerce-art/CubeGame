## 1. Где живёт миссия

Миссия — часть записи landmark-колонки (0x68 байт, 8×8 на регион, `region+0x14018`, уже перенесена как `LandmarkColumn` до `+0x28`).
Блок миссии — `+0x2C…+0x53` (38 байт, тот же блок, что пишется в `world_*.db` под ключом `mission<x>_<z>`, читатель `deserialize_struct_0x28` `0x44CB50`).

| Смещение | Поле | Кто пишет |
|---|---|---|
| `+0x30` | `rand()` — seed/вариант миссии | `0x5D8750`, последний вызов `rand()` |
| `+0x34` | тип миссии (0 = нет) | `0x5D8750` |
| `+0x38` | вид цели (kind) | `0x5D8750` по типу |
| `+0x3C` | максимальный уровень игроков в момент генерации | `0x5D8750` |
| `+0x40` | байт = `+0x28` колонки (класс уровня) | `0x5D8750` |
| `+0x41` | состояние: 0 спит, 1 активна, 2 выполнена | `0x5D8750` (0), `0x60CCA6` (1), `0x596517` (2) |
| `+0x44` | прогресс | `0x596501` |

## 2. Проход региона — `0x5D9AD0`

Имя в реконструкции `World_generateTreeRoot` ошибочно. Вызывается из кадрового обновления (`GameController_updateSubsystems` `0x60C510`), когда регион под героем имеет `+0x15A18 == 0`. Один раз на регион.

1. `minLevel`/`maxLevel` — по всем игрокам (`entity+0x60 == 0`), уровень `entity+0x190`.
2. Для каждой из 64 колонок, принадлежащих региону (`World_findNearestObjectRegion2` = этот регион):
   - если `+0x34 != 0` — сброс типа и прогресса, уведомление;
   - если `+0x54 != 0` — сброс `+0x54/+0x58/+0x5C`;
   - **колонка без ориентира (`+0x18 == 0`)** — назначить босса:
     диапазон уровня по климатической клетке региона (`0x5D7A70`, `Field3=+0xC`, `Field4=+0x10`, `rare=+8`):
     `[1,10]`; `Field4 < 0.2` → `[10,20]`; `Field3 < 0.2 ∧ Field4 > 0.8` → `[15,25]`; `Field3 > 0.8 ∧ Field4 > 0.8` → `[10,20]`; `rare` → `[20,30]` (проверки идут в этом порядке, последняя выигрывает);
     `+0x58 = rand() % (hi − lo + 1) + lo`; `+0x54 = 0x5F7820(rx, rz, +0x58)`;
     зона босса: `+0x64 = colZ·8 + 2 + rand()%4`, `+0x60 = colX·8 + 2 + rand()%4` (порядок вызовов `rand`: сначала Z, потом X);
     колонка добавляется в список P (plain).
   - **колонка-ориентир** (`+0x18 ∉ {0, 10}`, уровень `+0x24 ≤ maxLevel + 2`, деревня `+0x18 == 1` — только при `rand() % 50 == 0`):
     `+0x24 ≥ maxLevel − 2` → список A, иначе список B.
3. Две миссии из ориентиров: на каждой итерации `rand() % 6 == 0 ∧ B ≠ ∅` → случайная из B (`rand() % |B|`, удалить); иначе A, если не пуст; иначе B.
4. Две миссии из списка P (`rand() % |P|`, удалить).
5. Для каждой из 64×64 зон региона — `0x5D9460` (см. §4). Затем `+0x15A18 = 1`.

## 3. Генератор миссии колонки — `0x5D8750`

Имя `World_generateVegetationCluster` ошибочно.

1. Удаляет существ с флагом `0x2000` (`entity+0x7E`), стоящих в этой колонке; очищает спавны её зон.
2. Обнуляет `+0x34`, `+0x41`, `+0x44`, `+0x48`. Колонка `+0x18 == 10` — выход.
3. Кандидаты типа по `+0x18`:

| landmark `+0x18` | кандидаты | смысл |
|---|---|---|
| 0 | `[1]` | monster (босс колонки) |
| 1 Village | `[9, 3, 4]` | villageinvasion, villagemonster, villagerareboss |
| 0xE | `[5]` | dungeon |
| прочие (кроме 10) | `[5]` | dungeon |

   Тип = `list[rand() % n]` (беззнаковое деление; `rand()` вызывается и при `n = 1`).
4. `minLevel`/`maxLevel` игроков (повторно).
5. Цель и требование по типу:

| Тип | `+0x38` (вид цели) | `+0x48` | `+0x4C/+0x50` |
|---|---|---|---|
| 1 monster | `= +0x54` | 0 | `= +0x60/+0x64` |
| 7 invasion | `0x5F7400(cx, cz, maxLevel)` | `rand()%8 + 25` | −1 |
| 10 caveinvasion | `0x5F7400` | `rand()%5 + 10` | −1 |
| 11 riverinvasion | `0x5F7400` | `rand()%5 + 15` | −1 |
| 3 villagemonster | `0x5F7820(cx, cz, maxLevel)` | 0 | лучшая зона |
| 2, 4 | `0x5F56C0(зона, высота +0x14, 0)` | 0 | лучшая зона |
| 12 gang | `0x5F56C0(…, 1)` | `rand()%5 + 6` | лучшая зона |
| 13 gangboss | `0x5F56C0(…, 1)` | 0 | лучшая зона |
| прочие (5, 8, 9) | `0x5F7400` | `rand()%10 + 10` | лучшая зона |

   «Лучшая зона»: по 8×8 зонам колонки вес `w = (1 − d²)²` при `1 − d² > 0`, где `d²` — `vec3_distanceSquared` между центром колонки и центром зоны (16.16); для типов 12/13 вес ×2 у зон с нечётной суммой индексов. Список сортируется `introsort_float`, берётся первый элемент. `d²` — `0x5F8E10` с колонкой в `ecx` (тот же искажённый шумом `Distance2`, что у рельефа); для 12/13 множитель `0x745E10 = 2.0`. Сортировка по убыванию (`insertion_sort_float` `0x5C1060`: `cur > first` → в начало), берётся зона с наибольшим весом. Пустой список (`0x5D91BE…0x5D91D3`) → выход **без** записи типа и без `rand()` хвоста. Декомпиляция показывает ложный переход мимо записи типа для непустого списка — байты `0x5D92FE → 0x5D9319` его опровергают.
   По §2 типы 2, 7, 8, 10, 11, 12, 13 генератором **не выбираются**: их ветки есть, но списки кандидатов их не содержат.
6. `+0x30 = rand()`, `+0x40 = +0x28`, `+0x3C = maxLevel`, `+0x34 = тип`; запись добавляется в список уведомлений.

### Виды целей

- `0x5F7820` (имя `dtor_listBuffer` ошибочно) — **вид босса** по климату и уровню: `[Field4 ≤ 0.2 ? 0x72 : 0x6C, Field4 ≤ 0.2 ? 0x74 : 0x77]`; `level > 10` + `0x73`; `> 20` + `0x75`; `> 50` + (`Field4 < 0.2` ? `0x71` : rare ? `0x70` : `0x6F`) и `0x6D`; `> 70` + `0x6E`; результат `list[rand() % n]`. Для отсутствующей клетки — `0x6C`. Все виды, кроме `0x6E/0x6F/0x70/0x71`, входят в `creature_isBossType` `0x4445D0`.
- `0x5F7400` (имя `dtor_geometryBuffer` ошибочно) — вид вторжения: `[0x30, 0x33, 0x60, 0x50, 0x4C, 0x28, 0x2B, 0x2D, 0x34][rand() % 9]`.
- `0x5F56C0` — уже перенесённый селектор вида дикого существа (`AlphaCreatureKindSelector`, `EMULATED_ALPHA_CODE`).

## 4. Постановка босса — `0x5D9460`

Имя `World_generateTreeRecursive` ошибочно. Для каждой зоны региона:
1. Удаляет прежние спавны зоны.
2. Если у колонки зоны `+0x54 != 0` и зона = (`+0x60`, `+0x64`) — создаёт `cube::Spawn`: роль `+0x28 = 1`, флаг `0x2000`, **только если тип миссии колонки = 1**; позиция — центр зоны, высота — `world_getChunkCell256`; вид `+0x54`, уровень `+0x58`, качество `+0x5C`; два предмета снаряжения (`0x…buildDecalMesh2/…buildDecalMesh`, редкость `q+1`, бонусы 1/20 и 1/100, затем 1/100 и 1/1000, предел 4); поведение `Sequential[Combat(20.0), RandomWalk]`; внешность и поведение по виду.
3. Иначе — обычная постановка зоны `World_buildStructureMesh(zone, 0)` (имя не проверено).

Флаг `0x2000` во всём `.text` выставляется **только** в `0x5D9730` (скан всех `or/mov` в `+0x7A/+0x7E`). Значит цели с флагом есть только у миссии типа 1. Типы 3, 4, 9 в одиночной Alpha не завершаются; тип 5 завершается убийством хозяина данжа (`+0x1D38`).

## 5. Активация — `0x60CC3D…0x60CCA6`

Каждый кадр: колонка под героем (`0x487DA0`, координаты зоны `>> 3`); если `+0x34 != 0`, `+0x41 == 0` и `0x5FA4C0(x, z) > 0.0` (`0x745D84`) → `+0x41 = 1`, уведомление. `0x5FA4C0` = `w = 1 − 0x5F8E10(x, z)`, `w > 0 ? w² : 0` — то есть герой внутри территории ориентира колонки; у колонки без ориентира радиус 0 и вес 1 в любой её точке.

## 6. Зачёт — `0x59642A…0x596517`

В обработчике смерти существа:
1. Колонка по зоне спавна существа (`+0x1B0/+0x1B4 >> 3`); выход, если `+0x41 == 2`.
2. Существо должно иметь флаг `0x2000`, **или** тип миссии = 5 и существо — «хозяин данжа» (`+0x1D38 != 0`).
3. Среди атакующих существа (`+0x13A4`) должен быть игрок (`+0x60 == 0`).
4. Таблица `0x596C84`/`0x596C78` по `тип − 1`: типы 1–5 и 13 → сразу `+0x41 = 2`; 7–12 → `+0x44++`, `+0x41 = 1`, при `+0x44 ≥ +0x48` → `+0x41 = 2`; 6 → ничего.
5. При завершении — `missioncomplete.wav` (`0x1E`, F4) и награда `0x595A60` (перенесена в P5).

## P7-B этапы 2–3 — коридоры, вход, поворот, палитра, колонны (14 ноября 2026)

`AlphaDungeonGenerator.GenerateCells` (до `0x5CEA6B`, перед записью объёма в зону):

- **Связи комнат** — список пар слотов в порядке Alpha, взят из исполнения (порядок в декомпиляции другой): схемы `flag=1` (5), 0 (8), 1 (8), 2 (9), подтип 2 (10), подтипы 4/5 (10). Коридор строится, только если обе комнаты есть.
- **Коридор `0x5C52A0`** — по оси перекрытия комнат (X, затем Y; иначе нет): основная линия на `m = B + sB/2` (зажато в A) и с вероятностью ½ линии на `m−1` и `m+1`. В Y-ветке Alpha сравнивает `m` с X-границами (`0x5C55BF`, `0x5C5682`) — перенесено как есть.
- **Линия `0x5EF6D0`** — `n = max(|dx|,|dy|,|dz|)`, шаги с отбрасыванием дроби, тип 3; смена высоты открывает соседнюю клетку и ставит ступень `|1`.
- **Вход** — тип 4 перед комнатой A первой связи (`7i+2+A, 7j+1+B, 7k+3+C`).
- **Поворот** `rand()&3`, **зеркало** `(rand()&1)==0`; адресация `0x5FA3C0` = `AlphaDungeonVolume.Offset`.
- **Палитра** — цвет стен `3×(rand()%50+20)`; база `rand()%50` (подтип 3: `+100`); две тройки `rand()%50+50+база`; подтипы 1/2 и 4 перезаписывают их своими `rand()`, подтип 5 — константы; коэффициент 0.005 / 0.0015 / 0.0025.
- **Колонны** (подтипы 0–3) — сверху вниз до первой непустой клетки (не вход), над ней `h` клеток типа 2: `h=1`, при `rand()%6==0` (кроме подтипа 2) `h=rand()%3+2`.

Проверка: 27 исполненных случаев, все схемы комнат — связи, объём 22³ (SHA-256), поворот, зеркало, палитра, коэффициент и CRT до записи в зону совпадают (`CorridorsTurnAndPaletteMatchTheExecutedAlphaGenerator`, эталон `alpha_dungeon_cells_oracle_666666.json`). Python-порты, которыми проверялся каждый шаг: `tools/alpha_models/world/dungeon_*_port.py`.

Дальше (этап 4): запись объёма в зону с `0x5CEA6B` — воксели стен/пола/мебели и проход по клеткам, в котором создаются монстры, хозяин (клетка `|4`) и сундуки; `rand()` там общий для вокселей и существ, поэтому этап переносится целиком.
