# S00-R01 — спецификация генерации и перемещения (проверяемое поведение и неизвестное)

**Проект:** CubeGame (рабочее название).
**Этап:** S00-R01 (D40, ТЗ `docs/stages/S00_STATIC_R01.md`, п. 6).
**Назначение:** зафиксировать (а) константы и модель координат Alpha настолько, насколько их можно доказать статически, (б) что именно из этого принимает пилот S01-PILOT, (в) что остаётся неизвестным и требует игрового теста.

Метки: `BINARY_STATIC`, `RECONSTRUCTED_SOURCE`, `SAVE_OBSERVED`, `ALPHA_DIRECT`, `UNKNOWN`, `PLACEHOLDER_NOT_ALPHA`.

---

## 1. Модель координат (по Reversal, `RECONSTRUCTED_SOURCE`)

| Константа | Значение | Как получено |
|---|---|---|
| Единиц на блок | **65 536** (`0x10000`) | `world_getColumnAtFixedPos`: позиция в fixed-point 16.16 делится на `0x10000` → индекс блока |
| Предел мира по каждой оси | **65 536 блоков** (`0x10000`) | `world_getRegionCell64`: координата валидна только при `0 <= c < 0x10000` |
| Шаг «ячейки региона» | **64 блока** (`с >> 6`) | `world_getRegionCell64`: `c >> 6`, локальный индекс `(c & 0x3F)`, всего 4096 ячеек |
| Шаг «зоны» | **2048 блоков** (`>> 11`) | `WorldInfo_sampleTerrainHeight` вызывает `GameController_getVoxelColumn8((x + …) >> 11, (y + …) >> 11)` |
| Плитка зоны (`ZoneTile`) | **32 блока** | `Zone::constructTileGrid`: 4096 плиток `0x34` Б + 64 объекта `0x68` Б = `0x35A00`; 4096 = 64×64 → 2048 / 64 = 32 блока |
| Сетка поля зоны (`Field`) | 65 536 записей × 32 Б | `Zone::ctor_0`: `operator_new(0x200004)`, 0x10000 элементов по 0x20 |
| Сетка `Region` | 64 × 64 = 4096 ячеек по 4 Б | `Region::ctor_0` (массив с шагом `0x10`, цикл 64×64), чтение `+0x10018 + (lx*64 + ly)*4` |

### 1.1. Достоверность иерархии

Твёрдо установлено: блок = `2^16` единиц; мир ограничен `65 536` блоками по оси; присутствуют шаги 64 и 2048 блока; `Zone` = 64×64 плиток по 32 блока; `Region` = 64×64 ячеек.

Не установлено (`UNKNOWN`): точное вложение `World → Region → Chunk → Zone → ZoneTile`. В деградированном псевдокоде `Region`-объект индексируется 64×64, но вызывающая функция проверяет координату до `0x10000` и делит её на 64, то есть обращается к сетке до 1024×1024. Две равноправные гипотезы:

- **H1:** `Region` покрывает 4096 блоков (64 ячейки × 64 блока), мировое пространство — 16×16 регионов. Тогда сетка 1024×1024 — это глобальная карта чанков, а не `Region`.
- **H2:** `Region` — объект уровня всего мира (1024×1024 ячеек по 64 блока), а 64×64 в конструкторе — вложенная сетка более низкого уровня.

Ни одна из гипотез не влияет на пилот: он использует только блок, `ZoneTile`=32 блока и seed-детерминизм.

### 1.2. Форма функции высот (`RECONSTRUCTED_SOURCE`, уверенность низкая/средняя)

Реконструкция `WorldInfo_sampleTerrainHeight` в терминах поведения (без переноса кода):

1. два 2D-шума Перлина: `n1` на частоте ≈ 0.01 от координаты блока со смещением мира, `n2` на частоте ≈ 0.001 (координата × 0.001);
2. `h = |n1 * 0.1 + n2|`;
3. модуляция амплитуды третьим шумом `n3` (частота 0.001): `h *= 0.8 + 0.1 * (n3 + 1)`;
4. добавка от ближайшего объекта (`World_findNearestObject`) и от «дорожных/структурных» ячеек — выпуклость с затуханием по квадрату расстояния;
5. поверх всего добавляется базовая высота ячейки 256 блоков (`world_getChunkCell256`, поле `+0xC`).

Чего в этой форме **нет**: сида в явном виде, распределения биомов, уровня моря, границ зон. Всё это `UNKNOWN` и в пилот не переносится.

## 2. Что пилот S01-PILOT берёт из этой спецификации

| Параметр | Решение пилота | Статус |
|---|---|---|
| Размер блока | 1 единица Unity = 1 блок | принято как рабочая гипотеза (перенос константы `2^16` не нужен: fixed-point — деталь реализации Alpha) |
| Размер чанка | **32 × 32 блока** по X/Z, высота 0…255 | обосновано `ZoneTile`=32 (`RECONSTRUCTED_SOURCE`) |
| Размер видимой области | 8 × 8 чанков (256 × 256 блоков) | выбор пилота для измеримой производительности |
| Координаты | целочисленные блочные + seed (uint) | следует из §1 |
| Формула высот | **временная**: value-noise/fBm на целочисленном хеше `(seed, x, z)` | `PLACEHOLDER_NOT_ALPHA` |
| Палитра/текстуры | плоские цвета по высоте, без ассетов Alpha | `PLACEHOLDER_NOT_ALPHA` |
| Меши | один объединённый меш на чанк (границы только на открытых сторонах) | требование ТЗ P1.2 |

Пилот **не** воспроизводит формулу высот Alpha. Это прямо разрешено ТЗ S00-R01 п. 6 («временный детерминированный алгоритм с пометкой `PLACEHOLDER_NOT_ALPHA`»).

## 3. Приёмочные случаи для пилота (входы/выходы/допуски)

Формат: `id | вход | действие | ожидаемый результат | допуск`.

| ID | Вход | Действие | Ожидание | Допуск |
|---|---|---|---|---|
| `TC-GEN-01` | seed = 666666, область (0,0)…(255,255) | генерация дважды в одном процессе | хеш вершин и индексов меша совпадает побайтово | 0 (побитово) |
| `TC-GEN-02` | seed = 666666 vs 666667 | генерация | хеши различаются; ≥ 90 % вершин по высоте отличаются хотя бы на 1 блок | расхождение ≥ 90 % |
| `TC-GEN-03` | seed = 666666, чанки (0,0) и (1,0) | сравнение общих граней | высоты на общей границе совпадают во всех 32 столбцах | 0 (точное равенство) |
| `TC-GEN-04` | seed = 666666, чанк (0,0) | повторная генерация после перезагрузки сцены | хеш совпадает с результатом первого запуска | 0 (побитово) |
| `TC-GEN-05` | seed = 666666 | замер генерации области 8×8 чанков | время генерации зафиксировано в отчёте | измерение, не требование |
| `TC-MOVE-01` | старт (16, h, 16) | удержание «вперёд» 2 с | игрок сместился по X/Z, остаётся на поверхности (нет провала сквозь меш) | вертикальное отклонение ≤ 0.1 блока |
| `TC-MOVE-02` | склон 30° | движение вверх по склону | игрок поднимается, не застревает и не «прыгает» | без телепортации > 0.5 блока за кадр |
| `TC-CAM-01` | мышь по X | вращение | камера вращается вокруг игрока, дистанция постоянна | дистанция ±0.05 |
| `TC-CAM-02` | мышь по Y вверх/вниз до предела | наклон | наклон ограничен, камера не переворачивается | предел ±80° (значение пилота) |
| `TC-CAM-03` | игрок у стены | камера | камера не проходит сквозь геометрию (или честно зафиксировано, что проходит) | результат фиксируется как есть |
| `TC-HUD-01` | любой запуск | — | отображаются seed, координаты игрока, FPS | наличие всех трёх полей |

`TC-CAM-03` сформулирован как «зафиксировать фактическое поведение»: алгоритм обхода препятствий камеры в Alpha не исследован (`UNKNOWN`), придумывать его как «как в Alpha» нельзя.

## 4. Перемещение и камера: чего мы пока не знаем

В R01 **не выполнялся** запуск клиента (ТЗ R01 — статическая партия; запуск уже подтверждён в S00-G0). Поэтому по движению и камере честный статус — `UNKNOWN`:

| Вопрос | Статус | Как проверять |
|---|---|---|
| Скорость бега/ходьбы в блоках в секунду | `UNKNOWN` | замер по скриншотам/видео с известной геометрией либо прямой замер в клиенте |
| Есть ли отдельная ходьба/бег, ускорение, инерция | `UNKNOWN` | игровой тест S00-04 |
| Дистанция и высота камеры третьего лица, FOV | `UNKNOWN` | игровой тест S00-01 |
| Чувствительность мыши, инверсия, ограничения наклона | `UNKNOWN` | игровой тест S00-01 |
| Прыжок, лазание, плавание, дельтаплан, лодка | `UNKNOWN` (S00-04) | игровой тест |
| Коллизия с воксельной геометрией (размер капсулы, шаг вверх) | `UNKNOWN` | игровой тест |

До появления этих данных все числовые параметры пилота помечаются `PLACEHOLDER_NOT_ALPHA` и подлежат замене после S00-01/S00-04. Продюсер утверждает значения пилота отдельно.

## 5. Что должен уметь пилот, чтобы считаться проверенным (сводка)

1. Детерминизм: `TC-GEN-01`…`TC-GEN-04` — автоматические EditMode-тесты.
2. Играбельность: `TC-MOVE-01/02`, `TC-CAM-01/02`, `TC-HUD-01` — ручной прогон с записью результата.
3. Производительность: `TC-GEN-05` + FPS/время кадра, измеренные, не выдуманные.
4. Отчёт `docs/stages/S01_PILOT_REPORT.md` с фактическими PASS/FAIL/NOT_RUN.
