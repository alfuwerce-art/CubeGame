# Извлечение поз Alpha 2013 из машинного кода (`Creature_drawModel`)

**Задача:** `S05A2-D58-A1` по [D57](../../decisions/D57-continuous-animation-transfer-authorization.md) и [D58](../../decisions/D58-animation-research-autonomy.md).
**Статус исполнителя:** `PARTIAL` — позы как данные извлечены и воспроизводимы, **привязка каналов к частям тела не доказана**.
**Среда:** локальная копия Alpha `.scratch/alphatest2` (`Cube.exe`, SHA256 `84A7A132A84D4282338E7EA45A1940D32066D64E39CBAFED8F2418D5A6DC30BF`), реконструкция `.scratch/CubeWorld-Reversal`, Python 3.13.
**Правовая граница:** обрабатывается только локальная копия; в Git попадают собственный код и текст, без байтов игры, кадров и матриц.

---

## 1. В чём была настоящая проблема

Прошлая сессия ([ANIMATION_EXTRACTION_RESEARCH.md](ANIMATION_EXTRACTION_RESEARCH.md) §3) зафиксировала: «таблицы состояние → набор углов нет, переменные не локализованы». Причина оказалась не в отсутствии таблицы, а в **дефекте декомпиляции**.

В `Creature_drawModel` каждая запись позы идёт через крошечный аксессор:

```c
/* Global::arrayElem_stride4 @ 00428970 */
int arrayElem_stride4(int index) { return self + index * 4; }      // self — в ECX
```

Ghidra не восстановила `this`-регистр, поэтому в псевдокоде остаётся:

```c
puVar10 = (undefined4 *)arrayElem_stride4(0);
*puVar10 = 0xc2c80000;            /* −100.0f, но КУДА записано — не видно */
```

Без базы нельзя сказать, в какой из ~240 стековых переменных ушёл угол. Именно это, а не отсутствие данных, блокировало чтение поз.

## 2. Метод: восстановить базу из байтов, а не угадывать

MSVC 2012 компилирует такую запись в устойчивую форму:

```
6A ib            push <компонента 0|1|2>
8D 8C 24 id      lea  ecx, [esp+disp32]     ; база (адрес стекового vec3)
E8 rel32         call arrayElem_stride4
C7 00 id         mov  dword ptr [eax], <float imm>   ; значение (может быть отложено)
```

Инструмент читает `Cube.exe` (только чтение) и восстанавливает тройку `(слот, компонента, значение)` для каждого вызова. Ни отладчик, ни внедрение в процесс, ни установка ПО не использовались: всё сделано по файлу и по реконструкции, которая уже была локально.

Проверки, встроенные в инструмент (все выполняются автоматически, `POSE_TABLE_RESULT=PASS`):

| Проверка | Как проверяется | Результат |
|---|---|---|
| Размер кадра | пролог `push ebp / mov ebp,esp / and esp,-8 / mov eax,0x1730 / call __chkstk` | **0x1730** |
| Смещение `esp → ebp` | перебор двух вариантов (`0` и `4` из-за `and esp,-8`), выбирается тот, при котором имена слотов совпадают с декомпиляцией | **bias = 0**, совпадение **1.000** |
| Что запись действительно в позу | каждый слот переводится в имя декомпилятора `local_XXXX` и сверяется с текстом `Creature_drawModel` | **522 / 522** записей попали в существующие имена |
| Что значения не выдуманы | статические значения сверяются с константами соответствующего `case` в декомпиляции | **71 / 90** (79 %) |
| Таблица состояний | таблица переходов `jmp [eax*4+disp32]` @ `0x413AF6` → `.rdata` `0x423D4C` | **73 состояния**, 68 уникальных блоков |

Оставшиеся 19 из 90 статических значений — константы, которые компилятор пишет через `movss` из пула констант либо выносит за пределы блока; они помечены как неподтверждённые, а не подставлены по догадке.

## 3. Что теперь доказано про анимационную систему Alpha

1. **Анимация — это код, а не ассеты.** В `Creature_drawModel` (0x4128F0) есть `switch` по целочисленному состоянию (`draw-state + 2`) на **73 состояния**; таблица переходов лежит по `0x423D4C`, диспетчер — по `0x413AF6`. Состояния с одинаковым адресом блока — намеренные fallthrough-дубликаты.
2. **Поза задаётся покомпонентно** в стековые `vec3` (по 3 компоненты), значения — углы в градусах (диапазон −250…+90 в восстановленных константах) и позиционные добавки.
3. **Время — миллисекунды** (`self[1]`), фазы атаки берутся из `combat_getAttackWindup` / `combat_getAttackTiming`; это те же функции, чьи тайминги уже перенесены в S05A-2 как `RECONSTRUCTED_FROM_EVIDENCE`.
4. **Есть два наблюдаемых момента на одном и том же канале.** Состояние 1 (атака с 500 мс замаха), канал `local_15fc`:

   | Момент | Условие | Значение канала | Адрес записи |
   |---|---|---|---|
   | замах | `t < 500` (ветка медленного замаха) | **−100.0°** | `0x41763E` |
   | восстановление | `t ≥ 500` и `t < combat_getAttackTiming()` | **−60.0°**, затем формула `(1 − f)·(−60)` при `f = clamp((t−500)/500·2)` | `0x4179B1` (константа) + расчёт в `0x4179xx` |
   | ветка руны | `weapon_isSpecialRune()` | **−250.0°** | `0x417A58` |

   То есть это не «угаданная» поза, а **формула движения** одного канала с двумя и более различными моментами, снятая с конкретных адресов.

   Оговорка о точности: адреса записей подтверждены байтами, а отнесение их к веткам «замах»/«восстановление» выведено из тела `case 1` в декомпиляции (там же стоят константы −100 и −60) и из порядка блоков. Отдельно проверено, что обе записи принадлежат одному и тому же блоку состояния 1 (`0x4174A0..0x417AB1`) и одному и тому же слоту `local_15fc`.

5. **Каналы образуют непрерывный блок с шагом 12 байт.** Все записи позы попадают в девять соседних слотов `local_15fc, 15f0, 15e4, 15d8, 15cc, 15c0, 15b4, 15a8, 159c` — ровно 12 байт между ними, то есть по три `float` на канал: `(rx, ry, rz)` в градусах. Это же число каналов, что и «10 float» в `render_uploadBoneMatrices`, и оно согласуется с набором костей человекоподобного существа; **но это гипотеза о костях, а не доказательство** (§4).
6. **Структура кода одинакова для 73 состояний** — значит конвейер применим ко всем состояниям, а не к одной атаке.

## 4. Что НЕ доказано (и почему это честный `PARTIAL`)

Каналы известны только как стековые слоты (`local_15fc`, `local_15e4`, `local_15c0`, …). **Соответствие «слот → часть тела» не установлено.** Проверенные причины:

| Гипотеза привязки | Проверка | Итог |
|---|---|---|
| Имена костей в бинарнике | поиск строк `"body"`, `"head"`, `"leg"`, `"arm"` в реконструкции | строк нет — скелет неявный |
| Таблица костей в `.rdata` | поиск ссылок `DAT_*` внутри `Creature_drawModel` | ссылок на таблицу нет |
| Матрицы костей на GPU | `render_uploadBoneMatrices` вызывается только в двух местах (квест-HUD, эффекты), из `drawModel` — нет | скиннинга по этому пути не видно; части рисуются жёсткими матрицами |
| Runtime-память | позы собираются в стековом кадре функции `drawModel` и не сохраняются между кадрами | чтение памяти процесса бесполезно без перехвата вызова |
| Графическая трасса | нужен apitrace/отладчик (в D55 разрешены, но не установлены) | не проверено в этой сессии |

Полезный побочный вывод: раз части рисуются жёсткими матрицами, привязка каналов к частям в принципе возможна по коду отрисовки, но участок отрисовки берёт углы из полей существа (`+0x10c…+0x114`, `+0xc0`), а не из найденных слотов, — это следующий участок, который нужно проследить.

## 5. Как это превращается в координаты Unity

Alpha собирает преобразование части в порядке (см. `0x4128F0`, блок `mat4_translate`/`mat4_rotateZ/Y/X`, строки 5985–5996 реконструкции):

```
M_alpha = T(x, y, z) · Rz(rz) · Ry(ry) · Rx(rx) · S
```

**Не переводить это в `Quaternion.Euler(x, y, z)` напрямую:** Unity собирает поворот в порядке ZXY (`Ry·Rx·Rz`), то есть другой порядок умножения. Правильный путь — собрать матрицу в порядке Alpha и перевести её в базис Unity одной заменой базиса:

```
S_basis = [[1,0,0],[0,0,1],[0,1,0]]        // (x, y, z)_alpha → (x, z, y)_unity, det = −1
M_unity = S_basis · M_alpha · S_basis⁻¹
localRotation = M_unity.rotation            // кватернион извлекается из матрицы
localPosition = M_unity.GetColumn(3)
```

Такой порядок сохраняет последовательность поворотов Alpha, а не подменяет её удобным для Unity. Выбор именно `(x, z, y)` — гипотеза о базисе (Z-up справа → Y-up слева); она **должна быть подтверждена визуально** на первом же сравнении кадров, поэтому ось-замена вынесена в один множитель, а не размазана по коду.

Именно под этот контракт сделан Unity-адаптер (`CharacterPilotPoseAdapter`): он принимает **матрицы частей**, **локальные позиции/повороты** и **процедурные функции**, и не требует, чтобы источник знал про базис Unity.

## 6. Воспроизведение

```powershell
# 1. таблица поз по состояниям (читает только локальную копию игры)
python -m tools.alpha_models.anim.pose_table --exe ".scratch/alphatest2/Cube.exe" `
    --source ".scratch/CubeWorld-Reversal/cube/control/GameController.cpp" `
    --first-line 1815 --last-line 7390 --state 1 --state 3

# 2. полная выгрузка в JSON
python -m tools.alpha_models.anim.pose_table --exe ".scratch/alphatest2/Cube.exe" --json pose_table.json

# 3. тесты декодера на синтетических байтах (игра не нужна)
python -m unittest tools.alpha_models.tests.test_alpha_write_scan
```

Ожидаемые маркеры: `POSE_TABLE_RESULT=PASS`, `slot names … 1.000`, `resolved 522/522`, тесты — 12/12.

Ограничение достоверности: инструмент принимает только две реально встречающиеся формы инструкций; всё остальное помечается `не подтверждено`, а не додумывается. Поэтому число восстановленных значений (90) меньше числа записей (522) — вычисляемые значения статически не восстанавливаются.

## 7. Статус по обязательным маркерам

| Маркер | Значение |
|---|---|
| `TRANSFER_METHOD` | байтовое восстановление сайтов доступа `arrayElem_stride4` + таблица переходов `switch` |
| `ALPHA_POSES_EXTRACTED` | **`PARTIAL`** — 73 состояния, 522 записи, 90 статических значений, привязка к конечностям не доказана |
| `ALPHA_LIMB_TRANSFORM` | **`PARTIAL`** — два момента одного канала доказаны (−100° / −60°), конечность не определена |
| `TRANSFERRED_FROM_ALPHA` | **не присваивается** |
| `UNITY_ATTACK_TEST` / адаптер | см. [UNITY_POSE_ADAPTER_REPORT.md](UNITY_POSE_ADAPTER_REPORT.md) |

## 8. Следующий шаг (конкретный)

1. Проследить участок отрисовки частей в `Creature_drawModel` (строки 6088–6300 реконструкции) до конкретной части: какая матрица какой модели (`body`/`head`/`hair`/`hand_*`/`foot_*`/`sword`) соответствует, и какие поля существа её поворачивают.
2. Для найденной части поднять по цепочке, какой стековый слот питает её угол, и тем самым получить **именованную конечность** — после этого статус канала становится `TRANSFERRED_FROM_ALPHA` для первого клипа.
3. Если шаг 1 не даёт однозначности без графической трассы — использовать разрешённый D55 apitrace на копии игры (установка ПО требует отдельного согласования) и получить реальные матрицы кадра.

## 9. Ограничения

* Извлечённые числа — только локально; в Git их нет.
* Привязка каналов к частям не доказана, поэтому клипы в Unity помечаются `PARTIAL`, а не `TRANSFERRED_FROM_ALPHA`.
* Оригинал `D:\Games\Cube world` не изменялся; запуски игры в этой сессии не выполнялись.
