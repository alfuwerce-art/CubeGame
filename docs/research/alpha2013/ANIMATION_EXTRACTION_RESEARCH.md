# Откуда в Cube World Alpha 2013 берутся анимации (исследование)

**Задача:** `S05A2-ANIMATION-EXTRACTION-01` по [D53](../../decisions/D53-original-animation-extraction-priority.md).
**Статус исполнителя:** `BLOCKED` для полного переноса атаки; часть данных получена и помечена `RECONSTRUCTED_FROM_EVIDENCE`.
**Среда:** локальная копия `.scratch/alphatest2` (только чтение оригинала), реконструкция `Cube.exe` в `.scratch/CubeWorld-Reversal`, Unity `6000.3.27f2`.
**Правовая граница:** извлечённые числа и кадры — только локально; в Git публикуются собственный код и текст.

## 1. Где фактически лежат анимации

| Проверенный источник | Результат | Статус |
|---|---|---|
| Файлы клипов (`.anim`, `.plx`-анимации, ресурсы) | клипов анимаций в поставке нет; `.plx` — UI/скрипты, не позы | `VERIFIED_ALPHA` (для этой сборки) |
| Таблицы поз / keyframes в коде | отдельной таблицы поз не найдено; позы **вычисляются** из состояния, времени и параметров оружия | `VERIFIED_ALPHA` |
| `Attribute_deserialize_*_keyframes` | слой keyframes существует (атрибуты/эффекты), но привязки «атака → кадры поз» нет | `PARTIAL` |
| `Creature_drawModel` (0x004128f0) | строит матрицы частей из состояния/времени: 106 вызовов `combat_getAttackWindup`, 46 — `combat_getReloadFrames`, 45 — `combat_getAttackTiming`; позы собираются синусами/косинусами и константами | `VERIFIED_ALPHA` |
| `render_uploadBoneMatrices` / `MaterialBone` | матрицы костей передаются в рендер; отдельного скелетного ассета нет | `PARTIAL` |

**Вывод:** анимация в Alpha 2013 — это **вычисление**, а не данные. Кадров, которые можно «импортировать», в поставке нет; переносимой сущностью являются **формулы и параметры**.

## 2. Что удалось доказать (реальные числа Alpha)

`combat_getAttackWindup` (0x0043caa0), `combat_getAttackTiming` (0x0043d1a0), `combat_getReloadFrames` (0x00447310)
устроены одинаково: `switch` по типу способности (`creature+0x68`), затем

```
frames = base_ms / (haste * speed(+0x17c))
```

Извлечённые базовые значения (миллисекунды, до деления на haste/speed):

| Функция | Тип 1, 9 | Типы 2, 3, 4 | 3, 4, 0x3e | 5, 0xc, 0x10, 0x11, 0x41, 0x42 | Прочее |
|---|---|---|---|---|---|
| `getAttackWindup` | **300** | **100** | — | — | 200/400/500/800/1000/5000 у отдельных типов |
| `getAttackTiming` (recover) | 300 | 100 | — | 200 | 100…800 по типам; `0x17` = 10 мс |
| `getReloadFrames` | 200 | 200 | **100** | **400** | — |

То есть у движка есть **таблица фаз атаки по типу оружия/способности**, масштабируемая haste и общим `speed` существа. Это первая реальная анимационная величина Alpha, пригодная для переноса: она задаёт **длительности фаз**, но не позы.

## 3. Чего доказать не удалось

1. **Позы и их параметры** (углы, смещения суставов, ключи интерполяции) в псевдокоде `Creature_drawModel` не локализованы: функция на 5 579 строк собирает матрицы из десятков локальных переменных, вычисляемых из состояния и таймеров; таблицы «состояние → набор углов» в просмотренных функциях нет.
2. **Соответствие «класс оружия → тип способности»** (`weapon type +0xaa9` → `ability +0x68`) не найдено — без него нельзя утверждать, что извлечённые 100/300 мс относятся именно к двуручному мечу.
3. **Живой захват** оригинальной атаки не выполнен (см. §4) — поэтому статус `TRANSFERRED_FROM_ALPHA` запрещён.

## 4. Запуск оригинала: диагностика

Попытки (всего пять, все из `.scratch/alphatest2`, оригинал не изменялся, `Save` копии восстановлен):

| # | Метод | Результат |
|---|---|---|
| 1–3 | запуск + клики по координатам меню | окно не получало ввод: игра создаёт окно без рамки поверх рабочего стола, но `SetForegroundWindow` возвращает `false` — срабатывает Windows foreground-lock, когда вызывающий процесс не является активным |
| 4 | `ShowWindow(SW_MAXIMIZE)` + `SetForegroundWindow` + захват | окно развернулось, но осталось **позади** окна терминала; кадр показал только перекрытие |
| 5 | запуск + `Start-Process` + фоновый сценарий захвата | сценарий зависал на этапе фокуса, процесс игры завершался вместе с прерванным сценарием |

Диагноз: проблема не в игре, а в **ограничении Windows на смену foreground-окна** для фонового自动化 процесса. Обходные пути, не требующие установки ПО:

* `AttachThreadInput` к потоку активного окна перед `SetForegroundWindow` (стандартный приём, требует того же desktop/сессии);
* синтетическое нажатие `Alt` перед `SetForegroundWindow` (снимает foreground-lock);
* запуск в отдельном рабочем столе (`CreateDesktop`/Task View) — игра становится единственным окном;
* ручная навигация продюсера с локальной записью экрана.

Ни один из них не был доведён до кадра атаки в этой сессии: пункты выше — конкретный план следующего запуска, а не отговорка.

## 5. Что сделано в Unity по итогам исследования

1. **Тайминги атаки взяты из Alpha-кода**: 100 мс windup + 100 мс контакт + 200 мс восстановление = 400 мс (тип 2/3/4 + reload 100 мс) вместо прежних произвольных 1.1 с. Позы по-прежнему наши → статус `RECONSTRUCTED_FROM_EVIDENCE` для тайминга, `ORIGINAL_NOT_ALPHA` для поз.
2. **Закрыты замечания ревью:**
   * `FIX-01`: `bladeHits` теперь влияет на вердикт, границы головы и торса пересчитываются **на каждом сэмпле** (динамические), допуск 0.02;
   * `FIX-02`: проверяется стык `t = 1−ε → 0` по позиции кисти, позиции и повороту оружия. Проверка сразу нашла два реальных дефекта (скачок 0.97 и 0.80 единицы), после исправления — **0.000**;
   * `FIX-03`: добавлен режим PlayMode с самой атакой (`-pilotAttack`), сэмплер в этом режиме проверяет контакт левой кисти с `secondaryGrip` и движение острия клинка, а не качание головы из ходьбы.
3. **Ограничение, зафиксированное честно:** прогон PlayMode в режиме атаки в этой сессии завершился `FAIL` — сэмплер забраковал движение по метрике ходьбы (правка метрики на траекторию клинка внесена, но повторный прогон упал на посторонней внутренней ошибке Unity `SearchDatabase` в batchmode). Поэтому PlayMode-подтверждение атаки остаётся **BLOCKED**, а не «зелёным».

## 6. Как данные превращаются в Unity

| Слой Alpha | Наш эквивалент | Статус |
|---|---|---|
| `ability type (+0x68)` → длительности фаз | `AttackPhases` в конфигурации (windup/strike/recovery в секундах) | `RECONSTRUCTED_FROM_EVIDENCE` |
| `haste`, `speed(+0x17c)` | множитель скорости анимации в конфигурации | `PARTIAL` (формула есть, значения неизвестны) |
| Матрицы костей (`render_uploadBoneMatrices`) | иерархия восьми Transform, `Transform.localRotation` | `ORIGINAL_NOT_ALPHA` (риг не восстановлен) |
| Точки крепления оружия | `primaryGrip`/`secondaryGrip` из геометрии меча (S05A-2 GRIP) | `RECONSTRUCTED_FROM_EVIDENCE` |
| Скиннинг (`MaterialBone`) | плоская иерархия без скиннинга | `UNKNOWN` (не воспроизводим на текущей модели) |

## 8. Можно ли метод использовать для других анимаций

Да, частично:

* **длительности** фаз любой атаки/перезарядки берутся из таблиц `combat_get*` — это воспроизводимо и проверяемо;
* **позы** придётся либо восстанавливать из `Creature_drawModel` (большой объём, переменные не именованы), либо получать захватом из живой игры;
* пока позы не получены, любые новые клипы честно помечаются `ORIGINAL_NOT_ALPHA`.

## 9. Блокеры и следующие шаги

1. Дожать захват оригинала: `AttachThreadInput` + `Alt`-трюк или отдельный рабочий стол; цель — 30 кадров атаки с двух ракурсов.
2. Довести PlayMode-режим атаки до зелёного (исправить метрику и обойти внутреннюю ошибку Unity).
3. Сопоставить класс оружия с типом способности (`+0xaa9 → +0x68`), чтобы привязать 100/300 мс к двуручному мечу.
4. После получения живых поз — перевести один клип в `TRANSFERRED_FROM_ALPHA` и только затем масштабировать на остальные.

## 10. Статус

`S05A2-ANIMATION-EXTRACTION-01 — READY_FOR_REVIEW` с честной пометкой: **полный перенос атаки `BLOCKED`**, перенесены и проверены тайминги (`RECONSTRUCTED_FROM_EVIDENCE`), позы остаются `ORIGINAL_NOT_ALPHA`.

## 11. Уточнение (S05A2-D58-A1, 2026-11-05)

Раздел §3 этой работы («таблицы состояние → набор углов нет, переменные не локализованы») уточнён: таблица **есть**, но её не видно в декомпиляции из-за потерянного `this`-регистра у аксессора `arrayElem_stride4`. Байтовый разбор `Cube.exe` восстановил адреса записей и стековые слоты: 73 состояния через таблицу переходов `0x423D4C` (диспетчер `0x413AF6`), 522 записи каналов, все 522 привязаны к именам переменных декомпиляции. Подробности, числа и границы достоверности — [ALPHA_POSE_EXTRACTION.md](ALPHA_POSE_EXTRACTION.md). Статус `TRANSFERRED_FROM_ALPHA` по-прежнему не присвоен: соответствие «канал → часть тела» не доказано.
