# Захват анимации из работающей Cube World Alpha (журнал)

**Задача:** `S05A2-MIGRATION-ANIMATION-01`, блок B. **Основание:** [D53](../../decisions/D53-original-animation-extraction-priority.md), [D54](../../decisions/D54-internal-alpha-research-prototype-policy.md), [D55](../../decisions/D55-animation-tooling-and-interactive-capture.md).
**Статус:** `PARTIAL` — окно и мышь под контролем, клавиатура пока не доходит до игры; анимация ходьбы не наблюдена в движении.
**Среда:** `D:\Projects\CubeGame\.scratch\alphatest2` (копия, SHA256 `Cube.exe` = `84A7A132A84D…`, совпадает с `D:\Games\Cube world\Cube.exe`); оригинал не изменялся, `Save` копии восстановлен после сессии.

## 1. Проблема фокуса: решена

Ранее `SetForegroundWindow` из фонового процесса возвращал `false` (Windows foreground-lock). Применён штатный приём, не требующий установки ПО:

```
ShowWindow(hwnd, SW_MAXIMIZE);
AttachThreadInput(currentThread, foregroundThread, true);
keybd_event(VK_MENU, …, tap);      // снимает foreground-lock
SetForegroundWindow(hwnd);
AttachThreadInput(currentThread, foregroundThread, false);
```

Результат проверки: `SetForegroundWindow=True`, `GetForegroundWindow()` = PID игры (`match=True`). После этого **клики мышью доходят**: игра прошла меню → выбор персонажа → выбор мира и загрузилась в мир.

## 2. Что реально наблюдено

| Действие | Результат |
|---|---|
| Синтетические клики (меню, START GAME, персонаж, мир) | **работают** — игра загрузила персонажа `SOCCO, LVL 1 WARRIOR` в мир `земли Arulon` |
| Синтетическое нажатие `W` (`keybd_event` без скан-кода) | **не работает** — персонаж не сдвинулся, кадры ходьбы идентичны idle |
| Съёмка окна через `GetWindowRect` + `CopyFromScreen` | **работает**, 12 кадров 1936×1048 (окно развёрнуто) |

Кадры: `.scratch/s05a2/alpha_walk/lambda-00-menu.png`, `lambda-10-ingame.png`, `lambda-walk-00..05.png`, `lambda-11-afterwalk.png`.

Вывод: **фокус и мышь больше не блокер**; блокер сместился на **синтетическую клавиатуру**. Наиболее вероятная причина — игра читает клавиатуру через DirectInput/raw input, а `keybd_event` с нулевым скан-кодом такой поток не генерирует. Следующие шаги: `keybd_event`/`SendInput` с реальными скан-кодами (`MapVirtualKey`), `SendInput` с `KEYEVENTF_SCANCODE`, либо штатный ввод через интерактивный сеанс.

## 3. Инструменты

Ничего нового не устанавливалось: выявленный блокер (фокус окна, затем клавиатура) не требует Ghidra/отладчика/трассировщика — все шаги выполнены имеющимися средствами Windows API и PowerShell. Установка специализированного ПО отложена до появления блокера, который без него не решается (согласно D55 «не устанавливать весь список без необходимости»).

## 4. Что это означает для переноса

* Наблюдение оригинальной ходьбы **не получено** → статус клипа ходьбы остаётся `ORIGINAL_NOT_ALPHA`, не `TRANSFERRED_FROM_ALPHA`.
* Тайминги фаз атак из кода (`combat_getAttackWindup/Timing/ReloadFrames`) по-прежнему единственная подтверждённая величина Alpha: 100/200/300/400/800/1000 мс, формула `base_ms/(haste×speed)`.
* Клавиатурный канал нужно дожать (скан-коды), после чего снимать idle → W → отпускание и атаку правой кнопкой мыши.

## 5. Следующий конкретный шаг

1. Повторить запуск, отправить `W` с реальным скан-кодом (`KEYEVENTF_SCANCODE`), проверить, что персонаж сдвинулся хотя бы на один блок.
2. Снять серию 10–15 кадров цикла и измерить длительность шага по кадрам.
3. Нажать кнопку атаки, зафиксировать замах и контакт, сопоставить с таймингами из кода.
4. Только после этого присваивать `TRANSFERRED_FROM_ALPHA` / `RECONSTRUCTED_FROM_EVIDENCE` самим позам.

## 6. Правовые ограничения

Кадры и любые извлечённые данные остаются локально в `.scratch`; в публичный репозиторий попадают только собственный код, инструменты и этот текст.


## 7. Продолжение (S05A-2 CONTINUOUS, D57)

**Что проверено дополнительно**

| Метод ввода | Код | Результат |
|---|---|---|
| `SendInput` со скан-кодом (`MapVirtualKey` + `KEYEVENTF_SCANCODE`) | `alpha_input2.ps1` | вызов вернул **0** — событие не вставлено (упрощённая структура `INPUT` без union-выравнивания → неверный `cbSize`) |
| `SendInput` по virtual-key | `alpha_input2.ps1` | тоже **0**, по той же причине |
| `keybd_event(0, scanCode, KEYEVENTF_SCANCODE, 0)` | `alpha_input3.ps1` | вызов выполняется без ошибки; в области персонажа зафиксировано изменение кадра, растущее по времени (110k → 229k пикселей), но фон (трава, облака, время) тоже анимирован → **движение не доказано однозначно** |

Вывод по вводу: проблема была в структуре `INPUT` (нужен полный union с корректным размером). `keybd_event` со скан-кодом доставляется, но нужен способ отделить движение персонажа от анимации окружения (например, вырезать область только персонажа и сравнить смещение, либо зафиксировать координаты персонажа по миникарте/панели).

**Кадры:** `.scratch/s05a2/alpha_walk3/s-10-ingame.png`, `s-walk-00..07.png`, `s-11-after.png` (10 шт.).

**Следующий шаг (без нового согласования):** исправить `INPUT` (полный union, `Marshal.SizeOf` = 40 на x64, `SendInput` должен вернуть 1), затем измерить смещение персонажа по кадрам в узкой области и получить длительность шага. После этого — атака правой кнопкой мыши и сопоставление с таймингами `combat_get*`.

**Статус переноса:** по-прежнему `BLOCKED` для поз (`TRANSFERRED_FROM_ALPHA` не присвоен); из Alpha подтверждены только тайминги фаз атак.
