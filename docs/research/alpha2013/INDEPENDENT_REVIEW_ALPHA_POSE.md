## 2. Найденные дефекты (опровержения)

### 2.1 Границы блоков состояний заданы неверно → «522 записи» завышены

`pose_table.collect_states` вычисляет конец блока как ближайший *больший* адрес из таблицы переходов. Последний вход таблицы — `0x41E660`, он же Adjacent к default-цели `0x41E666`; больше целей нет, поэтому блок продлевается до конца функции (`0x423F20`) и **поглощает весь код отрисовки**.

Следствия, проверенные экспериментально:

* реальных сайтов всего **338**, а сумма по блокам — **522**;
* **46 сайтов** приписаны сразу к пяти состояниям (12, 13, 14, 36, 64) — у них общий вход таблицы;
* значит, числа «522 записи» и «30 записей у состояния 1» из отчёта первого агента получены на смещённой разметке; для пяти перечисленных состояний разметка бессмысленна.

### 2.2 «Записи» — это не только записи

Классификация по инструкции сразу после вызова: `movss xmm0,[eax]` — **213 чтений**, `movss [eax],xmm0` / `mov [eax],imm32` — **31 запись**, ещё **279** не классифицируются простым шаблоном. Называть все сайты «writes» некорректно.

### 2.3 Проверка «522/522 имён существует» слабая

Имя `local_XXXX` выводится из смещения по стек-фрейму, а объявлений локальных переменных в функции около 240 — почти любое смещение попадёт в существующее имя. Эта проверка не подтверждает семантику и **не способна заметить ошибку разметки блоков** (§2.1).

### 2.4 Покрытие: треть вызовов не декодируется

`523` вызова аксессора в функции, декодируется `338–341`. Остальные имеют базу в регистре (например, в коде отрисовки — `lea ecx,[esi+0x80]`, чтение массива в куче), а не на стеке. Это ограничение метода, а не ошибка конкретного сайта, но оно означает: «все записи позы восстановлены» — неверная формулировка.

## 3. Главная цель: канал → часть тела

### 3.1 Что удалось проследить

1. Каналы позы — стековые `vec3` (`local_15fc, 15f0, 15e4, 15d8, 15cc, 15c0, 15b4, 15a8, 159c, 1590, 1584`), запись идёт по компонентам через аксессор.
2. В коде отрисовки (адреса ≥ `0x41F600`) канал читается аксессором и сразу попадает в матрицу части. Полный список таких чтений (после исправления знака смещения — см. ниже):

   | Адрес | Канал | Блок отрисовки (upload → draw) |
   |---|---|---|
   | `0x420BE4` | `local_15a8[2]` | 10: `0x420CC3 → 0x420CD2` |
   | `0x421664` | `local_15b4[2]` | 16: `0x4219DE → 0x421A01` |
   | `0x421E9D` | `local_15d8[2]` | 18: `0x4222F8 → 0x42231B` |
   | `0x423067` | `local_15d8[2]` | 20: `0x4231F1 → 0x423214` |
   | `0x423413` | `local_15b4[2]` | 22: `0x4235A6 → 0x4235B1` |

   Замечание по методике: при первом проходе я получил «0 чтений» из-за ошибки знака при пересчёте `esp → ebp` (компонента с индексом `k` лежит по адресу `base + 4k`, то есть по **меньшему** по модулю смещению). После исправления — 5 чтений выше. Это ровно тот класс ошибок, который делает «проверку по именам» бесполезной: смещение на один компонент всё равно попадает в существующее имя.
3. В этих блоках значение используется как поворот/смещение части: последовательность `mat4_translate(arr0,arr1,arr2)` → `mat4_rotateZ(arr2)` → `mat4_rotateY(arr1)` → `mat4_rotateX(arr0)` (например, строки 7142–7154 и 7205–7219 реконструкции).
4. Часть выбирается полем существа: в блоке 10 условие `if (pfVar9[0x32] != 0)`; сам слот заполняется в начале функции из короткого индекса `*(short*)(creature + 0x98)` либо из модели `item_icon_id(creature + 0x990)` (строки 2117–2119, 2195–2203).

### 3.2 Чего доказать не удалось

Анатомическое имя части (`hand_l`, `foot_r`, …) не установлено: слот `0x32` связан с полем `creature+0x98`, но порядок восьми appearance-индексов (`creature+0x8c, +0x8e, +0x90, +0x92, +0x94, +0x96, +0x98, +0x9a`) в реконструкции нигде не подписан, а список моделей (`param_4`) формируется вызывающим кодом и в статике не сопоставлен с именами `.cub`.

Дополнительная сложность: помимо стековых каналов, код отрисовки читает **массив в куче** (`lea ecx,[esi+0x80]`), то есть в кадре есть второй источник позы, и часть поворотов берётся оттуда, а не из найденных стековых каналов.

### 3.3 Статус

`CHANNEL_TO_BODY_PART = PARTIAL` — цепочка «запись значения → стековый канал → чтение аксессором → `mat4_rotateZ` части → `render_uploadModelViewMatrices` → `draw_mesh`» прослежена до **конкретного блока отрисовки** (адреса выше), но не до **имени части тела**. Утверждение первого агента о девяти каналах как о позе подтверждено частично: каналы действительно читаются кодом отрисовки, но лишь немногие (z-компоненты `15a8`/`15d8`), и рядом есть второй, нестековый источник.

## 4. Формула движения

Подтверждено:

* источник чисел — инструкции `mov [eax], imm32` по адресам `0x41763E` (−100°), `0x4179B1` (−60°), `0x417A58` (−250°);
* все три пишут в **один и тот же** слот/компоненту `local_15fc[0]`, все три — внутри блока состояния 1;
* между −100 и −60 стоит вызов `combat_getAttackTiming` (`0x4176E9`), а раньше — `combat_getAttackWindup`; это согласуется с гейтингом «замах → восстановление», который описан в отчёте первого агента;
* угол > 180° (−250°) корректен как кватернион: `AngleAxis(−250°) ≡ AngleAxis(110°)`, поэтому сравнение через кватернион (а не через модуль угла) обязательно — это в Unity-пробе сделано правильно.

Не подтверждено:

* что `local_15fc` — именно **поворот части тела**, а не скаляр для другой цели: чтений этого слота в коде отрисовки нет (найдены только `15a8`, `15b4`, `15d8` — все компонента 2), то есть потребитель `15fc` пока не локализован;
* комбинации вращений по нескольким осям на одном канале: в блоках отрисовки видны `rotateZ/rotateY/rotateX` из **трёх разных** компонент, но принадлежность этих трёх компонент одному каналу не доказана (базы могут отличаться).

`ALPHA_MOTION_FORMULA = PARTIAL`: движение одного канала во времени доказано с адресами и порядком вычислений, привязка к части тела и полный набор осей — нет.

## 5. Unity

* `CharacterPoseAdapter.cs` — контракт корректен: матрицы/TRS/кривые, parent-first, валидация (NaN, вырожденный родитель, shear, зеркало), обязательный провенанс.
* `CharacterPilotAlphaPose.cs` — численно проверяет именно то, что заявляет: собирает вращение в порядке Alpha, один раз меняет базис `(x,y,z)→(x,z,y)`, применяет и сравнивает **кватернион, прочитанный из `Transform`**, с ожиданием; охранник провенанса отдельно проверен.
* Математика базиса перепроверена независимо: для отражения `S` (det = −1) `S·R(θ)·S = R(−θ)` вокруг отображённой оси; проба сравнивает именно с `AngleAxis(−value, ось)` — согласовано.
* Ограничение: значение применяется к **произвольной** части (`body`) с меткой `PARTIAL_BINDING`. Это проверка механизма, а не перенос движения конкретной части. Совпадение 0° подтверждает арифметику, но не анатомическую привязку.

`UNITY_TRANSFER = PARTIAL`.
