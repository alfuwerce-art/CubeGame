## 2. `data*.db` — SQLite key/value хранилища ресурсов

Схема одинакова во всех четырёх файлах (`BINARY_STATIC`):

```sql
CREATE TABLE blobs(key TEXT PRIMARY KEY, value BLOB)
```

Параметры страниц: `page_size = 1024`, `encoding = UTF-8`, `journal_mode = delete`, `user_version = 0`.
Дополнительных таблиц, индексов (кроме автоиндекса первичного ключа) и триггеров нет.

Распределение ключей по расширениям (полный перебор всех строк):

| База | Строк | Расширения ключей |
|---|---|---|
| `data1.db` | 2857 | `.cub` — 2857 (100 %) |
| `data2.db` | 93 | `.wav` — 93 (100 %) |
| `data3.db` | 104 | `.png` — 104 (100 %) |
| `data4.db` | 2 | `.xml` — 2 (100 %) |

Наблюдения:

1. Ключ — именно имя ресурса с расширением (`aim.cub`, `Explosion.wav`, `aim.png`, `dict_en.xml`), что совпадает с утверждением README Reversal о «key/value blob-хранилищах по именам ассетов». Утверждение **подтверждено** на локальной копии.
2. Размеры блобов: `.cub` — от 108 до 217 740 Б; `.wav` — от 16 428 до 5 118 322 Б; `.png` — от 276 до 997 Б.
3. Блобы **не являются** zlib-потоками: проверка `zlib.decompress` на выборке не даёт успеха, магия PNG/RIFF в открытом виде отсутствует. Точный формат `.cub` в R01 **не расшифрован** (`UNKNOWN`) — для пилота он не нужен.
4. Содержимое `data*.db` — закрытые ресурсы Alpha. В публичный репозиторий CubeGame они не выгружаются; здесь зафиксированы только метаданные (имена, размеры, схема).

## 3. `Save/*.db` — сохранения

Схема всех четырёх файлов одна и та же (§2), но семантика ключей разная.
Значения — `BLOB`; ключи — текст.

### 3.1. `characters.db` — персонаж

| Ключ | Значение |
|---|---|
| `num` | 4 байта little-endian = `1` — счётчик персонажей |
| `0` | 708 Б zlib → **63 753 Б** распакованных |

Начало распакованных данных (`SAVE_OBSERVED`): `01 00 00 00` затем структуры с повторяющимися `00 00 80 20` (0x20800000 как float ≈ 1.17e-19 → это не float, а упакованные флаги/идентификаторы), далее `7b 14 9a 00` (0x009a147b = 10 097 787) и `8d 00 00 00` (141). Разбор структуры персонажа — задача следующих партий; сейчас подтверждён только факт «zlib-контейнер + плоская структура без SQLite-таблиц».

### 3.2. `worlds.db` — список миров

| Ключ | Значение |
|---|---|
| `num` | 4 байта = `1` |
| `0` | 11 686 Б, **без сжатия** |

Разбор начала блоба (`SAVE_OBSERVED`, установлено однозначно):

| Смещение | Байты | Значение |
|---|---|---|
| 0 | `07 00 00 00` | версия записи мира = 7 |
| 4 | `G0WORLD` | имя мира, C-строка с завершающим `\0` |
| 12 | `2a 2c 0a 00` | seed = **666 666** (0x000A2C2A) — совпадает с введённым в G0 |
| 16 | `01 00 00 00` | тип/уровень мира (не подтверждено) |
| 20 | `20 00 00 00 20 00 00 00` | пара `32, 32` — вероятно, координаты стартовой области в блоках или тайлах (не подтверждено) |

Далее идут повторяющиеся записи, которые не декодированы (`UNKNOWN`).

### 3.3. `world_G0WORLD.db` — сущности мира

129 записей. Ключи имеют вид `<тип><X>_<Y>`, где `X`/`Y` — целые координаты ячейки (`SAVE_OBSERVED`):

- `time` — 8 байт (`00 00 00 00 cc d6 19 02`) — игровое время;
- `mission<X>_<Y>` — 38 Б, начинается с `01 00 00 00` + 34 нулевых байта;
- `monster<X>_<Y>` — 21 Б, например `01 00 00 00 00 00 00 00 00 00 00 19 48 00 05 c8 c8 c8 ff`.

Наблюдаемые координаты в ключах — `4096`, `4097`, … (непрерывный ряд по одной оси). Это значит, что сущности мира адресуются целочисленной решёткой; шаг решётки и её связь с блоком **не установлены** (`UNKNOWN`).

### 3.4. `map_G0WORLD.db` — карта регионов

101 запись с ключами `reg<X>_<Y>`, наблюдаемые значения `X`,`Y` ∈ [509…515]. Каждый блоб — ровно 60 164 Б, из них:

- 4 байта заголовка (`01 00 00 00`);
- 60 160 байт данных, в которых встречаются **только два значения байта** (0 и 1) → это растровое представление региона, а не структура с плавающими числами.

Строка `0x1` повторяется с шагом 14 байт в исследованной выборке; устойчивый период (16/64/128/256/470/512/940) не подтверждён, поэтому размерность сетки карты **не установлена** (`UNKNOWN`). 60 160 = 128 × 470 = 256 × 235 — обе факторизации «неудобные», что говорит против простого `N × N` байтового растра; возможны битовая упаковка или RLE.
Для пилота этот формат не нужен; вопрос вынесен в открытые.

## 4. `.plx` — поток объектов движка Plasma

Все пять файлов имеют **идентичный** 32-байтный префикс (`BINARY_STATIC`):

```
00000000: 00 00 00 00 16 00 00 00 01 00 00 00 0e 00 00 00
00000010: 50 6c 61 73 6d 61 47 72 61 70 68 69 63 73 01 00
```

то есть `dword[0]=0`, `dword[1]=22`, `dword[2]=1`, `dword[3]=14`, далее ASCII-тег `PlasmaGraphics`.

Далее поток читается как последовательность «тег + длина + данные»: в `cursor.plx` видны теги `Seal` (длина 0x12, внутри 14 байт непрозрачного значения) и `Mesh`; в `start.plx`/`gui.plx` — `QpEB`, `VUUB`, `TCtP`, `APKg`, `UW…`, `Seal` и т. п., то есть имена классов/свойств Plasma, записанные тегами.

Вывод: `.plx` — сериализованный объектный поток движка Plasma (совпадает с описанием README Reversal: «object stream format … tagged internally as `PlasmaGraphics`»). Полная схема тегов **не восстановлена** (`UNKNOWN`); для CubeGame переиспользование формата не планируется — это закрытый формат UI/ресурсов Alpha.

## 5. Сверка локального `Cube.exe` с исследовательским деревом Reversal

`BINARY_STATIC`, чтение файла без запуска и без дизассемблирования:

- `Cube.exe`, 3 885 568 Б, SHA-256 `84A7A132…6DC30BF`, PE32, компоновка 2013-07-20.
- В бинаре присутствуют **184** строки mangled RTTI (`.?AV…`), из них с пространством имён `cube::` — 48 классов, `plasma::` — 47, `abstr::` — 4, плюс `Concurrency`/STL/CRT. Это подтверждает, что сборка — MSVC C++ с RTTI и что архитектура действительно разделена на `cube::` (игра) и `plasma::` (движок).
- Извлечённые классы `cube::` (полный список, `BINARY_STATIC`):
  `AdaptionWidget, Audio, Behavior, BlueprintPreviewWidget, CharacterPreviewWidget, CharacterStyleWidget, CharacterWidget, ChatWidget, CombatBehavior, CompanionBehavior, Controller, Creature, CubeShader, Database, Dungeon, EnchantWidget, Field, GameController, House, InventoryWidget, LookAtPlayerBehavior, MapOverlayWidget, Music, ObjectiveWidget, OptionsWidget, PreviewWidget, QuestText, RandomInteractionBehavior, RandomWalkBehavior, SequentialBehavior, SkillWidget, SpawnLocationBehavior, Speech, SpeechWidget, Sprite, SpriteManager, SpriteWidget, StartMenuWidget, StatisticsWidget, SystemWidget, VoxelWidget, WalkPathBehavior, World, WorldMap, WorldPreviewWidget, XAudio2Engine, Zone, ZoneTile`.
- Классы `plasma::`: `Engine, D3D9Engine, D3D9Texture, D3D9RenderSurface, Widget, Font, PlasmaFont, PixelFont, ScalableFont, FontEngine, Shape, MeshShape, SmoothMeshShape, StaticMeshShape, CurveShape, TextShape, ObjectManager, NamedObject, Object, Node, Transformation, Keyable, Texture, RenderSurface, Display, Drawing, D3D9Drawing, Movie, ListWidget, Button, Edit, PopUpButton, ScrollButton, ScrollSlider, Attribute, Deformer, …`, а также исключения `InvalidFileFormatException`, `InvalidVersionException`, `IOException`, **`InvalidDemoLicenseException`**.
- Строки `Wollay` и `funck` присутствуют; строки `paraglider` нет, есть одна `glider` (то есть «исправление параплана», упомянутое в README Reversal, по строкам не опознаётся).

### Отличия и расхождения, которые надо держать в уме

1. Reversal заявляет классы `cube::Region`, `cube::Chunk`, `cube::ChunkBuffer`, `cube::WorldInfo`, `cube::LandscapeTile`, `cube::Spawn` — **в RTTI локального `Cube.exe` их нет**. Вероятная причина: эти классы в оригинале не полиморфные (без vtable), поэтому RTTI для них не генерируется. Это не доказывает ни наличие, ни отсутствие классов — только то, что по RTTI их не подтвердить.
2. Итог сверки: набор классов и использованные технологии **согласуются** с описанием Reversal, но бит-в-бит тождественность по-прежнему не доказана (нет официальных хешей). Reversal остаётся `RECONSTRUCTED_SOURCE`, а не истиной.

## 6. Расхождение по локализации (закрывает открытый вопрос G0 частично)

В G0 было зафиксировано: UI частично русский, `options.cfg: language 9` — при этом в `data4.db` есть ровно два словаря: `dict_de.xml` и `dict_en.xml`. Русского словаря в ресурсах нет (`BINARY_STATIC`).
Следствие: русские подписи в интерфейсе приходят не из `data4.db` — либо из изменённых `.plx`/`.cub` репака, либо из отдельного механизма. Точный источник **не установлен** (`UNKNOWN`). Для CubeGame это несущественно, но усиливает оговорку G0 о неофициальном происхождении копии.
