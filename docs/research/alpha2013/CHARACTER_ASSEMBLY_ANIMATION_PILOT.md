**Отдельные модели конечностей — `NOT_FOUND` в исследованном наборе.** В `Cube.exe` из 2550 имён `*.cub` нет ни одного `leg*`/`*-leg`, а `-arm` встречается только у монстров (`troll-arm`, `golem-arm`, `cyclops-arm`…). **Чего это НЕ доказывает (уточнено в REVIEW-FIX-01):** отсутствие отдельных `.cub`-моделей рук и ног **не** означает отсутствие скелетной системы. Точная структура исходного рига гуманоида, матриц костей и анимационных контроллеров **не восстановлена** (`UNKNOWN`): возможно, конечности — часть `body*` и деформируются костями, возможно, поза считается кодом для отдельных узлов. Пилот проверяет только ту схему, которую удалось собрать из отдельных моделей.

### 2.2 Иерархия и Transform-параметры (пилот)

```
character_human-male-proxy              (root, status = PROXY_NOT_ALPHA)
├─ part_body        worldMin (-5, 3, -4)   size (10,10,8)
│  ├─ part_head     worldMin (-7,13, -4)   size (14, 8, 8)   pivot = верх головы
│  │  └─ part_hair  worldMin (-6,13, -6)   size (12,11,12)   offset = голова + grid-дельта
│  ├─ part_hand_l   worldMin (-10,9, -3)   size ( 5, 4, 6)   pivot = сустав кисти
│  ├─ part_hand_r   worldMin (  5,9, -3)   size ( 5, 4, 6)   pivot = сустав кисти
│  │  └─ part_sword worldMin (  6,9, -6.5) size ( 3,37,13)   offset в системе кисти
│  ├─ part_foot_l   worldMin ( -5,0, -4)   size ( 5, 3, 8)   pivot = низ стопы
│  └─ part_foot_r   worldMin (  0,0, -4)   size ( 5, 3, 8)
```

Два правила, которые пришлось вывести и проверить (оба ловятся валидаторами):

1. **Пивот части стоит в суставе**: мировая точка пивота = `frameOffset + joint`, а вложенная часть позиционируется относительно *пивота* родителя. Ошибка → `world min != frameOffset + sourceMin`.
2. **Части размещаются по исходной сетке, а не по минимальному углу bbox** (FIX-02). Голова и волосы authored в одной сетке 18×16×16; при совмещении min-углов волосы уезжали вперёд и закрывали лицо. Теперь у каждой части есть `frameOffset` (начало её воксельной сетки в пространстве персонажа) и `joint` (пивот внутри сетки), вершины меша остаются в координатах сетки, а заполненная область сохраняет своё смещение внутри неё:

| Часть | `sourceMin` (x,h,d) | сетка | `frameOffset` | `joint` | `frameOffset + sourceMin` |
|---|---|---|---|---|---|
| body | (0, 0, 0) | 10×8×10 | (−5, 3, −4) | (0, 0, 0) | (−5, 3, −4) |
| head | (2, 2, 4) | 18×16×16 | (−9, 11, −8) | (9, 10, 8) | (−7, 13, −4) |
| hair | (3, 2, 2) | 18×16×16 | **(−9, 11, −8)** | (0, 0, 0) | (−6, 13, −6) |
| hand_l | (0, 0, 0) | 5×6×4 | (−10, 9, −3) | (2.5, 4, 3) | (−10, 9, −3) |
| hand_r | (0, 0, 0) | 5×6×4 | (5, 9, −3) | (2.5, 4, 3) | (5, 9, −3) |
| foot_l | (0, 0, 0) | 5×8×4 | (−5, 0, −4) | (2.5, 0, 4) | (−5, 0, −4) |
| foot_r | (0, 0, 0) | 5×8×4 | (0, 0, −4) | (2.5, 0, 4) | (0, 0, −4) |
| sword | (0, 0, 0) | 3×13×37 | (6, 9, −6.5) | (0, 0, 0) | (6, 9, −6.5) |

У головы и волос `frameOffset` **совпадает** — это и есть подтверждённое соответствие исходных координат, а не искусственное совмещение bounding boxes. Проверяется отдельно: `ValidateSharedFrame` (равенство frame) и `ValidateSkinAlignment` (кожные воксели волос обязаны попадать в кожу головы, ≥ 99%, уже в пространстве собранного персонажа).

## 3. RGB-маркеры: что подтверждено, что нет

**Подтверждено кодом** (`VoxelModel_set_data` @ `0x004e7650`): при загрузке модели движок перебирает все воксели и складывает координаты вокселей с **точно** чистым цветом в три отдельных списка — зелёный `(0,255,0)`, красный `(255,0,0)`, синий `(0,0,255)`. При этом буфер цветов копируется **без изменений**, то есть маркеры остаются и в геометрии. Сканирование выполняется не всегда: оно пропускается, когда модель грузится с ненулевым флагом последнего аргумента (для части моделей клиент грузит именно так).

**Измерения на моделях:**

| Модель | R `(255,0,0)` | G `(0,255,0)` | B `(0,0,255)` | Наблюдение |
|---|---|---|---|---|
| `human-head-m01` | 0 | 0 | 0 | маркеров нет |
| `human-hair-m01` | 298 | 4 | 10 | G/B — по 4–10 вокселей, 100% на поверхности, симметричные кластеры у макушки |
| `human-hair-base` | 308 | 4 | 8 | красный — 97% на поверхности |
| `orc-hair-base` | 354 | 10 | 8 | то же |
| `body1`, `glove`, `orc-hand`, `foot` | 0 | 0 | 0 | маркеров нет |

**Интерпретация (осторожно):**

- `PARTIAL`: **зелёный и синий** наборы — крошечные (≤ 16 вокселей), полностью на поверхности, в симметричных позициях у макушки → согласуются с ролью служебных маркеров посадки волос. Их точное назначение не доказано.
- `PARTIAL`: **красный** встречается во **всех** моделях волос и ни в одной модели головы/торса/кисти/стопы, занимает ~300 вокселей и в `human-hair-base` покрывает 97% видимой поверхности → согласуется с ролью «подстановочного» цвета волос, который игра заменяет цветом персонажа.
- `UNKNOWN`: как именно игра выбирает цвет (замена палитры, тинт, две ступени светлоты — белая оболочка + красное «ядро») — не восстановлено.

**Реализация (не «слепое правило»):** конвертер ничего не классифицирует сам. `cub_markers.py` **измеряет** каждую группу и выдаёт эвристическую метку (`ANCHOR_CANDIDATE` / `VOLUME_TINT_CANDIDATE` / `UNKNOWN_DECORATIVE`) с обоснованием, а **скрывает** воксели только то, что оператор явно назвал:

```powershell
python tools\alpha_models\cub_to_obj.py --db ... --key "human-hair-m01.cub" --out-dir ... `
    --markers hair.markers.json --exclude-markers green,blue
```

В пилоте для волос скрыты **green, blue** (14 вокселей), красный **оставлен** (тинт не подтверждён, выдумывать замену нельзя). Геометрия маркеров сохраняется отдельно: `.markers.json` содержит их координаты, bbox, долю на поверхности и метку.

## 4. Тинт волос: статус `PARTIAL`, без подмены поведения

- В `human-hair-m01` белая оболочка (463 вокселя, 66% на поверхности) + красное «ядро» (298, 44%) + 286 кожных вокселей (скальп, 2% на поверхности).
- В `human-hair-base` белого нет вообще: 308 красных (97% на поверхности) + скальп.
- У эльфийской головы `elf-head-female` 434 белых вокселя и **ноль** красных.

**Вывод:** белый — самостоятельный цвет (у эльфов это буквально цвет волос), красный — кандидат на «подстановочный» цвет. Механизм (какой именно цвет заменяется, применяется ли тинт к белому) **не подтверждён**, поэтому:

- тест смены цвета волос **не реализован** (ТЗ разрешает только при подтверждённой семантике);
- в Unity волосы отрисованы «как есть» — красная чёлка видна на снимках, это честный артефакт открытого вопроса, а не «поведение Alpha»;
- воспроизведение возможно двумя путями (vertex colors по маске / отдельный параметр материала), но выбор требует данных, а не догадки.

## 6. Собственный технический цикл

| Параметр | Значение |
|---|---|
| Имя | `technical_walk_NOT_ALPHA` |
| Длительность | 1.6 с, фаза 0…1 |
| Реализация | `ProceduralCharacterAnimator` (MonoBehaviour, детерминированный `Sample(t)` + `Update()` в PlayMode) |
| Тело | вертикальная качка `abs(sin)·0.35`, наклон ±2° |
| Голова | кивок ±3°, независимый поворот ±14° (проверка «голова не отрывается») |
| Кисти | мах ±26° в противофазе вокруг сустава |
| Стопы | подъём до 0.55 и ход ±0.45 в противофазе |
| Волосы, меч | не анимируются локально — следуют за родителем |
| Проверки | движение (head/hand/foot), стабильность гнезда оружия в системе кисти, замыкание цикла (позиция + поворот головы) |

Почему процедурный контроллер, а не `AnimationClip`: клип потребовал бы ручного authored-контента, которого нет; процедурный слой даёт детерминированные сэмплы (их можно проверять тестом) и работает и в EditMode-сэмплировании, и в PlayMode.

**Найденный тестом дефект:** первая версия аниматора в каждом кадре сбрасывала локальный offset меча в ноль («чтобы следовал за рукой»), из-за чего меч прыгал из кисти в её начало. Инвариант «смещение в системе кисти постоянно» это поймал (`sword drifted in the hand at frame 1`), после исправления — `drift = 0`.

## 12. S05A-1-REVIEW-FIX-01 (2026-11-04) — исправления по ревью ChatGPT

Ревью: `PASS WITH FIXES`. Все три замечания приняты; геометрия, цвета и материалы моделей не подгонялись,
статусы неизвестных механизмов не менялись.

### FIX-01 — координаты вокселей считаются в два прохода

**Дефект.** `BuildMeshFromPayload()` обновлял `minX/minD/minH` в том же цикле, где создавались вершины.
Первые вершины вычитали ещё не окончательный минимум: если позже встречался воксель с меньшей координатой
по какой-то оси, ранние вершины оставались смещёнными, а итоговый `bounds` при этом выглядел правдоподобно.

**Воспроизведение.** В самотестах осталась копия прежнего алгоритма (`BuildMeshFromPayloadLegacySinglePass`)
и синтетическая модель `asymmetric_4x1x2`, где первый по порядку обхода воксель стоит при `x = 3`, а более
поздний — при `x = 0`. На ней старый алгоритм даёт набор вершин, отличный от ожидаемого (тест
`legacy single-pass distorts the asymmetric model` — PASS, то есть дефект воспроизведён), новый — совпадает
побитово по целочисленным координатам.

**Исправление.** Первый проход — только границы видимых вокселей (с учётом маски маркеров); второй — эмиссия
граней. Цвета, нормали, порядок обхода вершин и правила отсечения скрытых граней не менялись. Пустая модель
и модель, полностью скрытая маской, теперь дают явную ошибку `no visible voxels`, а не молчаливый успех.

**Новые тесты:** двухпроходный меш строится; `grid min` не отрицателен; каждая вершина лежит внутри сетки;
мультимножество вершин совпадает с независимым брутфорс-ожиданием; дефект старого алгоритма воспроизведён;
пустая модель распознаётся; кросс-проверка с Python-конвертером (ниже).

### FIX-02 — исходное взаимное положение головы и волос

**Дефект.** Сборщик обрезал пустые края каждой модели до её bbox и затем ставил части по `worldMin`. Из-за
этого терялось смещение заполненной области внутри исходной воксельной сетки, а совпадение «284 из 286 кожных
вокселей» держалось на вычисленной вручную поправке, а не на данных.

**Исправление.** Введена явная цепочка координат (все поля пишутся в отчёт):

| Слой | Что это | Пример (hair) |
|---|---|---|
| исходные координаты вокселя | `(x, h, d)` внутри сетки модели | `(3, 2, 2)` … `(14, 12, 13)` |
| `sourceMin` | начало заполненной области внутри сетки | `(3, 2, 2)` |
| mesh local | вершины остаются **в координатах сетки**, без обрезки | `(3, 2, 2)` … |
| `joint` | пивот внутри сетки (сустав) | `(0, 0, 0)` |
| `frameOffset` | начало сетки в пространстве персонажа | `(−9, 11, −8)` |
| положение относительно родителя | `frameOffset + joint − родительский пивот` | `(−9, −10, −8)` |
| мир | `frameOffset + координата вокселя` | `(−6, 13, −6)` … |

Голова и волосы получают **один и тот же** `frameOffset = (−9, 11, −8)`, потому что authored в одной сетке
18×16×16; это и есть подтверждённое соответствие исходных координат вместо совмещения bbox. Проверяется:

* `ValidateSharedFrame` — `frameOffset` головы и волос обязаны совпадать;
* `ValidateSkinAlignment` — кожные воксели волос в пространстве персонажа обязаны попадать в кожу головы
  (порог ≥ 99%). Фактические числа при `frameOffset = (−9, 11, −8)` для обеих моделей: кожа головы — 569
  вокселей, кожа волос — 286, совпало **284 (99.30%)**. Сдвиг волос на один воксель даёт 279 (97.6%), сдвиг
  по глубине — 273 (95.5%), то есть порог действительно различает правильную и сдвинутую сборку.

**Новые тесты:** совпадение frame → PASS; сдвиг волос на один воксель → FAIL; сдвиг frame ломает
skin-alignment → FAIL; `sourceMin` разреженной модели не влияет на итоговое размещение; поворот головы
сохраняет положение волос относительно неё (PlayMode и EditMode сэмплы).

### FIX-03 — иерархия проверяется по реальной сцене

**Дефект.** Прежний `ValidateHierarchy()` сравнивал `AssemblySpec` с `PartResult`, а `PartResult.parent`
заполнялся из той же спеки — то есть проверка была тавтологией и не видела поломанный `Transform.parent`.

**Исправление.** Спека проверяется отдельно (`ValidateHierarchy` — самосогласованность), а фактическая сцена —
независимым `ValidateHierarchyFromScene(root, spec)`: он обходит реальные `Transform`, берёт
`Transform.parent`, отбрасывает технический узел `mesh` и любые узлы не вида `part_*`, и сравнивает набор
и родителей с ожидаемыми. Обнаруживаются отсутствующие узлы, лишние `part_*`, дубли и неверное подчинение.

**Негативные тесты (реальная сцена, 8 узлов):**

| Сценарий | Ожидание | Результат |
|---|---|---|
| корректная иерархия | PASS | PASS |
| голова переподчинена корню | FAIL | FAIL (`Transform.parent`) |
| волосы переподчинены туловищу | FAIL | FAIL |
| меч переподчинён туловищу вместо кисти | FAIL | FAIL |
| отсутствует кисть `hand_l` | FAIL | FAIL (`missing part node`) |
| лишний узел `part_ghost` | FAIL | FAIL (`unexpected part node`) |
| лишний технический узел `mesh` | PASS (игнорируется) | PASS |
