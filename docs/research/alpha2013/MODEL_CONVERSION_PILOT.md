**Проект:** CubeGame. **Этап:** `S05A-0` ([D47](../../decisions/D47-s04-accepted-s05a0-authorized.md), стратегия [D46](../../decisions/D46-asset-conversion-first.md), [план S05](../../stages/S05_ASSET_CONVERSION_PLAN.md)).

**Статус:** **`READY_FOR_REVIEW`** — не `ACCEPTED`. Решение о продолжении принимает продюсер после ревью ChatGPT.

**Кратко:** геометрия оригинальных `.cub` извлекается, декодируется и **реально отображается в Unity 6000.3.27f2** (3 образца из 3 + один дополнительный компонент модели). Потери и ограничения зафиксированы в §5; анимаций в ассетах Alpha **нет** — это статический вывод §7. Массовая конвертация не запускалась.

## 1. Исследованные форматы

| Формат | Где лежит | Что внутри | Итог |
|---|---|---|---|
| `.cub` | `data1.db` (2857 записей, 20 178 858 Б) | воксельная модель: `int32 width`, `int32 depth`, `int32 height`, `uint8[w·d·h·3]` (RGB, `(0,0,0)` = пусто) | **декодируется**, экспортируется в OBJ/Unity Mesh |
| обфускация блобов | все записи `data1..4.db` | табличный де-шаффл (44 `int32`) + побитовая инверсия каждого байта | **снята**, round-trip проверен |
| `.wav` | `data2.db` (93 записи) | звук | не нужен для геометрии, не проверялся |
| `.png` | `data3.db` (104 записи) | иконки UI/классов/навыков | не нужен для геометрии, не проверялся |
| `dict_en.xml`, `dict_de.xml` | `data4.db` | локализация | не нужен |
| `.plx` | `start/gui/help/quest-tag/cursor.plx` | поток `PlasmaGraphics` (UI/меню/шрифты/подсказки) | **не содержит моделей**; для CubeGame пересоздаётся средствами Unity |
| `.dat` / `.ttf` | `resource1.dat`, `resource2.dat` | проверено: `resource1.dat` — TrueType-шрифт (`PFFTM`), не таблица моделей | не относится к геометрии |

**Проверенные факты формата `.cub` (собственный декодер + независимое сравнение):**

- Заголовок — три `int32`: **width, depth, height**. Порядок подтверждён тремя независимыми способами: (a) арифметика размера блоба `12 + w·d·h·3` сходится для **всех 2857** записей; (b) силуэты превью (меч 3×13×37 — «тонкий, широкий, длинный», альга 8×1×36 — плоская лента); (c) независимая open-source реализация формата `CubeWorld` в `vengi` (`CubFormat.cpp`) читает те же три поля в том же порядке и отдельно отмечает, что depth/height для Cube World «перевёрнуты» относительно её собственной системы координат.
- Индекс вокселя: `(h * depth + d) * width + x`.
- Цвет — **один плоский RGB на воксель**, без альфы, без нормалей/UV/материалов; пустой воксель = `(0,0,0)`.
- Уникальных цветов в моделях мало: медиана **7**, среднее 9.6, максимум 57 (из 2857 моделей) — поэтому «один материал на цвет» практичен.
- В моделях встречаются **маркерные воксели** чистых цветов `(255,0,0)`, `(0,255,0)`, `(0,0,255)`; в `human-hair-m01.cub` — 298 красных, 4 зелёных, 10 синих. В движке `VoxelModel_set_data` такие воксели складываются в список «анкоров» (точек крепления/осей). В голове `human-head-m01` и в теле `porcupine-body` чистых маркеров **нет**.
- Плотность: 6 714 858 вокселей всего, из них 1 463 958 (21.8 %) заполнены. Размерностей 784; самая большая модель — `Sphinx01.cub` (64×50×64, 204 800 вокселей), 2822 модели ≤ 16 384 вокселей.

**Система идентификаторов:** идентификатор модели — её **имя файла (ключ блоба)**. Клиент содержит **захардкоженную таблицу имён** (`string`-константы в `Cube.exe`, 2550 вхождений `*.cub`) и грузит их по имени из `data1.db`; порядок таблицы даёт внутренний индекс модели (в коде видна подготовка таблицы спрайтов размером `0xa09` = 2569). 2857 ключей в базе > 2550 имён в таблице клиента — часть моделей либо не грузится этой сборкой, либо составляется из шаблонов.

**Связи между частями:** `.cub` — **один плоский воксельный грид**, внутри нет ни объектов, ни групп, ни иерархии, ни скелета. Составные существа/персонажи собраны из **отдельных файлов**: `troll-head/-body/-arm/-hand/-foot`, `human-head-*/human-hair-*` + общие `body1..5.cub`, `glove.cub`, `orc-hand.cub`. Именование единообразно: `<раса|материал>-<часть>[-<пол|вариант>][-random<N>]`. Смещения и масштабы частей при сборке в `.cub` **не хранятся** (см. §5, §7).

## 5. Измерения, потери информации и ограничения

**Что сохранилось полностью (проверено независимыми проверками):**

- Воксельная геометрия: число видимых граней совпадает с пересчётом по воксельной сетке **и** в собственном меше, **и** после импорта OBJ (`tris = 2 × квада`, расхождений 0).
- Габариты и пропорции: `bounds` собственного меша = `bounds` импортированного OBJ = протяжённость заполненных вокселей (x=width, y=height, z=depth) — совпадение до 0.001 юнита.
- Площадь поверхности: суммарная площадь квадов = «внешняя» площадь воксельного солида (скрытые грани отсечены) — проверено `verify_export.py`.
- Цвета: один материал на цвет; после импорта OBJ значения `Kd` совпадают с исходными `(r,g,b)` вокселей.
- Раздельные части модели: части персонажа — отдельные модели; каждая конвертируется независимо и остаётся отдельным объектом/мешем.

**Что потеряно или требует отдельного решения:**

| Потеря / риск | Факт | Следствие |
|---|---|---|
| **Маркерные воксели становятся видимой геометрией** | в `human-hair-m01.cub` есть чистые `(255,0,0)`, `(0,255,0)`, `(0,0,255)`; в Unity видны как зелёный/синий/красный воксели | нужен слой «маркеры отдельно»: при конвертации их следует исключать из меша и читать как анкоры; в пилоте они экспортированы как обычная геометрия (честно видно на скриншоте) |
| **Семантика цвета не переносится** | у волос белая оболочка + красное «ядро»: игра подкрашивает волосы цветом персонажа; плоский RGB даёт «белые волосы» | нужен этап «палитра/тинт»: часть цветов — не финальный цвет, а база под тинт. Не проверено, какие именно |
| **Масштаб частей при сборке неизвестен** | голова 18×16×16 против торса `body1.cub` 10×8×10; масштабы/смещения хранятся в коде клиента, не в файле | собрать персонажа «как в игре» из частей только средствами `.cub` нельзя; требует разбора кода (S05A-1) |
| **Нет нормалей, UV, сглаживания** | `.cub` хранит только RGB | нормали считаются по граням (плоское затенение); UV отсутствуют — текстурирование невозможно без генерации |
| **Нет рига/скелета/анимации** | в файле нет ни иерархии, ни весов (см. §7) | персонажи и существа — «жёсткие» наборы частей; анимация — отдельная задача |
| **Pivot = угол сетки (0,0,0)** | все модели начинают координаты с 0 по каждой оси; центр — произвольный | для сборки нужен собственный pivot/офсеты; в игре это делается кодом |
| **Ориентация осей** | принято `x → x`, `h → y` (вверх), `d → z`; лицо головы смотрит в +Z, меч «рукоять вниз, клинок вверх» | соответствует Unity (Y up); при импорте OBJ Unity сама не инвертирует оси — но это **наблюдение одного образца**, не гарантия для всех моделей |
| **Координаты и handedness** | OBJ (правосторонний, Y-up) импортирован в Unity без искажений (габариты совпали) | для отрицательных осей/зеркалирования специально не проверялось |
| **Квады** | экспорт в квадах; Unity триангулирует при импорте | проверено: треугольников ровно `2 × квадов` |

## 7. Анимации — предварительная разведка (только статика)

- **Файлов анимаций в поставке нет.** Инвентаризация всех строк путей в `Cube.exe`: `*.cub` — 2550, `*.png` — 98, `*.wav` — 95, `*.db` — 6, `*.plx` — 5, `*.ttf` — 1, `*.dat` — 2. Ни `*.anim`, ни иных клипов; в `data1..4.db` других расширений, кроме `.cub`/`.wav`/`.png`/`xml`, нет; `patch/` пуст; `.plx` — UI-потоки `PlasmaGraphics` (меню, помощь, курсор, теги квестов).
- **Анимация задаётся кодом.** В клиенте есть состояния: id состояния/атаки (`+0x68`, диапазон 0…0x77), `combat_selectAttackAnim`, `combat_getReloadFrames`; и есть механизм костей/матриц: `render_uploadBoneMatrices`, строка `MaterialBone`, а также общий движковый слой ключевых кадров (`Attribute_deserialize_int/vec3/vec4/matrix/scalar_keyframes`, `Attribute_deserialize_keyframes_v2/v3`, `Anim_playTrackByName`, `AnimMap_findValueByKey`, `Widget_updateAnimations`).
- **Как модели привязываются к анимациям:** по имеющимся данным — модель (`.cub`) даёт геометрию части; части существа перечислены отдельными файлами (`troll-arm`, `troll-hand`, …); трансформации частей вычисляет код (state id + процедурные позы + матрицы костей), а не файл клипа. Точная таблица «state id → поза/клип» **не восстановлена** (K-U3 остаётся `UNKNOWN`).
- **Можно ли восстановить структуру рига:** статически — да, но только через разбор кода сборки существа (какие части, какие смещения, какие оси вращения). В `.cub` этой информации нет. Это задача `S05A-1`.
- **Связь рук и оружия:** оружие — отдельная модель (`iron-greatsword`), крепление — через анкоры/код. В проверенных образцах оружия маркеров-анкоров не найдено; связь «рука ↔ оружие» статически **не подтверждена**.
