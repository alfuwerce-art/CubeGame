## 1. Главная цепочка: «команда → условие → action ID → предмет в руках → эффект»

Доказана для расходников (зелья/еда/бомба) и является образцом для остальных действий.

```
1. Очередь действий объекта: pEvent (структура действия + копия предмета)
2. GameController_handleObjectAction @ 0x4a2780        [GameController.cpp:42608-42648]
   условие входа: (char)pEvent[1] == 1  &&  creature+0x12c (таймер) < 1
   ветка A: subtype (pEvent+5) == 1 или 2   → creature+0x68 = 0x50   (action 80)
   ветка B: иначе                          → creature+0x68 = 0x51   (action 81)
   ветка C: subtype == 7                   → предмет копируется в список (Struct_reset_with256buf /
                                             Item_copyStruct / list_pushBack) — отдельная обработка
   после установки: creature+0x6c = 0, creature+0x128 = 0 (сброс таймера и «занятости»)
3. Отрисовка: Creature_drawModel @ 0x4128f0            [GameController.cpp:6408-6436]
   если action ∈ {0x50, 0x51}:
     cooldown = GameController_itemCooldown()           @ 0x4c6b80  [GameController.cpp:55766-55782]
        → 0 если item.type != 1; 3000 если item.type == 1 && item.subtype == 1; иначе 10000
     если creature+0x6c < cooldown  и  model = item_icon_id(creature+0x1e8) != 0:
        модель предмета рисуется в руке: позиция = середина между двумя опорными точками
        (vec3_add + scale 0.5), поворот rotateX по входной оси, масштаб из items
4. Переход: по завершении действия предмет расходуется, action сбрасывается; модель руки
   возвращается к оружию (ветка 0x50/0x51 — временная надстройка над обычной отрисовкой).
```

**Что это доказывает по существу вопроса «предметы в руках»:**

1. **Зелья/еда/бомба действительно рисуются в руке** — не как отдельная анимация, а как модель
   предмета, привязанная к действию 80/81 и к таймеру кулдауна. Меш берётся из
   `item_icon_id(creature+0x1e8)`, т.е. **та же модель, что иконка/модель предмета**, а не отдельный
   «фляга-в-руке».
2. **Кулдаун предмета — свойство предмета, а не действия**: 3 с для `type 1, subtype 1` (LifePotion),
   10 с для остальных расходников типа 1; для не-расходников 0.
3. **Действий два** (0x50 и 0x51), различаются подтипом объекта действия (1/2 против прочих); что
   именно различает 1 и 2 — `UNKNOWN` (кандидат: питьё против еды; не доказано).
4. **Подтип 7 (Bomb)** идёт в отдельную ветку: предмет копируется в список (закладка бомбы), а не
   просто «пьётся». Это согласуется с `combat_updateBombFuse @ 0x43cf20` (фитиль бомбы) и с тем, что
   бомба в таблице имён — `type 1, subtype 7`.

**Ограничение:** поза/анимация тела при 0x50/0x51 в этих строках не восстанавливается (она в общем
конвейере позы по action id). То есть «есть ли анимация питья» — **не доказано**; доказано, что
**модель предмета в руке есть** и что действие имеет собственный id.

## 2. Отрисовка предметов на существе: слоты, условия, что именно рисуется

`Creature_drawModel @ 0x4128f0` (тело: `GameController.cpp:1812…7390`) — единственный путь отрисовки
всех существ. Базовая пасса слотов — строки 2111…2123: модель берётся из `item_icon_id(creature + смещение)`.

| Смещение слота | Доказанный тип/смысл | Когда рисуется |
|---|---|---|
| `+0x300` | не идентифицирован («Special»?) | **не рисуется** (в `drawModel` не встречается) |
| `+0x418` | тип 8 (Amulet) | всегда, если предмет есть |
| `+0x530` | тип 4 (ChestArmor) | всегда |
| `+0x648` | тип 6 (Boots⁰) | всегда |
| `+0x760` | тип 5 (Gloves⁰) | всегда |
| `+0x878` | тип 7 (ShoulderArmor) | всегда |
| `+0x990` | тип 3, основное оружие | всегда |
| `+0xaa8` | тип 3, второе оружие/вторая рука | всегда |
| `+0xbc0` | тип 9 (Ring) | **не рисуется** |
| `+0xcd8` | тип 9 (Ring) | **не рисуется** |
| `+0xdf0` | предмет «за спиной» | `creature+0x124 & 0x200` (строка 7167): `(0,+2,−2)`, масштаб 0.8 |
| `+0xf08` | предмет «впереди» | `creature+0x124 & 0x10` (строка 5997) **или** action `0x6b` (строка 6026): Z `+8` / `−9`, масштаб ×2 |
| `+0x1020` | предмет состояния `'R'` | action `0x52` (строка 6437) |
| `+0x1e8` | **текущий расходник** (не слот экипировки) | action `0x50`/`0x51` (см. §1) |

Шаг между слотами — `0x118`, слоты идут непрерывно от `0x300` до `0x1020` (13 штук); базовая пасса отрисовки
(`drawModel` 2111-2123) запрашивает модели только для 7 из них:`+0x530, +0x648, +0x760, +0x878, +0x418, +0xaa8, +0x990`.

**Подтверждает и уточняет прежние данные:**

* 13 слотов экипировки стоят с шагом `0x118`; `getEquipmentSlotPtr @ 0x47b1b0`
  (`GameController.cpp:28374-28433`) перебирает **12** смещений `0x418,0x530,0x648,0x760,0x878,0x990,
  0xaa8,0xbc0,0xcd8,0xdf0,0xf08,0x1020`; слот `+0x300` в перебор не входит (вероятно, «Special»).
* `Equipment_sum_slot_values @ 0x446150` (`Interface.cpp:2938-2987`) независимо подтверждает
  **типы** предметов в слотах: `0x990`→тип 3, `0xaa8`→тип 3, `0x530`→тип 4, `0x648`→тип 6,
  `0x760`→тип 5, `0x878`→тип 7, `0x418`→тип 8, `0xbc0`/`0xcd8`→тип 9.
* **Кольца (`0xbc0`, `0xcd8`) и слот `+0x300` в отрисовке не участвуют** — они не видны на модели.
  Это отвечает на вопрос «есть ли модель у кольца»: **нет**.
* **Дельтаплан/лодка/лампа**: у них отдельные типы (`0x17`, `0x18`), слоты `0xf08`/`0xdf0` подходят
  по позиции (впереди/за спиной), но связь «тип предмета → слот `0xf08`/`0xdf0`» **не доказана** —
  условием там служат биты `creature+0x124`, а не тип. Пометка: `ГИПОТЕЗА`, требует проверки
  (см. §8 A-6).

## 3. Зависимость от оружия: подтип меняет и меш, и позу

Доказанные ветки внутри `drawModel`, где **подтип оружия в руке** меняет отрисовку:

| Строка | Условие | Действие |
|---|---|---|
| 2466 | `+0x990` тип 3 **и** `+0x991` подтип `0x0e` | подменяет модель текущего действия на модель предмета (`item_icon_id(+0x990)`), сбрасывает `self[0x38]` |
| 2634 | `+0x990` тип 3 **и** подтип `0x0d` | задаёт фиксированный вектор позы (щит), уходит в общую ветку `LAB_0041e65a` |
| 3582 | `+0x991` подтип `0x07` | меняет один из компонентов трансформации на `0x42480000` (50.0) |
| 3588 / 3649 / 3677 / 3710 | `+0x990` (или `+0xaa8`) тип 3 | подставляет модель `vectorU32_at(0x348)` как «оружие» в позу действия |
| 3599 | `+0xaa9` подтип `0x06` | ветка второй руки |
| 6461 / 6494 | `+0x990`/`+0xaa8` тип 3 **и** подтип 6 или 7 | рисует дополнительную модель `vectorU32_at(0x347)` (болт/снаряд) |

**Вывод:** в Alpha анимация действия **не** задаётся парой «класс + оружие» напрямую; задаётся
**action id** (`creature+0x68`), а подтип оружия влияет (а) на выбор доступного действия и (б) на
меш/смещения внутри действия. Это подтверждает архитектурное решение S05 (поза по action id), но
показывает, что **слой «оружие → оверлей позы» в Unity обязателен** и что для щита/бумеранга/арбалета
нужны отдельные ветки.

**Маска свойств предмета `creature+0x7e` (16 бит) — четыре независимых потребителя:**

| Бит | Потребитель | Смысл |
|---|---|---|
| `0x8`, `0x10` | `stat_calcWeaponDamage @ 0x43dc60` | апгрейды урона оружия |
| `0x1a00` | `ability_isChanneled @ 0x444680` | гейт канальных способностей |
| `0x4` | `projectile_getMuzzlePosition @ 0x446bb0` | выбор точки вылета снаряда |
| `0x1` | `drawModel` строка 7150 | дополнительный поворот при отрисовке |

Это новый подтверждённый факт: «свойства оружия» — не отдельные поля, а битовая маска `+0x7e`, и она
влияет на урон, на доступность каналов, на снаряды и на отрисовку. В `M0-00B` маска не была отражена.

## 4. Способности, ресурсы, кулдауны, каналы

Полные таблицы — [ALPHA_STATIC_TABLES_ITEM_SKILL §3–4](../research/alpha2013/ALPHA_STATIC_TABLES_ITEM_SKILL.md).
Кратко, что теперь **доказано** (адреса прямые):

1. **16 узлов способностей с именами** (`0x15 RangerKick`, `0x22 HealingStream`, `0x30 Intercept`,
   `0x31 Teleport`, `0x32 Retreat`, `0x36 Smash`, `0x4f Sneak`, `0x56 Cyclone`, `0x58 FireExplosion`,
   `0x60 Shuriken`, `0x61 Camouflage`, `0x63 Aim`, `0x64 Swiftness`, `0x65 Bulwark`, `0x66 WarFrenzy`,
   `0x67 ManaShield`). Совпадает 16/16 с ранее известным списком P-15 — независимая проверка метода.
2. **Кулдаун** — `Ability_get_cooldown @ 0x444860`: значения 2…10 с, часть делится на haste, часть
   фиксирована; для роли 3/5 (союзник/NPC) кулдаун не считается вовсе.
3. **Мана** — `ability_getManaCost @ 0x43e6a0`: `base − powerFactor·scale`, 15 разных пар констант,
   у большинства способностей стоимость зависит от `powerFactor`, у `0x48` — фиксированные 15000.
4. **Стамина** — `combat_getStaminaCost @ 0x444270`: база 100…600, делится на haste.
5. **Канал** — `ability_isChanneled @ 0x444680`: 32 id, плюс гейт по маске `+0x7e & 0x1a00`.
6. **Снаряды/эффекты** существуют отдельными системами: `projectile_getMuzzlePosition @ 0x446bb0`,
   `CombatBehavior_spawnProjectileHit @ 0x596d30`, `CombatBehavior_spawnHitParticles @ 0x59a800`,
   `Creature_spawnDeathEffects @ 0x59b180`, `render_build_projectile_mesh @ 0x4c04c0`,
   `GameController_spawnEffectMesh @ 0x4bd160`, `GameController_spawnRibbonEffect @ 0x4bbd80`,
   `World_emitDecalOrParticle @ 0x5f6d50`, `Entity_onStateChangeEmitEffect @ 0x5a58e0`.
   **Но**: какие модели/частицы какой эффект рисует — не выписано; это остаётся `BLOCKED` для
   переноса (R-3 в реестре D65).

**Важно про планирование M0-05B:** пространство action id шире ранее зафиксированного — в
`ability_isChanneled` встречаются `0x91,0x92,0x93`. Реестр «≤0x77» из старых отчётов использовать как
полный нельзя.

**Класс → способности:** `drawItemTooltip @ 0x4a28c0` читает `Creature+0x140` (1…4 = Warrior/Ranger/
Mage/Rogue) и вызывает `item_classifyRecursive`; прямого списка «класс → набор action id» в прочитанном
коде нет. Распределение по именам (Warrior: Smash/Cyclone/Bulwark/WarFrenzy; Ranger: RangerKick/Retreat/
Aim/Swiftness; Mage: FireExplosion/ManaShield/Teleport; Rogue: Sneak/Camouflage/Shuriken) — `ГИПОТЕЗА`.

## 5. Движение, лазание, плавание, дельтаплан, лодка

**Доказано (и не меняется от этого прохода):** навыки-ранги `0 = Taming, 1 = Riding, 2 = Climbing,
3 = HangGliding, 4 = Swimming, 5 = BoatDriving`, `6…10 = Ability1…5` — прямо из таблицы имён;
массив `i32[11]` у существа — по `memcpy(…, param_1 + 0x1138, 0x2c)` (44 байта = 11 × 4) и
`level = *(int*)(self + 0x1138 + slot*4)`.

**Не доказано (честный отрицательный результат этого прохода):**

* **Прыжка в коде не найдено** ни как отдельной функции, ни как константы: целенаправленный поиск
  по `+0x1138`/`+0x1194`/`+0x1190` дал только считывание рангов и стамины, функции «jump» в
  `RENAMES.tsv`/`GAP_ANALYSIS.md` нет. Ранее зафиксированное «констант прыжка нет вообще» —
  **подтверждается**; в Unity `PlayerMotor.JumpSpeed = 7f` остаётся `PLACEHOLDER_NOT_ALPHA`.
* **Лодка и езда** — механика не найдена (в таблицах есть только предмет `0x17/1 Boat` и
  навык 5). Статус `UNKNOWN` сохраняется.
* **Плавание/лазание/дельтаплан** — есть имена навыков, иконки (`"swimming.png"`,
  `"climbing.png"` в `GameController.cpp:21395-21403`), но формулы (`@swimmingspeed`,
  `@climbingpower`, `@flyingspeed`) в этом проходе не перепроверялись — статус `PARTIAL`, как в
  `I_movement.md`.
* **OQ-23 (масштаб единиц)** остаётся `OPEN`: без него ни одна дистанция/скорость не переводится в
  блоки/с. Это блокер M0-03B и M0-06C, а не «деталь баланса».

## 7. Матрица новых и уточнённых записей

Формат: `id | вид/тип | доказательство (символ/адрес/строка) | conf | в Unity | зависимость | M0 | тест | открытый вопрос`.

`CORE_ONLY`.

   отчётов, а не из этого прохода.

   контент (D54/D46).
