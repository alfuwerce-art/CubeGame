# CubeGame — производственные пайплайны (единый проект)

**Дата:** 2026-11-06. **Статус:** **ACCEPTED 2026-11-06** — утверждённый производственный регламент; его принятие НЕ разрешает новые игровые этапы и не является приёмкой механик/ассетов.  
**Действующие источники:** [ACTIVE_STAGE](../ACTIVE_STAGE.md), [ROADMAP_DRAFT](../planning/ROADMAP_DRAFT.md), [MULTI_AGENT_WORKFLOW](../agents/MULTI_AGENT_WORKFLOW.md), [ADR-0001](../architecture/ADR-0001-modular-monolith.md), [S05 пайплайн](../architecture/UNIVERSAL_ASSET_ANIMATION_PIPELINE.md), [D46](../decisions/D46-asset-conversion-first.md), [D35](../planning/DECISIONS_001-036.md).

## 1. Зачем нужен этот документ

**ROADMAP говорит «какой продукт и этап когда». PIPELINE говорит «как агент из принятого задания производит проверяемый артефакт».** Нельзя смешивать:
- **ACCEPTED DESIGN** = выбран игровой принцип;
- **AUTHORIZED STAGE** = разрешено воплощение ограниченного объёма;
- **TEST PASS** = прошла конкретная проверка;
- **ART APPROVED** = продюсер принял конкретный визуальный образец;
- **ACCEPTED STAGE** = этап целиком закрыт продюсером.

Единый шаблон для всех пайплайнов: **вход → производственная операция → выход → машинный тест → визуальная/игровая проверка → ревью → принятие/повтор**. Каждый шаг имеет ответственного, входной SHA, критерий перехода и известные блокеры.

## 1.1. Два уровня пайплайна и обязательный аудит совместимости

**Уровень 1 — общий маршрут любой задачи:** утверждённое ТЗ/референс → анализ связей → выбор Claude/Codex или DeepSeek → работа в своей сессии/ветке → checkpoint в `PROJECT_MEMORY.md` при остановке → итоговая комплексная проверка и ревью → решение продюсера. Не считать каждое промежуточное действие отдельной полной приёмкой.

**Уровень 2 — специализированная последовательность:** у оружия, персонажа, существа, окружения, UI, NPC и игровой механики свои входы и стадии изготовления. Такой маршрут обязателен в ТЗ соответствующей категории и не подменяет общие полномочия или авторизацию из `ACTIVE_STAGE.md`.

**Перед реализацией любой самостоятельной функции/ассета агент заполняет матрицу влияния и совместимости.** Это не догадка «ничего не сломает»: каждый вывод ссылается на существующий модуль, файл, контракт или утверждённое решение; неподтверждённые зависимости отмечаются `UNKNOWN`.

| Поле матрицы | Что установить до начала работы |
|---|---|
| **Затрагиваемые механики** | Какие существующие игровые действия, правила и системы изменяются напрямую или косвенно (бой, экипировка, персонаж, AI/NPC, лут, мир, UI, сохранения и т. д.) |
| **Затрагиваемые функции/компоненты** | Реальные модули, классы, публичные API, события, данные, Unity scenes/prefabs, анимационные контроллеры, файлы конфигурации, сборки и зависимости; точные пути после осмотра репозитория |
| **Обязательная совместимость** | С какими уже действующими механиками и процессами результат должен работать без новых параллельных реализаций; какие контракты, входы, выходы и инварианты сохраняются |
| **Риски поломки** | Что может перестать работать: анимации, хитбоксы, экипировка, старые сейвы, генерация по seed, производительность, сериализованные ссылки, пайплайны сборки, другие ассеты |
| **Обратные зависимости** | Кто вызывает/читает изменяемый код, кто владеет данными и кто зависит от изменённого формата; влияние на принятые этапы |
| **Изменение контрактов** | Можно ли использовать текущий интерфейс/адаптер; если нужен разрыв API, миграция сохранений, новая подсистема или архитектурный рефакторинг — `BLOCKED / OPEN DECISION` до отдельного согласования |
| **План сопряжения** | Куда именно объект подключается в Unity и через какие уже существующие адаптеры, слоты, события, конфиги и точки привязки; порядок подключения |
| **Проверка совместимости** | Названные интеграционные/регрессионные сценарии на завершении этапа: что должно продолжать работать и по каким наблюдаемым признакам |
| **Способ отката** | Как вернуться к исходному поведению через Git, не повредив сохранения, сцены, префабы и результаты принятых этапов |

**Порядок действий:** агент самостоятельно читает релевантные файлы по карте `AGENTS.md`, строит матрицу → выявляет противоречия и риски → дополняет ТЗ способом совместной работы → реализует только в разрешённом scope. Если зависимость нельзя подтвердить, не писать `COMPATIBLE` без доказательств. При критическом разрыве совместимости — согласовать отдельное решение до изменения архитектуры.

**Проверки:** на протяжении работы только необходимые короткие проверки рисков; в конце этапа/цельного пакета — регрессионная проверка всех затронутых систем из матрицы. Визуальное утверждение каждого переработанного образца по D35 делается **до масштабирования партии**, даже если техническая итоговая проверка этапа будет позже.

## 1.2. Пример специализированного маршрута: двуручный меч

Это **шаблон процесса**, а не разрешение сейчас производить новый меч:

1. **Референс и ТЗ:** тип/стиль, масштаб, игровой вид, референс, требуемое поведение и то, что уже принято в GDD.
2. **Источник:** для M0 исследовать доступный эталон Alpha в разрешённых границах; для M1 — самостоятельная модель или переработка согласно D46/D31. Нет необходимого референса/права использования — запросить данные/решение.
3. **Модель и технический контракт:** выбранный инструмент/скрипт, геометрия, pivot, масштаб, материалы, рукоять, точки хвата, коллизии; без создания параллельного рига.
4. **Конфигурация оружия:** существующий тип предмета, слот, крепление, характеристики и боевые контракты; новые параметры — только после утверждения.
5. **Анимационная совместимость:** рука/двуручный хват, доступные действия, события удара и физические пересечения, совместимость с текущим контроллером.
6. **Интеграция в Unity:** подключить через существующие системы экипировки, боя и персонажа без разрастания архитектуры.
7. **Итоговая регрессия и личная визуальная приёмка:** тест экипировки/смены оружия, анимаций и контактов, сохранений и обратимости; кадры/видео образца, решение продюсера.

**Обязательная матрица меча (пример целей проверки, не утверждение существования конкретного API):** бой и расчёт урона; слот и данные экипировки; контроллер персонажа/анимации и точки хвата; коллизии/взаимодействие с врагами; инвентарь/лут; сериализация предмета и сохранения. В каждом TASK проверить фактическое наличие этих связей в коде, выделить `EXISTING / PROPOSED / NOT_APPLICABLE / UNKNOWN` и не придумывать имена классов.

Другие маршруты:
- **Персонаж:** референс → модель/части тела → скелет и совместимость → анимации → контроллер → игровые действия и Unity.
- **Существо:** референс → модель/риг → базовые состояния → поведение/AI → атаки → подключение к миру, боям и луту.
- **Окружение:** референс → block/voxel геометрия → материалы/свет → коллизии и генерация → LOD/оптимизация → интеграция в чанки.
- **Игровая механика:** утверждённый GDD → контракты данных/событий → правила Core → взаимодействия UI/мира/AI → сохранения → Unity и итоговая регрессия.
- **NPC:** модель состояния/памяти → правила выбора действий → события и связи с фракциями/миром → диалоги → интеграция; модель LLM не должна самовольно менять авторитетное игровое состояние.

Для каждого маршрута сохранять общий шаблон TASK, карту зависимостей, checkpoint в памяти и финальную точку проверки. Детальные технические рецепты размещаются в существующих профильных playbook **по необходимости**, не заводить новый документ на каждый объект.

## 2. Контур A. Концепция / GDD / принятие механики

1. **Идея:** описание желаемого опыта игрока, референс, что решает, какую систему затрагивает.
2. **Проверка ограничений:** уже принятые Dxx, совместимость с Alpha M0, производительность, влияние на NPC/мир/сохранения, бюджет.
3. **Рабочая механика:** правила, входы/выходы, действия игрока, реакция мира, крайние случаи, UI; маркируется DRAFT.
4. **Игровая проверка на бумаге:** один базовый сценарий, один исключительный, один конфликт с другими системами.
5. **Решение продюсера:** принять / отправить на переработку / отложить / отменить. Только принятое превращается в Dxx ACCEPTED.
6. **Синхронизация:** обновить GDD и PROJECT_MEMORY (разрешённая ветка, не main); новый этап Unity не открывать.

**Выход:** Dxx + однозначная ссылка в GDD + граница ещё открытых решений.

## 3. Контур B. Новая игровая функция в Unity

| Стадия | Действия | Признак завершения |
|---|---|---|
| **B0. Вход** | Принятая механика + AUTHORIZED задача + Dxx/ADR + Git SHA | Нет противоречия/неразрешённой зависимости |
| **B1. Вертикальный срез** | Минимальный работающий пример с тестовой сценой/заглушками | Можно запустить и проверить правило |
| **B2. Логика** | Отделить правила в Core, данные/настройки, сервисы, UI адаптер | Не создаётся неявной зависимости Core от UnityEngine |
| **B3. Проверки** | Unit/EditMode/PlayMode, негативные и граничные сценарии, регрессия прежних подсистем | Конкретные проверки PASS или честный FAIL/BLOCKED |
| **B4. Игровая проверка** | Реальный игрок/продюсер смотрит темп, управление, читаемость, удовольствие | Доказательства: запись/скрин/сцена/инструкция воспроизведения |
| **B5. Ревью** | Independent diff review, исходный SHA, тесты, сохранения, ограничения | READY_FOR_REVIEW и список замечаний |
| **B6. Приёмка** | Продюсер решает правки/ACCEPTED, Git merge только по прямому разрешению | Завершён документально, memory/stage синхронизированы |

**FAIL при:** ошибке сохранений, нарушении утверждённой механики, регрессии, пропуске фактической игровой проверки, подмене PARTIAL на PASS. Не превращать `test green` в художественную/геймплейную приёмку.

## 4. Контур C. Перенос эталонов Cube World Alpha → Unity

**Этот контур специфичен для M0 и S05, не для произвольного создания новых моделей.** Действующий detailed source — `docs/architecture/UNIVERSAL_ASSET_ANIMATION_PIPELINE.md` (его собственный статус DRAFT) и отдельные playbook/S05 TASK.

Этапы:
1. **Инвентаризация эталона:** какие исходные модели, состояния, виды, размеры, оттенки, свойства и ограничения релиза; всё закрытое остаётся локально.
2. **Получение доказательств:** статический разбор формата, рантайм позы, временные диаграммы, анимационные действия. Для каждого числа/кадра — проверяемый источник.
3. **Конвертация/адаптация:** валидный межформатный экспорт → собственные материалы/геометрия Unity → совместимый риг/план тела → данные анимации.
4. **Автоматическая верификация:** число граней, трансформы, scale/handedness, привязки костей, длительность/позы, независимая регрессия.
5. **Визуальный просмотр:** реальная сцена Unity, вид со всех сторон, типовые движения, оружие в руке, тени, силуэты.
6. **Решение по одному образцу:** продюсер утверждает/отклоняет модель. **По D35 каждый переработанный образец лично показывается на приёмку.**
7. **Масштабирование:** только после эталонного пилота; автоматические партии не являются автоматическим художественным одобрением.

**Жёсткие ограничения:** Alpha оригинал `D:\Games\Cube world` READ-ONLY; оригинальные закрытые ассеты/бинарники/исходный код не публиковать; S05B не начинать без AUTHORIZED; визуальная конвертация `PASS` не доказывает перенос анимации.

## 5. Контур D. Собственные 3D модели, анимации и окружение (будущий M1)

1. **Арт-бриф:** художественный эталон [ART_DIRECTION_DRAFT](../art/ART_DIRECTION_DRAFT.md) + референсы + читаемость на игровой камере.
2. **Силуэт и масштаб:** 1–3 грубых варианта; выбрать один целевой образец, не генерировать сотню неподтверждённых ассетов.
3. **Voxel/block модель:** единый масштаб блоков, совместимые якоря, материал/палитра, отсутствие случайных зазоров.
4. **Риг/анимация:** использовать согласованные family rig/контроллеры; **D32:** на одной переработанной модели проверить исходную анимацию, затем одну новую.
5. **Материалы/свет/эффекты:** тест в эталонной сцене и на целевых настройках качества; нет фотореалистической подмены стиля.
6. **Проверка:** naming, pivot, LOD/батчинг, memory, коллизия, свет, движение, падение производительности.
7. **Ревью:** картинка+видео+Unity сцена, личное ART APPROVED каждого переработанного образца по D35.
8. **Импорт партии:** только из одобренных единиц, отчёт и возможность отката без вмешательства в accepted-код.

**Статус:** предлагаемый общий метод, не утверждение конкретного софта/Blender/обязательной AI-генерации/авторского стиля. Генерируемые AI-референсы не заменяют игровой ассет и приёмку в движке.

## 6. Контур E. Процедурные системы, NPC, экономика и фракции (будущий M2)

**Правило:** сначала один работающий **локальный причинный цикл**, затем ширина мира.

Малый срез: **ресурсный лагерь → перевозка → деревня → нападение → недопоставка → реакция NPC/стражи → действие игрока → сохранённый результат**.

Этапы: data contracts → deterministic simulation → краткая сводная симуляция вдали от игрока → память и видимость информации NPC → LLM диалоги поверх проверенного состояния → события/квесты из причинных условий → E2E тест → баланс производительности.

**Масштаб/нагрузка:** в поле зрения — полная игровая логика и анимация; вдали — упрощённая группировка; если мир закрыт — не обещать фоновую симуляцию. Нет обязательных LLM-запросов на каждого моба или каждую шахтёрскую кирку.

## 7. Контур F. Интеграция/оптимизация/релиз (будущий)

1. Регрессия: core, saves/versioning, gameplay, negative tests, воспроизводимость seed.
2. Профилирование CPU/GPU/memory и измерения на заданных настройках; исправления без потери игрового поведения.
3. UX/доступность, отказоустойчивость сохранений, настройки качества, локализация.
4. Аудит сторонних ассетов, лицензий, секретов, исходников Alpha; без этого production release заблокирован.
5. Билд/инсталлятор, тесты запуска на чистом ПК, журнал релиза, rollback и обновления.

**Не выполнять весь F сейчас**: это контур будущих этапов, а не санкция массовой разработки.

## 8. Файлы и полномочия

- `AGENTS.md`: утверждённые 2026-11-06 общие и ролевые правила; единый нормативный источник.
- `PROJECT_MEMORY.md`: оперативная память текущего этапа + CHECKPOINT; обновляют все агенты, чистит только GPT. Историю этапов GPT ведёт в `docs/STAGE_HISTORY.md`.
- `docs/ACTIVE_STAGE.md`: единственная точка авторизации и статуса активного этапа.
- `docs/stages/<TASK>.md`: точные цели/тесты/границы/назначенный агент.
- `docs/reports/<TASK>_REPORT.md`: факты выполненного и оставшегося, SHA/тесты.
- `docs/decisions/Dxx...`: принятые правила, отмены и история.
- `docs/architecture/ADR-...`: утверждённые технические контракты; проектные гипотезы отдельно.

**Статусы каждой единицы:** DRAFT → AUTHORIZED → IN_PROGRESS → READY_FOR_REVIEW → ACCEPTED (только продюсер). Возможны BLOCKED/REVIEW_FIX с сохранением данных о причинах. Объём DRAFT не становится автоматически работой агента.

## 8.1. Экономный QA и управляемая очистка проекта

- При постановке этапа задать **одну итоговую точку проверки**: необходимые EditMode/PlayMode, ручной визуальный просмотр, регрессии и независимое ревью. Не требовать полный набор тестов после каждого мелкого действия или промежуточного коммита.
- Во время исполнения использовать только дешёвые проверки по конкретному риску: компиляция после критичного рефакторинга, проверка сохранений перед миграцией, проверка форматов при массовых операциях. Блокирующие дефекты проверяются адресно до продолжения.
- В завершение этапа включать **инвентаризацию ненужных компонентов**: список кандидатов, зависимости и Unity-ссылки, решение keep/deprecate/remove, дифф удаления, способ отката и регрессию затронутых систем. Без доказанной неиспользуемости и разрешённого scope не удалять.
- Маршрутизация задач: Claude/Codex взаимозаменяемы для тяжёлых систем и продолжения по HANDOFF при лимитах; DeepSeek выполняет ограниченные исправления, локальные функции и интеграцию, а сложный перенос/переделку — только как разрешённый эксперимент.

## 9. Универсальный Definition of Done

Независимо от типа задачи результат не считается готовым к ревью без общего минимума:

| Тип результата | Обязательный минимум перед `READY_FOR_REVIEW` |
|---|---|
| **Документ / дизайн** | источник решения, статус DRAFT/ACCEPTED_DESIGN, список OPEN-вопросов, отсутствие противоречий с поздними Dxx |
| **Код / Unity** | исходный SHA, матрица влияния/совместимости и затронутые контракты, изменённые файлы, итоговые автоматические и интеграционные проверки, негативный сценарий по риску, инструкция запуска, регрессия затронутых систем |
| **Исследование / reverse** | происхождение данных, разделение VERIFIED/PARTIAL/UNKNOWN, воспроизводимый метод, запрет выдавать реконструкцию за оригинал |
| **3D / анимация / визуал** | Asset ID, источник/лицензия, матрица сопряжения с ригами/анимациями/игровыми системами, Unity-сцена, ракурсы/видео, техническая проверка, отдельный статус `ART_APPROVED` только от продюсера |
| **Интеграция / релизный шаг** | совместимость сохранений/версий, профилирование где применимо, rollback-план, отсутствие секретов и закрытых Alpha-ассетов |

Для любого типа результата дополнительно обязательны:
- ветка и точный commit SHA;
- `git status` без неописанного мусора;
- понятный способ отката;
- список того, что **не** проверялось;
- независимое ревью для значимых изменений; самопроверка исполнителя не заменяет ревью;
- явное подтверждение продюсера для `ACCEPTED`, `ART_APPROVED` и merge.
