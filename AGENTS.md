# CubeGame — правила для ИИ-агентов

**Единственный рабочий репозиторий проекта:** `alfuwerce-art/CubeGame`. Действующая цель — собственная игра на Unity. Автоматический конвейер создания моделей закрыт решением [D95](docs/decisions/D95-single-repository-close-model-pipeline.md).

## Перед работой — короткий обязательный контекст

1. Прочитать [PROJECT_MEMORY.md](PROJECT_MEMORY.md), [docs/ACTIVE_STAGE.md](docs/ACTIVE_STAGE.md), [Concept](docs/CONCEPT.md) и этот файл.
2. Для **конкретной** задачи выборочно открыть релевантные GDD, Roadmap, решения, ADR и профильный [skill](.dsh/skills/). Не загружать все отчёты и архивы в постоянный контекст.
3. Проверить `git status`, реальный GitHub HEAD, рабочую ветку, PR и явно разрешённый scope. Перед записью при доступном Node выполнить `node tools/harness/preflight.mjs`.
4. История Alpha/M0/Factoria не является активным ТЗ. При конфликте источников фиксировать блокер и запрашивать решение, не фантазировать реализацию.

**Правила по слоям:** [HARNESS_ARCHITECTURE](docs/agents/HARNESS_ARCHITECTURE.md). Общие принципы здесь; узкие процедуры — в skill, подсчёты и сверки — в скрипте, обязательные машинные блокировки — в проверенном hook/permissions/CI. Никто не меняет эти границы автоматически.

## Роли и полномочия

- Владелец — игровой дизайн, художественные решения, разрешение задач, приёмка и merge.
- ChatGPT — архитектура, проектные решения для согласования, ревью и проверка соответствия документации.
- DeepSeek Harness / Codex — исполнение явно поставленных задач, код, локальные инструменты, проверки и отчёты; роли внутри задачи задаёт владелец.

Никто из агентов не может принимать художественные решения или ставить `ACCEPTED` за владельца. Если технология, модель, интерфейс или архитектура не утверждены, нельзя выдавать их за принятые.

## Границы

- **Не запускать и не восстанавливать** прежний конвейер моделей: его оркестрацию, ComfyUI/Tripo workflow, массовую генерацию, фабрику моделей, автоматические риги, предыдущие манекены, пресеты и производственные контракты. Требуется новое прямое решение владельца.
- Не изменять сторонние репозитории, секреты, системные настройки, оплачиваемые сервисы или чужие рабочие копии без отдельного разрешения.
- Игровой Unity-код и утверждённые игровые механики сохраняются. Удаление или замена кода требует анализа зависимостей и отдельного задания.
- Перед записью: `git status`, отдельная рабочая ветка, контроль diff, секретов и лицензий. Не делать force-push и не удалять историю.
- Результат задания: SHA/ветка/PR, изменённые файлы, фактические тесты, блокеры и воспроизводимые проверки. `READY_FOR_OWNER_REVIEW` не означает `ACCEPTED`.
- Не менять каноническую ветку, не сливать PR и не удалять удалённые данные без разрешённой операции.

После одобренного изменения синхронизировать память, активную задачу, GDD, Roadmap и реестр решений, не переписывая прошлые Git-коммиты.

## Навигация и технические имена

- Для реальных имён кода искать определения и использования, затем сверять с [NAME_REGISTRY](docs/architecture/NAME_REGISTRY.md) и [DEPENDENCY_MAP](docs/architecture/DEPENDENCY_MAP.md); реестр имён пока пустой шаблон, не выдумывать API.
- Профильный навык брать из [SKILLS_INDEX](docs/agents/SKILLS_INDEX.md), один под реальную задачу. Не исполнять все workflows автоматически; скилл не разрешает установку Blender, Unreal или изменение GDD.
- Действующие инструменты и варианты подключения — [DSH_PLUGIN_EVALUATION](docs/agents/DSH_PLUGIN_EVALUATION.md). Никакого изменения пользовательского профиля DSH без локального разрешения и проверки.
- [D96](docs/decisions/D96-ai-harness-unreal-research.md) разрешает подготовить исследовательскую документацию и навыки. Unreal — отдельный эксперимент; **Unity остаётся движком игры**.
